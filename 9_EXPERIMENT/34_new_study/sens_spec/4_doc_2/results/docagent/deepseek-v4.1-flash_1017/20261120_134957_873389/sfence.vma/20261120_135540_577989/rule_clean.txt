RULE 1: Executing SFENCE.VMA in M-mode is permitted and is not trapped by mstatus.TVM or hstatus.VTVM.
RULE 2: Executing SFENCE.VMA in S-mode/HS-mode with V=0 when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 3: Executing SFENCE.VMA in S-mode/HS-mode with V=0 when mstatus.TVM=0 is permitted and does not raise an illegal-instruction exception due to TVM.
RULE 4: Executing SFENCE.VMA in U-mode raises an illegal-instruction exception.
RULE 5: Executing SFENCE.VMA in VS-mode when hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 6: Executing SFENCE.VMA in VS-mode when hstatus.VTVM=0 is permitted, and mstatus.TVM does not affect execution in VS-mode.
RULE 7: Executing SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 8: If satp.MODE is read-only zero, executing SFENCE.VMA may raise an illegal-instruction exception.
RULE 9: If the value held in rs1 is not a valid virtual address, executing SFENCE.VMA has no architectural effect and raises no exception.
RULE 10: For rs1=x0 and rs2=x0, SFENCE.VMA orders any previous stores already visible to the current hart before subsequent implicit reads and writes to any level of the page tables for all address spaces.
RULE 11: For rs1=x0 and rs2=x0, SFENCE.VMA invalidates all address-translation cache entries for all address spaces.
RULE 12: For rs1=x0 and rs2≠x0, SFENCE.VMA orders any previous stores already visible to the current hart before subsequent implicit reads and writes to any level of the page tables for the address space identified by rs2, excluding global mappings.
RULE 13: For rs1=x0 and rs2≠x0, SFENCE.VMA invalidates all address-translation cache entries matching the address space identified by rs2, except entries containing global mappings.
RULE 14: For rs1≠x0 and rs2=x0, SFENCE.VMA orders any previous stores already visible to the current hart before subsequent implicit reads and writes to leaf page-table entries corresponding to the virtual address in rs1, for all address spaces.
RULE 15: For rs1≠x0 and rs2=x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page-table entries corresponding to the virtual address in rs1, for all address spaces.
RULE 16: For rs1≠x0 and rs2≠x0, SFENCE.VMA orders any previous stores already visible to the current hart before subsequent implicit reads and writes to leaf page-table entries corresponding to the virtual address in rs1, for the address space identified by rs2, excluding global mappings.
RULE 17: For rs1≠x0 and rs2≠x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page-table entries corresponding to the virtual address in rs1 and match the address space identified by rs2, except entries containing global mappings.
RULE 18: When rs2≠x0, SFENCE.VMA ignores bits SXLEN-1:ASIDMAX of the value held in rs2.
RULE 19: When rs2≠x0 and ASIDLEN<ASIDMAX, SFENCE.VMA ignores bits ASIDMAX-1:ASIDLEN of the value held in rs2.
RULE 20: SFENCE.VMA orders only the local hart's implicit references to the memory-management data structures.
RULE 21: SFENCE.VMA does not order cache-block invalidate, clean, or flush operations.
RULE 22: After an SFENCE.VMA subsumes an address, an implicit read of the memory-management data structures may return any translation for that address that was valid at any time since the most recent subsuming SFENCE.VMA.
RULE 23: Executing SFENCE.VMA is permitted to order and invalidate a superset of the accesses and address-translation cache entries specified by its rs1 and rs2 operands, including by treating rs1 as x0 and/or rs2 as x0.
RULE 24: When V=0, the virtual-address argument of SFENCE.VMA is an HS-level virtual address and the ASID argument is an HS-level ASID.
RULE 25: When V=0, SFENCE.VMA orders stores only to HS-level address-translation structures with respect to subsequent HS-level address translations.
RULE 26: When V=1, the virtual-address argument of SFENCE.VMA is a guest virtual address within the current virtual machine and the ASID argument is a VS-level ASID within the current virtual machine.
RULE 27: When V=1, the current virtual machine for SFENCE.VMA is identified by hgatp.VMID.
RULE 28: When V=1, the effective ASID for SFENCE.VMA is the combination of hgatp.VMID and the VS-level ASID held in rs2.
RULE 29: When V=1, SFENCE.VMA orders stores only to VS-level address-translation structures with respect to subsequent VS-stage address translations for the same virtual machine, when hgatp.VMID equals its value at the time SFENCE.VMA executed.
RULE 30: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp, which is the HS-level satp when V=0 and vsatp when V=1.
RULE 31: After menvcfg.PBMTE is changed, executing SFENCE.VMA with rs1=x0 and rs2=x0 synchronizes the address-translation caches with the altered interpretation of page-table entries' PBMT fields.
RULE 32: After menvcfg.ADUE is changed, executing SFENCE.VMA with rs1=x0 and rs2=x0 synchronizes the address-translation caches with the altered interpretation of page-table entries' A/D bits.
RULE 33: After PMP CSRs are written in a manner that affects page tables, executing SFENCE.VMA with rs1=x0 and rs2=x0 synchronizes the PMP settings with the virtual-memory system and any PMP or address-translation caches.
