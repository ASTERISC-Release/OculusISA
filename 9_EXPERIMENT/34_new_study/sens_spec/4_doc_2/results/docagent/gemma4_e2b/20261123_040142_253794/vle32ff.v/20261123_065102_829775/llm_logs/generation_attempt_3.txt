## I. Core Address Translation and Protection

### 1. Supervisor Address Translation (`satp`)
*   **Function:** The `satp` CSR controls supervisor-mode address translation and protection. It holds the Physical Page Number (PPN) of the root page table, an Address Space Identifier (ASID), and the `MODE` field (e.g., `Bare`, `Sv32`, `Sv39`, `Sv48`, `Sv57`).
*   **ASID Management:** ASIDs are used to facilitate address-translation fences on a per-address-space basis. Swapping ASIDs and page table bases is intended to be atomic.
*   **Mode Definitions:**
    *   `MODE=Bare`: Supervisor virtual addresses equal supervisor physical addresses (no extra protection).
    *   `Sv32`: 32-bit paged virtual memory.
    *   `Sv39`, `Sv48`, `Sv57`: Multi-level paged virtual memory schemes for RV64, increasing the virtual address space progressively.
*   **Page Table Entries (PTEs):** PTEs contain R/W/X (Read/Write/Execute) bits, a Valid (V) bit, and a Global (G) bit.
*   **Address Translation Process (Sv32):** A detailed, multi-step process involving translating the virtual address through the page table hierarchy, checking permissions, and handling updates (A/D bits) atomically.

### 2. Memory Management Fences
*   **`SFENCE.VMA`:** Orders stores relative to subsequent implicit reads during VS-stage address translation.
*   **`HFENCE.VVMA` / `HFENCE.GVMA`:** Hypervisor instructions that provide fences complementary to `SFENCE.VMA`, operating on VS-level or G-stage memory management structures (`vsatp` or `hgatp`).
*   **Synchronization:** Synchronization between PMP settings and address translation structures (e.g., by executing `SFENCE.VMA` with specific register values) is crucial when memory protection or PTE attributes change.

## II. Virtualization Support (H Extension)

The Hypervisor extension transforms Supervisor mode into **HS-mode** (Hypervisor-extended Supervisor mode) or **VS-mode** (Virtual Supervisor mode), enabling guest OS hosting.

### 1. Modes and State
*   **Virtualization Mode (V):** Indicates if two-stage address translation is active ($V=1$) or inactive ($V=0$).
*   **Privilege Modes:** Defines the relationship between M, HS, U, VS, and VU modes.
*   **Hypervisor Status (`hstatus`):** Tracks exception behavior for VS-mode guests, including VSXLEN (VSXL for VS-mode width) and interrupt pending/enable bits.
*   **Virtual Supervisor State (`vsstatus`):** The VS-mode version of `sstatus`, managing VS-mode floating-point (FS) and vector (VS) state.

### 2. Guest Address Translation (`hgatp`)
*   **Function:** Controls G-stage address translation and protection for guest physical addresses. It holds a Guest Physical Root Page Table PPN, a Virtual Machine Identifier (VMID), and a `MODE` field (e.g., `Bare`, `Sv39x4`, `Sv48x4`, `Sv57x4`).

### 3. Hypervisor Instructions
*   **Virtual-Machine Load/Store Instructions (`HLV.*`, `HSV.*`):** These instructions perform explicit memory accesses with an effective privilege mode of VS or VU.
*   **Hypervisor Fences (`HFENCE.VVMA`, `HFENCE.GVMA`):** Used to synchronize VS-stage or G-stage address translation caches associated with specific VMs (`hgatp.VMID`).

### 4. Trap Handling
*   **Trap Cause Codes (mcause/scause):** The extension augments trap cause encoding to include codes for VS-level interrupts, guest-page faults, and virtual instruction exceptions.
*   **Trap Return (`MRET`/`SRET`):** These instructions handle returning from traps, setting privilege modes based on state registers (`mstatus`, `hstatus`, `vsstatus`).
*   **Trap Value Registers (`htval`, `mtval2`, `mtinst`):** Used to pass exception-specific information (guest physical addresses for faults, instruction transformation information) to the trap handler.

## III. Extensions and Advanced Features

### 1. Zicfiss (Shadow Stack)
*   **Purpose:** Provides backward-edge Control-Flow Integrity (CFI) using shadow stacks.
*   **State Management:** Uses `xSSE` (determined by privilege mode and `menvcfg.SSE`) to enable/disable the extension.
*   **Memory Access Restrictions:** Shadow stack instructions (`SSPUSH`, `SSPOPCHK`, `SSAMOSWAP.W/D`) are restricted to specific PTEs (`pte.xwr=010b`) and require memory to be idempotent.

### 2. Svinval (Fine-Grained Invalidation)
*   **Purpose:** Splits coarse-grained fences (`SFENCE.VMA`, `HFENCE.*`) into fine-grained invalidation/ordering operations (`SINVAL.VMA`, `SFENCE.W.INVAL`, `SFENCE.INVAL.IR`) for efficient pipelining.

### 3. Ssdbltrp (Double Trap)
*   **Purpose:** Enables critical error handling handlers in guest VMs during double traps (M-mode to VS-mode, or M-mode to S/HS-mode).

### 4. Svnapot (Contiguity)
*   **Purpose:** Allows PTEs to indicate contiguous virtual-to-physical translation ranges (NAPOTs) to reduce TLB pressure by allowing large entries to cover contiguous regions.

### 5. Sscofpmf (Count Overflow)
*   **Purpose:** Standardizes field usage in `mhpmevent` CSRs to reliably indicate counter overflow status and enable interrupts.

### 6. QoS Identifiers (`ssqosid`)
*   **Purpose:** Introduces `srmcfg` to configure Resource Control IDs (RCID) and Monitoring Counter IDs (MCID) for resource allocation and monitoring for Quality of Service (QoS).

### 7. Pointer Masking (PM)
*   **Mechanism:** Allows the CPU to ignore the upper bits of an effective address (PMLEN bits) during explicit memory accesses, often used for security features like HWASAN.
*   **Scope:** Applies to most explicit memory accesses (loads, stores, atomics, FPU ops, HLV/HSV instructions, etc.).
*   **Privilege Dependence:** The set of supported PMLEN values depends on the active privilege mode.
*   **Extensions:** `Ssnpm` (Supervisor), `Smnpm` (Machine), `Smmpm` (Machine), `Sspm` (Supervisor), and `Supm` (User) define the pointer masking support per privilege level.

## IV. Hardware/Software Interaction

*   **Hardware Updates (Svadu):** The `menvcfg.ADUE` and `henvcfg.ADUE` fields control hardware updating of PTE A/D bits for VS-stage translation.
*   **Performance Implications:** The specification discusses trade-offs between implementation complexity (e.g., software TLB refills vs. hardware support) and performance (e.g., large page sizes, TLB reach).
*   **Speculative Execution:** The interaction between speculative address translation and memory fencing (`SFENCE.VMA`) is carefully defined to ensure correctness, especially regarding caching of potentially stale PTEs.

**In essence, this specification defines a highly complex, multi-stage address translation architecture layered with robust virtualization capabilities, specific extensions for control-flow integrity and memory management, and mechanisms for fine-grained performance monitoring.**
