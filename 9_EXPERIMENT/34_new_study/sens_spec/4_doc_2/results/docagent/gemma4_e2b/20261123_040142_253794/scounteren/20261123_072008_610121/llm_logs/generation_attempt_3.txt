This document excerpt details extensive aspects of the RISC-V Privileged Architecture, focusing heavily on **Supervisor Mode (S-mode)**, **Hypervisor Extensions (H-extension)**, and advanced memory management features like **Pointer Masking** and **Control-Flow Integrity (CFI)**.

---

## I. Core Address Translation and Protection (satp/vsatp)

The foundation of memory management revolves around address translation registers:

### 1. satp Register (Supervisor Mode)
*   **Function:** Controls supervisor-mode address translation and protection. It holds the Physical Page Number (PPN) of the root page table, an Address Space Identifier (ASID), and a MODE field.
*   **Modes:**
    *   **Bare:** Supervisor virtual addresses equal supervisor physical addresses (no translation/protection beyond physical memory protection).
    *   **Sv32:** 32-bit paged virtual memory scheme (SXLEN=32).
    *   **Sv39, Sv48, Sv57:** Paged virtual memory schemes for SXLEN=64, increasing virtual address space (39, 48, 57 bits).
*   **ASID:** Allows address-translation fences to operate on a per-address-space basis.
*   **Atomic Operations:** ASID and page table base address are stored together to allow atomic swapping on context switches.
*   **Page Table Entries (PTEs):** PTEs include V (Valid), R/W/X (Permissions), G (Global mapping), A (Accessed), and D (Dirty) bits.
*   **Address Translation Process (Sv32):** Involves a two-level walk (VPN $\rightarrow$ PPN) and checks permissions (R, W, X), boundary alignment, and handling of A/D bits (with or without the `Svade` extension).

### 2. vsatp Register (Virtualization Mode)
*   **Function:** The VS-mode version of `satp`, controlling the first stage of two-stage address translation for guest virtual addresses.
*   **Two-Stage Translation (V=1):** Guest Virtual Address (VA) $\rightarrow$ Guest Physical Address (GPA) (via `vsatp`) $\rightarrow$ Supervisor Physical Address (via `hgatp`).
*   **Guest Physical Address Translation (G-stage):** Controlled by `hgatp`. This stage implements the page-based translation scheme (Sv32x4, Sv39x4, Sv48x4, Sv57x4), widening the address based on the mode.
*   **Synchronization:** `HFENCE.VVMA` and `HFENCE.GVMA` are used to order stores to memory-management data structures based on the active `satp`/`vsatp` context (defined by `hgatp.VMID` and the corresponding ASID).

## II. Memory Type and Fine-Grained Control Extensions

These extensions modify how memory is managed and how memory accesses are ordered.

### 1. Svpbmt Extension (Memory Types)
*   **Function:** Bits 62-61 in PTEs define memory types (PMA, NC, IO).
*   **Behavior:** Overrides standard Physical Memory Attributes (PMA) for cacheability and ordering (e.g., mapping memory to I/O or Non-cacheable attributes).
*   **Ordering:** Dictates memory ordering rules (RVWMO vs. I/O ordering) for accesses to these pages, requiring specific fence instructions (like `fence iorw`) for coherence when mixing attributes.

### 2. Svnapot Extension (Contiguity)
*   **Function:** Enables **Non-Aligned Page-of-Type (NAPOT)** PTEs in Sv39/Sv48/Sv57 to represent contiguous virtual-to-physical translation ranges.
*   **Benefit:** Allows large regions to be cached as a single TLB entry, reducing TLB pressure.
*   **Update Handling:** Requires synchronization (e.g., `SFENCE.VMA`) when modifying PTEs to ensure consistency across aliases.

### 3. Zicfiss Extension (Control-Flow Integrity - CFI)
*   **LPE State:** Determines if forward-edge CFI using landing pads (`xLPE`) is enabled based on the privilege mode.
*   **SSE State (`xSSE`):** Determines if backward-edge CFI using shadow stacks is enabled.
*   **Shadow Stack (SS):** A new page type (`pte.xwr=010b`) protects stack memory. Accesses to SS pages must use specific instructions (`SSAMOSWAP.W/D`, `SSPUSH`, etc.) and require memory to be **idempotent**.
*   **Memory Accesses:** Pointer masking (see Section V) applies to explicit memory accesses (loads, stores, atomics, etc.).

## III. Hypervisor Extension (H-extension)

The H-extension virtualizes the supervisor architecture to host guest operating systems (HS-mode and VS-mode).

*   **Privilege Modes (V):**
    *   **V=0 (M-mode, HS-mode, U-mode):** Standard execution environment.
    *   **V=1 (VS-mode, VU-mode):** Two-stage address translation is active.
*   **CSRs:** A rich set of CSRs are added (`hstatus`, `hgatp`, `hcounteren`, `hvip`, etc.) to manage virtualization state, guest address translation, and interrupts.
*   **Trap Handling:** Sophisticated delegation mechanisms (`hedeleg`, `hideleg`) allow traps to be routed from M $\rightarrow$ HS $\rightarrow$ VS.
*   **Virtual Machine Instructions (HLV/HSV):** These instructions perform memory access with an effective privilege mode (VS or VU), applying two-stage address translation.
*   **Memory Fences:** `HFENCE.VVMA` (VS-stage structures) and `HFENCE.GVMA` (G-stage structures) provide memory ordering guarantees specific to the active stage and VMID.
*   **Guest-Page Faults:** Trap values (`htval`, `mtval2`) are used to pass faulting guest physical addresses back to the hypervisor.

## IV. Pointer Masking (PM)

*   **Purpose:** Allows the CPU to ignore the upper bits of the effective address (`NVBITS`) during memory access, primarily for security features like HWASAN.
*   **Mechanism:** The "Ignore" transformation modifies the address based on the address type (virtual vs. physical) and the configured `PMLEN`.
*   **Scope:** Applies to **all explicit memory accesses** (loads/stores, atomics, floating-point operations, hypervisor instructions, cache management operations). It **does not** apply to implicit accesses (page table walks, instruction fetches).
*   **Control:** Pointer masking is controlled by privilege mode-specific configuration bits (e.g., `UXL`, `SXL`, `MXL`).
*   **Security Note:** Ensures that even if an address is masked, the behavior is consistent across privilege modes, simplifying software design.

---

## Summary of Key Architectural Decisions and Implications

1.  **Hierarchy of Address Translation:** The system supports nested translation (VS-stage $\rightarrow$ G-stage), managed by `vsatp` and `hgatp`, with the H-extension providing the infrastructure for this nesting.
2.  **Performance vs. Safety:** The specification balances performance (e.g., allowing speculative execution, using large pages, NAPOT extensions) with robust safety mechanisms (e.g., strict ordering requirements via `SFENCE.VMA` and detailed exception handling).
3.  **Granular Control:** Extensions like Svnapot and Svinval aim to reduce TLB pressure and synchronization overheads associated with massive address spaces and dynamic mapping changes.
4.  **Security:** CFI (`Zicfiss`) and Pointer Masking provide hardware-assisted defenses against common software attacks (ROP, buffer overflows, use-after-free).
5.  **Context Switching:** The design heavily emphasizes atomic updates for context-dependent data (like ASID/page table swaps) and relies on explicit fence instructions to enforce memory ordering between translation structure writes and subsequent memory accesses.
