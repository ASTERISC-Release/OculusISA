REGISTER: mseccfg
RULE 1: The system can trap attempted access to the seed and feed a less privileged client virtual entropy source data instead of invoking an SP 800-90B or PTG.2 physical entropy source.
RULE 2: Implementations may implement mseccfg such that the [s,u]seed field is a read-only constant value 0.
RULE 3: Software may discover if access to the seed CSR can be enabled in U and S mode by writing a 1 to [s,u]seed and reading back the result.
RULE 4: The direct `mseccfg.[s,u]seed` option allows one to draw a security boundary around a component in relation to Sensitive Security Parameter (SSP) flows, even if that component is not in M mode.
RULE 5: The mechanism enabled by `mseccfg` can enforce the entire key lifecycle from birth in the entropy source to death zeroization without the key being passed across the boundary to external code.
RULE 6: The privilege level for the `mseccfg` register is MRW.
RULE 7: mseccfg is a 64-bit read/write register that controls security features.
RULE 8: mseccfg exists if any extension that adds a field to mseccfg is implemented; otherwise, it is reserved.
RULE 9: The Zkr extension adds the SSEED and USEED fields to the mseccfg CSR to control access to the seed CSR from modes less privileged than M.
RULE 10: When USEED is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 11: When USEED is 1, read-write access to the seed CSR from U-mode is allowed, and all other types of accesses raise an illegal-instruction exception.
RULE 12: If Zkr or U-mode is not implemented, the USEED field in mseccfg is read-only zero.
RULE 13: When SSEED is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 14: When SSEED is 1, read-write access to the seed CSR from S-/HS-mode is allowed, and all other types of accesses raise an illegal-instruction exception.
RULE 15: If Zkr or S-mode is not implemented, the SSEED field in mseccfg is read-only zero.
RULE 16: When the H extension is implemented, access to the seed CSR from an HS-qualified instruction leads to a virtual-instruction exception in VS and VU modes, and all other types of accesses raise an illegal-instruction exception.
RULE 17: The Smepmp extension adds the RLB, MMWP, and the MML fields in mseccfg.
RULE 18: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 19: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any rule or entry, then mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 20: The mseccfg.MMWP is a WARL field that changes the default PMP policy for Machine mode when accessing memory regions that don't have a matching PMP rule.
RULE 21: When mseccfg.MMWP is set, it changes the default PMP policy for M-mode when accessing memory regions that don't have a matching PMP rule, to denied instead of ignored.
RULE 22: The mseccfg.MMWP is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 23: The mseccfg.MML is a WARL field that changes the interpretation of the pmpcfg.L bit defined in Section 3.7.1.2.
RULE 24: The mseccfg.MML is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 25: When mseccfg.MML is set, the meaning of pmpcfg.L changes, marking a rule as M-mode-only when set and S/U-mode-only when unset.
RULE 26: When mseccfg.MML is set, an M-mode-only rule is enforced on Machine mode and denied in Supervisor or User mode, and this rule remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 27: When mseccfg.MML is set, an S/U-mode-only rule is enforced on Supervisor and User modes and denied on Machine mode.
RULE 28: When mseccfg.MML is set, a Shared-Region rule is enforced on all modes, with restrictions depending on the pmpcfg.L and pmpcfg.X bits.
RULE 29: A Shared-Region rule where pmpcfg.L is not set can be used for sharing data between M-mode and S/U-mode, where it is not executable and M-mode has read/write access to that region, and S/U-mode has read access if pmpcfg.X is not set, or read/write access if pmpcfg.X is set.
RULE 30: A Shared-Region rule where pmpcfg.L is set can be used for sharing code between M-mode and S/U-mode, where it is not writable, both M-mode and S/U-mode have execute access on the region, and M-mode also has read access if pmpcfg.X is set, and this rule remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 31: The encoding pmpcfg.LRWX=1111 can be used for sharing data between M-mode and S/U-mode, where both modes only have read-only access to the region, and this rule remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 32: Adding a rule with executable privileges that either is M-mode-only or a locked Shared-Region is not possible, and such pmpcfg writes are ignored, leaving pmpcfg unchanged, unless mseccfg.RLB is set.
RULE 33: Executing code with Machine mode privileges is only possible from memory regions with a matching M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 34: Executing code from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 35: If mseccfg.MML is not set, the combination of pmpcfg.RW=01 remains reserved for future standard use.
RULE 36: The Zicfilp extension adds the MLPE field in mseccfg.
RULE 37: When the MLPE field is 1 in mseccfg, the Zicfilp extension is enabled in M-mode.
RULE 38: When the MLPE field is 0 in mseccfg, the Zicfilp extension is not enabled in M-mode.

REGISTER: satp
RULE 1: The satp register is located at address 0x180.
RULE 2: The satp register has the privilege level of Supervisor, Supervisor, Write (SRW).
RULE 3: The satp register is a Virtual Supervisor register with Privilege HRW.
RULE 4: All S-mode instruction fetches implicitly read the satp CSR.
RULE 5: Unless otherwise specified, the value returned by an implicit read of the satp CSR is the same value that would have been returned by an explicit read of the satp CSR using a CSR-access instruction in a sufficient privilege mode.
RULE 6: If S-mode is not supported, SUM must be read-only 0.
RULE 7: If satp .MODE is read-only 0, SUM must be read-only 0.
RULE 8: If the TVM bit is set to 1, attempts to read or write the satp CSR while executing in S-mode will raise an illegal-instruction exception.
RULE 9: If the TVM bit is set to 1, attempts to execute an SFENCE.VMA instruction while executing in S-mode will raise an illegal-instruction exception.
RULE 10: If the TVM bit is set to 1, attempts to execute a SINVAL.VMA instruction while executing in S-mode will raise an illegal-instruction exception.
RULE 11: If the TVM bit is set to 0, attempts to read or write the satp CSR or execute an SFENCE.VMA or SINVAL.VMA instruction are permitted in S-mode.
RULE 12: Trapping satp accesses and the SFENCE.VMA and SINVAL.VMA instructions provides the hooks necessary to lazily populate shadow page tables.
RULE 13: When the PBMTE bit is set to 1, Svpbmt is available for S-mode and G-stage address translation for page tables pointed to by satp or hgatp.
RULE 14: When the PBMTE bit is set to 0, the implementation behaves as though Svpbmt were not implemented for page tables pointed to by satp or hgatp.
RULE 15: If Svpbmt is not implemented, the PBMTE bit must be read-only zero.
RULE 16: For implementations with the hypervisor extension, the henvcfg .PBMTE register must be read-only zero if the menvcfg .PBMTE register is zero.
RULE 17: Executing an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields when menvcfg .PBMTE is changed.
RULE 18: When the ADUE bit is 0, the implementation behaves as though the Svade extension were implemented for S-mode and G-stage address translation for page tables pointed to by satp or hgatp.
RULE 19: When the ADUE bit is 1, hardware updating of PTE A/D bits is enabled during S-mode address translation, and the implementation behaves as though the Svade extension were not implemented for S-mode address translation for page tables pointed to by satp or hgatp.
RULE 20: The Svade extension requires page-fault exceptions to be raised when PTE A/D bits need to be set, and Svade is implemented when the ADUE bit is 0.
RULE 21: If Svadu is not implemented, the ADUE bit must be read-only zero.
RULE 22: For implementations with the hypervisor extension, the henvcfg .ADUE register must be read-only zero if the menvcfg .ADUE register is zero.
RULE 23: Executing an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' A/D bits when menvcfg .ADUE is changed.
RULE 24: SUM is read-only 0 if satp .MODE is read-only 0.
RULE 25: The satp CSR is an SXLEN-bit read/write register that controls supervisor-mode address translation and protection.
RULE 26: The satp register holds the physical page number (PPN) of the root page table, defined as its supervisor physical address divided by 4 KiB.
RULE 27: The satp register holds an address space identifier (ASID) which facilitates address-translation fences on a per-addressspace basis.
RULE 28: The satp register holds a MODE field that selects the current address-translation scheme.
RULE 29: The satp .PPN field might not be capable of holding all physical page numbers, and platform standards may place constraints on the values satp .PPN may assume, such as requiring that all physical page numbers corresponding to main memory be representable.
RULE 30: The satp CSR is considered active when the effective privilege mode is S-mode or U-mode.
RULE 31: Executions of the address-translation algorithm may only begin using a given value of satp when satp is active.
RULE 32: The number of implemented ASID bits, termed ASIDLEN, may be determined by writing one to every bit position in the ASID field and reading back the value in satp to see which bit positions in the ASID field hold a one.
RULE 33: If ASIDLEN is greater than zero, ASID[ASIDLEN-1:0] is writable.
RULE 34: The maximal value of ASIDLEN, termed ASIDMAX, is 9 for Sv32 or 16 for Sv39, Sv48, and Sv57.
RULE 35: The MODE field selects the current address-translation scheme.
RULE 36: When MODE is set to Bare, supervisor virtual addresses are equal to supervisor physical addresses, and there is no additional memory protection beyond the physical memory protection scheme described in Section 3.7.
RULE 37: Attempting to select MODE=Bare with a nonzero pattern in the remaining fields has an UNSPECIFIED effect on the value that the remaining fields assume and an UNSPECIFIED effect on address translation and protection behavior.
RULE 38: When SXLEN=64, three paged virtual-memory schemes are defined by the MODE field: Sv39, Sv48, and Sv57, respectively.
RULE 39: If satp is written with an unsupported MODE, the entire write has no effect, and no fields in satp are modified.
RULE 40: When SXLEN=64, all satp encodings corresponding to MODE=Bare are reserved for future standard use.
RULE 41: The remaining fields in satp had no effect when MODE=Bare, according to Version 1.11 of this standard.
RULE 42: Translations that began while satp was active are not required to complete or terminate when satp is no longer active, unless an SFENCE.VMA instruction matching the address and ASID is executed.
RULE 43: The SFENCE.VMA instruction must be used to ensure that updates to the address-translation data structures are observed by subsequent implicit reads to those structures by a hart.
RULE 44: Writing satp does not imply any ordering constraints between page-table updates and subsequent address translations, nor does it imply any invalidation of address-translation caches.
RULE 45: If the new address space's page tables have been modified, or if an ASID is reused, it may be necessary to execute an SFENCE.VMA instruction after, or in some cases before, writing satp.
RULE 46: Not imposing upon implementations to flush address-translation caches upon satp writes reduces the cost of context switches, provided a sufficiently large ASID space.
RULE 47: Implementations must only perform implicit reads of the translation data structures pointed to by the current contents of the satp register or a subsequent valid (V=1) translation data structure entry.
RULE 48: Implementations must only raise exceptions for implicit accesses that are generated as a result of instruction execution, not those that are performed speculatively.
RULE 49: Changes to the sstatus fields SUM and MXR take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 50: Changing satp .MODE from Bare to other modes and vice versa takes effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 51: Changes to satp .ASID take effect immediately.
RULE 52: For implementations that make satp .MODE read-only zero (always Bare), attempts to execute an SFENCE.VMA instruction might raise an illegal-instruction exception.
RULE 53: The property that any translation since the last subsuming SFENCE.VMA might be used applies even if the virtual-address width for that translation differs from the width currently specified by satp.MODE.
RULE 54: For a given virtual address and ASID, any translation since the last subsuming SFENCE.VMA might be used, even if that translation used a virtual address of a different width.
RULE 55: For a given virtual address, any global translation since the last subsuming SFENCE.VMA might be used, regardless of both ASID and virtual-address width.
RULE 56: In the Sv32 mode, supervisor and user virtual addresses are translated into supervisor physical addresses by traversing a radix-tree page table.
RULE 57: Sv32 mode is supported when SXLEN is equal to 32.
RULE 58: When Sv32 virtual memory mode is selected in the MODE field of the satp register, supervisor virtual addresses are translated into supervisor physical addresses via a two-level page table.
RULE 59: The physical page number of the root page table is stored in the satp register.
RULE 60: When the value of satp .MODE is Sv32, a 34-bit physical address is produced directly, and therefore no zero extension is needed.
RULE 61: The satp register must be active, requiring the effective privilege mode to be S-mode or U-mode.
RULE 62: As long as the satp register is active, implementations may execute the address-translation algorithm speculatively for any virtual address.
RULE 63: When the address-translation algorithm is executed speculatively because the satp register is active, this action pre-populates the address-translation cache.
RULE 64: The range of addresses that an implementation's page-table walker will touch is fully under supervisor control because the algorithm may only touch page tables reachable from the root page table indicated in satp.
RULE 65: The physical page number of the root page table is stored in the satp register's PPN field.
RULE 66: Implicit reads of NAPOT page table entries may create address-translation cache entries.
RULE 67: These address-translation cache entries map an address of $+ j \times \text{PTESIZE}$ to a copy of the page table entry.
RULE 68: Within that copied page table entry, the field $\text{pte}.\text{ppn}[i][\text{pte}.\text{napot\_bits}-1:0]$ must be replaced by the value $\text{vpn}[i][\text{pte}.\text{napot\_bits}-1:0]$.
RULE 69: This replacement mechanism applies for any or all indices $j$ where $j \gg \text{napot\_bits} = \text{vpn}[i] \gg \text{napot\_bits}$.
RULE 70: This entire process applies to all address spaces identified in satp as loaded by step 1.
RULE 71: The satp register holds the physical page number (PPN) of the guest-physical root page table, a virtual machine identifier (VMID) that facilitates address-translation fences on a per-virtual-machine basis, and the MODE field which selects the address-translation scheme for guest physical addresses.
RULE 72: A write to the satp register with an unsupported MODE value is not ignored, unlike for standard satp.
RULE 73: When indicated, the fields of the satp register are WARL in the normal way.
RULE 74: When V=1, instructions that normally read or modify satp actually access vsatp instead.
RULE 75: When V=1, a write to satp with an unsupported MODE value is ignored and no write to vsatp is effected.
RULE 76: When V=0, a write to vsatp with an unsupported MODE value is either ignored as it is for satp, or the fields of vsatp are treated as WARL in the normal way.
RULE 77: When V=0, vsatp does not directly affect the behavior of the machine, unless a virtual-machine load/store (HLV, HLVX, or HSV) or the MPRV feature in the mstatus register is used to execute a load or store as though V=1.
RULE 78: Instruction SFENCE.VMA applies only to the memory-management data structures controlled by the current satp.
RULE 79: The current satp is the HS-level satp when the value V is 0.
RULE 80: The current satp is the vsatp when the value V is 1.
RULE 81: HFENCE.VVMA applies to the VS-level memory-management data structures controlled by CSR vsatp.
RULE 82: The instruction traps enabled by TVM=1 permit machine level to co-opt both satp and hgatp and substitute shadow page tables that merge the OS's chosen page translations with M-level's lower-stage translations without the OS being aware.
RULE 83: Setting TVM=1 does not cause traps for accesses to vsatp or instructions HFENCE.VVMA or HINVAL.VVMA.
RULE 84: Setting TVM=1 does not cause traps for any actions taken in VS-mode because M-level software is not expected to need to involve itself in VS-stage address translation regarding satp.
RULE 85: Zeroing the corresponding `vsatp` register can effectively disable either the VS-stage or the G-stage translation.
RULE 86: hgatp substitutes for the usual satp.
RULE 87: hgatp is used for the conversion of an Sv32x4, Sv39x4, Sv48x4, or Sv57x4 guest physical address.
RULE 88: For the translation to begin, the effective privilege mode must be VS-mode or VU-mode.
RULE 89: When checking the U bit, the current privilege mode is always taken to be U-mode.
RULE 90: Guest-page-fault exceptions are raised instead of regular page-fault exceptions.
RULE 91: No mechanism is provided to atomically change `vsatp` and `hgatp` together.
RULE 92: World-switch code should zero `vsatp` to prevent speculative execution causing one guest's VS-stage translations to be cached under another guest's VMID.
RULE 93: World-switch code should swap `hgatp` after zeroing `vsatp`.
RULE 94: World-switch code should write the new `vsatp` value finally.
RULE 95: If `henvcfg .PBMTE/ADUE` need to be world-switched, they should be switched after zeroing `vsatp` but before writing the new `vsatp` value.

RULE 97: If `vsatp.MODE` is not equal to Bare, the pointer masking issue does not apply to the satp register.
RULE 98: If `satp.MODE` (or `vsatp.MODE` when V=1) is set to Bare and the effective privilege mode is less than M, shadow stack instructions must raise a store/AMO access-fault exception.

RULE 100: If the G-stage page table does not have read-write permission for the accessed memory when G-stage page tables are active, a store/AMO guest-page-fault exception must be raised for shadow stack instructions.

REGISTER: scounteren
RULE 1: The scounteren register is a Supervisor-level CSR (Control and Status Register).
RULE 2: When the CY, TM, IR, or HPMn bit in the scounteren register is clear, attempting to read the cycle, time, instret, or hpmcountern register while executing in U-mode will cause an illegal-instruction exception.
RULE 3: When one of the CY, TM, IR, or HPMn bits in the scounteren register is set, access to the corresponding register is permitted.
RULE 4: Any of the bits in scounteren may be read-only zero, which indicates that reads to the corresponding counter will cause an exception when executing in U-mode, and these bits are effectively WARL fields.
RULE 5: U-mode may only access a counter if the corresponding bits in both scounteren and mcounteren are set.
RULE 6: The setting of a bit in mcounteren does not affect whether the corresponding bit in scounteren is writable.
RULE 7: scounteren continues to have its usual function and accessibility even when V=1.
RULE 8: The usual function and accessibility of scounteren are not retained when VS-mode and VU-mode substitute for HS-mode and U-mode when V=1.
RULE 9: Hypervisor software is expected to manually swap the contents of scounteren as needed.
RULE 10: In VU-mode, a counter is not readable unless the applicable bits are set in both hcounteren and scounteren.
