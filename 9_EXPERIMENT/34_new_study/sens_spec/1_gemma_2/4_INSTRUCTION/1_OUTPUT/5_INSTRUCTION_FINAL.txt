INSTRUCTION: CSRRWI
FORMAT: csrrwi rd, csr, zimm5
RULE 1: If the uimm[4:0] field is zero, the CSRRWI instruction shall not write to the CSR.
RULE 2: If the uimm[4:0] field is zero, the CSRRWI instruction shall not cause any of the side effects that might otherwise occur on a CSR write.
RULE 3: If the uimm[4:0] field is zero, the CSRRWI instruction shall not raise illegal instruction exceptions on accesses to read-only CSRs.
RULE 4: If the destination register rd equals x0, the CSRRWI instruction shall not read the CSR.
RULE 5: If the destination register rd equals x0, the CSRRWI instruction shall not cause any of the side effects that might occur on a CSR read.
RULE 6: If the destination register rd is not x0 and the uimm[4:0] field is zero, the CSRRWI instruction shall read the CSR but shall not write to the CSR.
RULE 7: If the destination register rd is not x0 and the uimm[4:0] field is non-zero, the CSRRWI instruction shall read the CSR and cause any read side effects.
RULE 8: If the destination register rd is not x0 and the uimm[4:0] field is non-zero, the CSRRWI instruction shall write to the CSR and cause any write side effects.
RULE 9: If an instruction $i$ is a CSR instruction and $i$ is CSRRWI, then a register $r$ other than $x0$ is not considered a source register if the destination register $rd$ of instruction $i$ is set to $x0$.
RULE 10: For an instruction $i$ that is a CSR instruction, a register $r$ other than $x0$ is a source register if the opcode of $i$ sets the $csr$ field to $r$, unless the instruction $i$ is CSRRW or CSRRWI and the destination register $rd$ is set to $x0$.

INSTRUCTION: FCVT.W.D
FORMAT: fcvt.w.d rd, fs1, rm
RULE 1: FCVT.W.D converts a double-precision floating-point number held in floating-point register `rs1` to a signed 32-bit integer, which is stored in integer register `rd`.
RULE 2: Variants of the conversion instructions, including FCVT.WU.D, FCVT.LU.D, FCVT.D.WU, and FCVT.D.LU, convert to or from unsigned integer values.
RULE 3: For RV64, FCVT.W[U].D performs a sign-extension operation on the resulting 32-bit integer.
RULE 4: FCVT.W.D must always round towards zero.
RULE 5: FCVT.W.D must convert positive infinity, negative infinity, and NaN values to zero.
RULE 6: FCVT.W.D must take bits 31:0 from the rounded, unbounded two's complement result, sign-extend them to XLEN bits, and write the result to the integer register rd.
RULE 7: FCVT.W.D must raise floating-point exception flags identical to those generated by FCVT.W.D when using the same input operand.
RULE 8: FCVT.W.D must be encoded with the rs2 field set to 8 and the rm field set to 1, designating RTZ.
RULE 9: FCVT.W.D must require the RTZ rounding mode to be explicitly specified in the assembly syntax.

INSTRUCTION: SFENCE.VMA
FORMAT: sfence.vma rs1, rs2
RULE 1: If any supervisor-level memory management data structures remain in use across a change to SBE, M-mode software must execute an SFENCE.VMA instruction using rs1 set to x0 and rs2 set to x0.
RULE 2: When the TVM bit is set to 1, attempting to execute an SFENCE.VMA instruction while executing in S-mode must raise an illegal-instruction exception.
RULE 3: When M-mode software modifies the PMP settings, execution of the SFENCE.VMA instruction is required to synchronize the PMP settings with the virtual memory system and any PMP or address-translation caches.
RULE 4: If page-based virtual memory is not implemented, no SFENCE.VMA instruction is needed because memory accesses check the PMP settings synchronously.
RULE 5: Translations that began while `satp` was active are not required to complete or terminate when `satp` is no longer active unless an `SFENCE.VMA` instruction matching the address and ASID is executed.
RULE 6: It is always legal to over-fence the instruction, such as by fencing only based on a subset of the bits in rs1 and/or rs2, or by treating all SFENCE.VMA instructions as having rs1=x0 and/or rs2=x0.
RULE 7: If the value held in rs1 is not a valid virtual address, the SFENCE.VMA instruction has no effect, and no exception is raised.
RULE 8: When rs2 is not x0, the bits SXLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use and should be zeroed and ignored by current implementations.
RULE 9: If rs1 is not x0 and rs2 equals x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for all address spaces, and invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 10: If software modifies a non-leaf PTE, it should execute SFENCE.VMA with rs1=x0, setting rs2 to x0 if any PTE along the traversal path had its G bit set, or setting rs2 to the ASID for which the translation is being modified otherwise.
RULE 11: When using `rs1= x0`, the SFENCE.VMA instruction must either terminate all previously-launched speculative executions of the address-translation algorithm for the specified ASID or simply wait for them to complete.
RULE 12: When using `rs1= x0`, if the SFENCE.VMA waits for speculative executions to complete, any address-translation cache entries created are invalidated by the SFENCE.VMA as appropriate.
RULE 13: An attempt to execute SFENCE.VMA in S-mode or HS-mode when mstatus .TVM=1 raises an illegal-instruction exception.
RULE 14: An attempt to execute SFENCE.VMA in VS-mode or VUmode, or to execute SINVAL.VMA in VU-mode, raises a virtual-instruction exception.
RULE 15: An attempt to execute SFENCE.VMA in VS-mode also raises a virtual-instruction exception when hstatus .VTVM=1.
RULE 16: When the VS-mode is active and the VTVM field is set to 1, an attempt to execute SFENCE.VMA raises a virtual-instruction exception.
RULE 17: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp, which is the HS-level satp when V is zero or vsatp when V is one.
RULE 18: If operand rs2 is not x0, the SFENCE.VMA instruction specifies a single guest address-space identifier (ASID).
RULE 19: Neither mstatus .TVM nor hstatus .VTVM causes SFENCE.VMA to trap.
RULE 20: When the virtualization mode V is 0, the virtual-address argument to SFENCE.VMA is an HS-level virtual address, and the ASID argument is an HS-level ASID.
RULE 21: When the virtualization mode V is 0, the SFENCE.VMA instruction orders stores only to HS-level address-translation structures with subsequent HS-level address translations.
RULE 22: When the virtualization mode V is 1, the SFENCE.VMA instruction orders stores only to the VS-level address-translation structures with subsequent VS-stage address translations for the same virtual machine, provided that hgatp.VMID is the same as when the SFENCE.VMA executed.
RULE 23: If an SFENCE.VMA instruction is executed without synchronizing the HS-level address translation state with G-stage and VS-stage data structures, then an exception occurs.
RULE 24: For HS-level address translation, synchronization is accomplished by executing an SFENCE.VMA instruction in M-mode with rs1 set to x0 and rs2 set to x0 after the PMP CSRs have been written.
RULE 25: In VS-mode, an attempt to execute the SFENCE.VMA instruction results in raising a virtual-instruction exception if the attempt occurs when `hstatus .VTVM` is 1.

INSTRUCTION: VLE32FF.V
FORMAT: vle32ff.v vd, (rs1), vm
RULE 1: The VLE32FF.V instruction executes as a regular load, except that it will only take a trap caused by a synchronous exception on element 0.
RULE 2: If element 0 raises an exception during the VLE32FF.V operation, the vector length is not modified, and the trap is taken.
RULE 3: If an element greater than 0 raises an exception during the VLE32FF.V operation, the corresponding trap is not taken, and the vector length is reduced to the index of the element that would have raised an exception.
RULE 4: Load instructions for VLE32FF.V may overwrite active destination vector register group elements past the element index at which the trap is reported.
RULE 5: Fault-only-first instructions for VLE32FF.V may update active destination elements past the element that causes trimming of the vector length, but they must not update elements past the original vector length.
RULE 6: Spurious updates to destination elements resulting from the VLE32FF.V instruction do not have to correspond to the values in memory at the addressed memory locations.
RULE 7: If the VLE32FF.V instruction has a starting index of zero and the vector length is greater than zero, then at least one element must be processed.
RULE 8: When the VLE32FF.V instruction takes a trap due to an interrupt, implementations should not reduce the vector length and should instead set a starting address value.
RULE 9: When the VLE32FF.V instruction would trigger a debug data-watchpoint trap on an element after the first, implementations should not reduce the vector length but instead should trigger the debug trap to prevent the event from being lost.
