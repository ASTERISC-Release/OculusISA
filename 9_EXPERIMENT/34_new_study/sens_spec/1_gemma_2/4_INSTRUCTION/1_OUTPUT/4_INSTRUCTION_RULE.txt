INSTRUCTION: CSRRWI
RULE 1: If the uimm[4:0] field is zero, the CSRRWI instruction shall not write to the CSR.
RULE 2: If the uimm[4:0] field is zero, the CSRRWI instruction shall not cause any of the side effects that might otherwise occur on a CSR write.
RULE 3: If the uimm[4:0] field is zero, the CSRRWI instruction shall not raise illegal instruction exceptions on accesses to read-only CSRs.
RULE 4: If the destination register rd equals x0, the CSRRWI instruction shall not read the CSR.
RULE 5: If the destination register rd equals x0, the CSRRWI instruction shall not cause any of the side effects that might occur on a CSR read.
RULE 6: If the destination register rd is not x0 and the uimm[4:0] field is zero, the CSRRWI instruction shall read the CSR but shall not write to the CSR.
RULE 7: If the destination register rd is not x0 and the uimm[4:0] field is non-zero, the CSRRWI instruction shall read the CSR and cause any read side effects.
RULE 8: If the destination register rd is not x0 and the uimm[4:0] field is non-zero, the CSRRWI instruction shall write to the CSR and cause any write side effects.
RULE 9: If an instruction $i$ is a CSR instruction and $i$ is CSRRWI, then a register $r$ other than $x0$ is not considered a source register if the destination register $rd$ of instruction $i$ is set to $x0$.
RULE 10: For an instruction $i$ that is a CSR instruction, a register $r$ other than $x0$ is a source register if the opcode of $i$ sets the $csr$ field to $r$, unless the instruction $i$ is CSRRW or CSRRWI and the destination register $rd$ is set to $x0$.

INSTRUCTION: FCVT.W.D
RULE 1: FCVT.W.D converts a double-precision floating-point number held in floating-point register `rs1` to a signed 32-bit integer, which is stored in integer register `rd`.
RULE 2: Variants of the conversion instructions, including FCVT.WU.D, FCVT.LU.D, FCVT.D.WU, and FCVT.D.LU, convert to or from unsigned integer values.
RULE 3: For RV64, FCVT.W[U].D performs a sign-extension operation on the resulting 32-bit integer.
RULE 4: FCVT.W.D must always round towards zero.
RULE 5: FCVT.W.D must convert positive infinity, negative infinity, and NaN values to zero.
RULE 6: FCVT.W.D must take bits 31:0 from the rounded, unbounded two's complement result, sign-extend them to XLEN bits, and write the result to the integer register rd.
RULE 7: FCVT.W.D must raise floating-point exception flags identical to those generated by FCVT.W.D when using the same input operand.
RULE 8: FCVT.W.D is only available if the D extension is implemented.
RULE 9: FCVT.W.D must be encoded with the rs2 field set to 8 and the rm field set to 1, designating RTZ.
RULE 10: FCVT.W.D must require the RTZ rounding mode to be explicitly specified in the assembly syntax.
RULE 11: Other values for the rm field in FCVT.W.D encoding are reserved.

INSTRUCTION: SFENCE.VMA
RULE 1: SFENCE.VMA does not order invalidate, clean, and flush operations relative to instructions that order stores, such as FENCE.I.
RULE 2: If any supervisor-level memory management data structures remain in use across a change to SBE, M-mode software must execute an SFENCE.VMA instruction using rs1 set to x0 and rs2 set to x0.
RULE 3: When the TVM bit is set to 1, attempting to execute an SFENCE.VMA instruction while executing in S-mode must raise an illegal-instruction exception.
RULE 4: When the TVM bit is set to 0, SFENCE.VMA operations are permitted while executing in S-mode.
RULE 5: Executing an SFENCE.VMA instruction with rs1 equal to x0 and rs2 equal to x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields after changing menvcfg.PBMTE.
RULE 6: Executing an SFENCE.VMA instruction with rs1 equal to x0 and rs2 equal to x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' A/D bits after changing menvcfg.ADUE.
RULE 7: When M-mode software modifies the PMP settings, execution of the SFENCE.VMA instruction is required to synchronize the PMP settings with the virtual memory system and any PMP or address-translation caches.
RULE 8: The SFENCE.VMA instruction must be executed after the PMP CSRs have been written.
RULE 9: The SFENCE.VMA instruction must be executed using the register value x0 for both the rs1 and rs2 operands.
RULE 10: If page-based virtual memory is not implemented, no SFENCE.VMA instruction is needed because memory accesses check the PMP settings synchronously.
RULE 11: Translations that began while `satp` was active are not required to complete or terminate when `satp` is no longer active unless an `SFENCE.VMA` instruction matching the address and ASID is executed.
RULE 12: The `SFENCE.VMA` instruction must be used to ensure that updates to the address translation data structures are observed by subsequent implicit reads to those structures by a hart.
RULE 13: If the new address space's page tables have been modified or an ASID is reused, it may be necessary to execute an `SFENCE.VMA` instruction after or before writing `satp`.
RULE 14: SFENCE.VMA execution causes implicit reads and writes to memory-management data structures, which are ordinarily not ordered with respect to explicit loads and stores.
RULE 15: Executing SFENCE.VMA guarantees that any previous stores already visible to the current RISC-V hart are ordered before certain implicit references by subsequent instructions to memory-management data structures.
RULE 16: SFENCE.VMA orders only the implicit references made to the memory-management data structures local to the hart.
RULE 17: SFENCE.VMA is used to invalidate entries in the address-translation cache associated with a hart.
RULE 18: SFENCE.VMA is used to flush local hardware caches related to address translation, providing cleaner semantics than a TLB flush.
RULE 19: SFENCE.VMA is used by higher privilege levels to synchronize page table writes and the address translation hardware.
RULE 20: It is always legal to over-fence the instruction, such as by fencing only based on a subset of the bits in rs1 and/or rs2, or by treating all SFENCE.VMA instructions as having rs1=x0 and/or rs2=x0.
RULE 21: If the value held in rs1 is not a valid virtual address, the SFENCE.VMA instruction has no effect, and no exception is raised.
RULE 22: Implementations must only perform implicit reads of translation data structures pointed to by the current satp register or a subsequent valid translation data structure entry.
RULE 23: Implementations must only raise exceptions for implicit accesses generated by instruction execution, not for accesses performed speculatively.
RULE 24: An implicit read of the memory-management data structures may return any translation for an address that was valid at any time since the most recent SFENCE.VMA that subsumes that address.
RULE 25: The ordering implied by SFENCE.VMA does not place implicit reads and writes to the memory-management data structures into the global memory order in a way that interacts cleanly with standard RVWMO ordering rules.
RULE 26: SFENCE.VMA does not necessarily place prior explicit accesses before subsequent explicit accesses in the global memory order, even though it orders prior explicit accesses before subsequent implicit accesses.
RULE 27: Implicit loads resulting from SFENCE.VMA need not obey normal program order semantics with respect to prior loads or stores to the same address.
RULE 28: An implementation may use any translation for an address that was valid at any time since the most recent SFENCE.VMA that subsumes that address.
RULE 29: It is generally unsafe to update a PTE using stores of a width less than the width of the PTE because the implementation is legal to read the PTE at any time.
RULE 30: This specification permits the caching of PTEs whose Valid (V) bit is clear, requiring operating systems to cope with this possibility.
RULE 31: If a hart employs an address-translation cache, that cache must appear to be private to that hart.
RULE 32: The meaning of an Address Space Identifier (ASID) is local to a hart, and software may choose to use the same ASID to refer to different address spaces on different harts.
RULE 33: When rs2 is not x0, the bits SXLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use and should be zeroed and ignored by current implementations.
RULE 34: If ASIDLEN is less than ASIDMAX, the implementation shall ignore bits ASIDMAX1:ASIDLEN of the value held in rs2.
RULE 35: Changes to the sstatus fields SUM and MXR take effect immediately without requiring an SFENCE.VMA instruction.
RULE 36: Changing satp.MODE from Bare to other modes and vice versa takes effect immediately without requiring an SFENCE.VMA instruction.
RULE 37: Changes to satp.ASID take effect immediately without requiring an SFENCE.VMA instruction.
RULE 38: For implementations that make satp.MODE read-only zero (always Bare), attempts to execute SFENCE.VMA might raise an illegal-instruction exception.
RULE 39: No SFENCE.VMA is required after enabling or disabling pointer masking because pointer masking applies only to the effective address and does not affect memory-management data structures.
RULE 40: If rs1 equals x0 and rs2 equals x0, SFENCE.VMA orders all reads and writes made to any level of the page tables for all address spaces and invalidates all address-translation cache entries for all address spaces.
RULE 41: If rs1 equals x0 and rs2 is not x0, SFENCE.VMA orders all reads and writes to page tables only for the address space identified by rs2, but not for global mappings, and invalidates all address-translation cache entries matching rs2, except for entries containing global mappings.
RULE 42: If rs1 is not x0 and rs2 equals x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for all address spaces, and invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 43: If rs1 is not x0 and rs2 is not x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for the address space identified by rs2, but not for global mappings, and invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 and matching the address space identified by rs2, except for entries containing global mappings.
RULE 44: When software recycles an ASID, it should first change satp to point to the new page table using the recycled ASID and then execute SFENCE.VMA with rs1=x0 and rs2 set to the recycled ASID.
RULE 45: If an implementation does not provide ASIDs or software chooses to always use ASID 0, then after every satp write, software should execute SFENCE.VMA with rs1=x0, setting rs2 to a register other than x0 that contains zero to prevent flushing global translations.
RULE 46: If software modifies a non-leaf PTE, it should execute SFENCE.VMA with rs1=x0, setting rs2 to x0 if any PTE along the traversal path had its G bit set, or setting rs2 to the ASID for which the translation is being modified otherwise.
RULE 47: If software modifies a leaf PTE, it should execute SFENCE.VMA with rs1 set to a virtual address within the page, setting rs2 to x0 if any PTE along the traversal path had its G bit set, or setting rs2 to the ASID for which the translation is being modified otherwise.
RULE 48: For permission changes involving increasing permissions on a leaf PTE or changing an invalid PTE to a valid leaf, software may choose to execute SFENCE.VMA lazily, using either the new or old permissions before the fence executes.
RULE 49: When the `SFENCE.VMA` instruction is executed with the second source register (`rs2`) not equal to `x0`, global mappings are not required to be flushed from local address-translation caches.
RULE 50: SFENCE.VMA is required to ensure that implicit reads observe writes to the same memory locations by flushing the relevant cached translations.
RULE 51: SFENCE.VMA must be executed when a page is upgraded to a superpage without first clearing the original non-leaf PTE's valid bit, such as when using `rs1= x0`.
RULE 52: If an SFENCE.VMA is not executed between a write to the memory-management tables and a subsequent implicit read of the same address, the outcome regarding whether the old non-leaf PTE or the new leaf PTE is used is unpredictable.
RULE 53: When using `rs1= x0`, the SFENCE.VMA instruction must either terminate all previously-launched speculative executions of the address-translation algorithm for the specified ASID or simply wait for them to complete.
RULE 54: When using `rs1= x0`, if the SFENCE.VMA waits for speculative executions to complete, any address-translation cache entries created are invalidated by the SFENCE.VMA as appropriate.
RULE 55: When using `rs1≠ x0`, the SFENCE.VMA instruction generally must either ensure that previously-launched speculative executions of the address-translation algorithm are prevented from creating new address-translation cache entries mapping leaf PTEs, or wait for them to complete.
RULE 56: If an update needs to be made, the operating system should generally first mark all Page Table Entries invalid before issuing SFENCE.VMA instructions covering all 4 KiB regions within the range.
RULE 57: The SFENCE.VMA instruction(s) covering the range may be issued via a single instruction where rs1 equals x0.
RULE 58: The SFENCE.VMA instruction(s) covering the range may be issued via multiple instructions where rs1 is not equal to x0.
RULE 59: If any inconsistencies exist during the update process following the SFENCE.VMA instruction(s), one of the translations will be chosen, but this choice is unpredictable.
RULE 60: The SFENCE.VMA instruction invalidates any address-translation cache entries that an SFENCE.VMA instruction with the same values of rs1 and rs2 would invalidate.
RULE 61: SFENCE.VMA functions as a synchronization instruction, which is different from the behavior of SINVAL.VMA.
RULE 62: High-performance implementations will defer any pipeline stalls or memory ordering enforcement until an SFENCE.W.INVAL, SFENCE.INVAL.IR, SFENCE.VMA, HFENCE.GVMA, or HFENCE.VVMA instruction is executed.
RULE 63: Simpler implementations may implement SINVAL.VMA identically to SFENCE.VMA, while implementing SFENCE.W.INVAL and SFENCE.INVAL.IR instructions as no-ops.
RULE 64: An attempt to execute SFENCE.VMA in S-mode or HS-mode when mstatus .TVM=1 raises an illegal-instruction exception.
RULE 65: An attempt to execute SFENCE.VMA in VS-mode or VUmode, or to execute SINVAL.VMA in VU-mode, raises a virtual-instruction exception.
RULE 66: An attempt to execute SFENCE.VMA in VS-mode also raises a virtual-instruction exception when hstatus .VTVM=1.
RULE 67: The sequence SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR, when executed in order by a single hart, has the same effect as a hypothetical SFENCE.VMA instruction where the values of rs1 and rs2 are the same as those used in the SINVAL.VMA.
RULE 68: Reads and writes prior to the SFENCE.W.INVAL are considered to be those prior to the hypothetical SFENCE.VMA.
RULE 69: Reads and writes following the SFENCE.INVAL.IR are considered to be those subsequent to the hypothetical SFENCE.VMA.
RULE 70: SFENCE.VMA is a memory-management instruction intended to synchronize the hart's address-translation caches specifically when a memory-resident Page Table Entry (PTE) is changed from Invalid to Valid.
RULE 71: The Svvptc extension relieves the operating system from executing SFENCE.VMA along with SINVAL.VMA, which serve as the mechanism for this synchronization.
RULE 72: Synchronization of the hart's address-translation caches with other forms of updates to a memory-resident PTE, including when a PTE is changed from Valid to Invalid, requires the use of suitable memory-management instructions.
RULE 73: The Svvptc extension guarantees that a change to a PTE from Invalid to Valid is made visible within a bounded time, thereby making the execution of SFENCE.VMA redundant.
RULE 74: When the VS-mode is active and the VTVM field is set to 1, an attempt to execute SFENCE.VMA raises a virtual-instruction exception.
RULE 75: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp, which is the HS-level satp when V is zero or vsatp when V is one.
RULE 76: Executing an HFENCE.VVMA guarantees that any previous stores already visible to the current hart are ordered before all implicit reads done for VS-stage address translation for instructions that are subsequent to the HFENCE.VVMA, provided that hgatp .VMID has the same setting as it did when HFENCE.VVMA executed.
RULE 77: Implicit reads need not be ordered after an SFENCE.VMA when hgatp .VMID is different than at the time HFENCE.VVMA executed.
RULE 78: An SFENCE.VMA instruction applies only to a single virtual machine, identified by the setting of hgatp .VMID when SFENCE.VMA executes.
RULE 79: If operand rs1 is not x0, the SFENCE.VMA instruction specifies a single guest virtual address.
RULE 80: If operand rs2 is not x0, the SFENCE.VMA instruction specifies a single guest address-space identifier (ASID).
RULE 81: When operand rs2 is not x0, bits XLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use.
RULE 82: Until their use is defined by a standard extension, bits XLEN-1:ASIDMAX of the value held in rs2 should be zeroed by software and ignored by current implementations of SFENCE.VMA.
RULE 83: If ASIDLEN is less than ASIDMAX, the implementation shall ignore bits ASIDMAX1:ASIDLEN of the value held in rs2 when executing SFENCE.VMA.
RULE 84: Simpler implementations of HFENCE.VVMA may ignore the guest virtual address in rs1, the guest ASID value in rs2, and hgatp .VMID during SFENCE.VMA execution.
RULE 85: Simpler implementations of HFENCE.VVMA may always perform a global fence for the VS-level memory management of all virtual machines or a global fence for all memory-management data structures during SFENCE.VMA execution.
RULE 86: Neither mstatus .TVM nor hstatus .VTVM causes SFENCE.VMA to trap.
RULE 87: When the virtualization mode V is 0, the virtual-address argument to SFENCE.VMA is an HS-level virtual address, and the ASID argument is an HS-level ASID.
RULE 88: When the virtualization mode V is 0, the SFENCE.VMA instruction orders stores only to HS-level address-translation structures with subsequent HS-level address translations.
RULE 89: When the virtualization mode V is 1, the virtual-address argument to SFENCE.VMA is a guest virtual address within the current virtual machine, and the ASID argument is a VS-level ASID within the current virtual machine.
RULE 90: When the virtualization mode V is 1, the current virtual machine is identified by the VMID field of CSR hgatp, and the effective ASID is the combination of this VMID and the VS-level ASID.
RULE 91: When the virtualization mode V is 1, the SFENCE.VMA instruction orders stores only to the VS-level address-translation structures with subsequent VS-stage address translations for the same virtual machine, provided that hgatp.VMID is the same as when the SFENCE.VMA executed.
RULE 92: For HS-level address translation, synchronization with G-stage and VS-stage data structures is required when executing an SFENCE.VMA instruction.
RULE 93: For HS-level address translation, synchronization is accomplished by executing an SFENCE.VMA instruction in M-mode with rs1 set to x0 and rs2 set to x0 after the PMP CSRs have been written.
RULE 94: In VS-mode, an attempt to execute the SFENCE.VMA instruction results in raising a virtual-instruction exception if the attempt occurs when `hstatus .VTVM` is 1.

INSTRUCTION: VLE32FF.V
RULE 1: The VLE32FF.V instruction executes as a regular load, except that it will only take a trap caused by a synchronous exception on element 0.
RULE 2: If element 0 raises an exception during the VLE32FF.V operation, the vector length is not modified, and the trap is taken.
RULE 3: If an element greater than 0 raises an exception during the VLE32FF.V operation, the corresponding trap is not taken, and the vector length is reduced to the index of the element that would have raised an exception.
RULE 4: Load instructions for VLE32FF.V may overwrite active destination vector register group elements past the element index at which the trap is reported.
RULE 5: Fault-only-first instructions for VLE32FF.V may update active destination elements past the element that causes trimming of the vector length, but they must not update elements past the original vector length.
RULE 6: Spurious updates to destination elements resulting from the VLE32FF.V instruction do not have to correspond to the values in memory at the addressed memory locations.
RULE 7: Non-idempotent memory locations can only be accessed by the VLE32FF.V instruction when it is known the corresponding element load operation will not be restarted due to a trap or vector-length trimming.
RULE 8: Even when an exception is not raised during the VLE32FF.V operation, implementations are permitted to process fewer than the vector length and reduce the vector length accordingly.
RULE 9: If the VLE32FF.V instruction has a starting index of zero and the vector length is greater than zero, then at least one element must be processed.
RULE 10: When the VLE32FF.V instruction takes a trap due to an interrupt, implementations should not reduce the vector length and should instead set a starting address value.
RULE 11: When the VLE32FF.V instruction would trigger a debug data-watchpoint trap on an element after the first, implementations should not reduce the vector length but instead should trigger the debug trap to prevent the event from being lost.
