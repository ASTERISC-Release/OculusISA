INSTRUCTION: CSRRWI
RULE 1: CSRRWI updates the single CSR selected by the CSRRWI's CSR specifier using an XLEN-bit value obtained by zero-extending the 5-bit unsigned immediate uimm[4:0] instead of using a value from an integer register.
RULE 2: CSRRWI with rd = x0 shall not cause any side effects that might occur on a read of the single CSR selected by the CSRRWI's CSR specifier.
RULE 3: CSRRWI with rd = x0 writes the single CSR selected by the CSRRWI's CSR specifier.
RULE 4: CSRRWI with rd not equal to x0 reads the single CSR selected by the CSRRWI's CSR specifier.
RULE 5: CSRRWI with rd not equal to x0 writes the single CSR selected by the CSRRWI's CSR specifier.
RULE 6: CSRRWI with rd not equal to x0 causes any side effects that occur as a consequence of reading the single CSR selected by the CSRRWI's CSR specifier.
RULE 7: CSRRWI causes any side effects that occur as a consequence of writing the single CSR selected by the CSRRWI's CSR specifier.
RULE 8: CSRRWI triggers side effects for all fields within the CSR selected by the CSRRWI's CSR specifier that have side effects when CSRRWI writes that CSR.

INSTRUCTION: FCVT.W.D
RULE 1: FCVT.W.D converts a double-precision floating-point number in floating-point register rs1 to a signed 32-bit integer in integer register rd.
RULE 2: On RV64, FCVT.W.D sign-extends the 32-bit integer result into the destination register.
RULE 3: FCVT.W.D rounds its result according to the rm field.
RULE 4: FCVT.W.D does not always round towards zero.
RULE 5: FCVT.W.D does not take bits 31:0 from the rounded, unbounded two's complement result, sign-extend them to XLEN bits, and write them to integer register rd.
RULE 6: FCVT.W.D does not convert positive infinity to zero.
RULE 7: FCVT.W.D does not convert negative infinity to zero.
RULE 8: FCVT.W.D does not convert NaN to zero.
RULE 9: FCVT.W.D raises floating-point exception flags based on its input operand.

INSTRUCTION: SFENCE.VMA
RULE 1: SFENCE.VMA is an instruction that orders stores.
RULE 2: SFENCE.VMA does not order cache-block management invalidate operations.
RULE 3: SFENCE.VMA does not order cache-block management clean operations.
RULE 4: SFENCE.VMA does not order cache-block management flush operations.
RULE 5: When TVM=1, an attempt to execute SFENCE.VMA while executing in S-mode raises an illegal-instruction exception.
RULE 6: When TVM=0, execution of SFENCE.VMA in S-mode is permitted.
RULE 7: When S-mode is not supported, TVM is read-only 0, so TVM does not cause SFENCE.VMA in S-mode to raise an illegal-instruction exception.
RULE 8: After changing menvcfg.PBMTE, executing an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields.
RULE 9: After changing menvcfg.ADUE, executing an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' A/D bits.
RULE 10: If page-based virtual memory is not implemented, memory accesses check the PMP settings synchronously and no SFENCE.VMA instruction is needed.
RULE 11: Unless an SFENCE.VMA instruction matching the address and ASID is executed, translations that began while satp was active are not required to complete or terminate when satp is no longer active.
RULE 12: The SFENCE.VMA instruction must be used to ensure that updates to the address-translation data structures are observed by subsequent implicit reads to those structures by a hart.
RULE 13: If the new address space's page tables have been modified, it may be necessary to execute an SFENCE.VMA instruction after, or in some cases before, writing satp.
RULE 14: If an ASID is reused, it may be necessary to execute an SFENCE.VMA instruction after, or in some cases before, writing satp.
RULE 15: Executing an SFENCE.VMA instruction guarantees that any previous stores already visible to the current RISC-V hart are ordered before certain implicit references by subsequent instructions in that hart to the memory-management data structures.
RULE 16: SFENCE.VMA orders only the local hart's implicit references to the memory-management data structures.
RULE 17: When SFENCE.VMA has rs1=x0 and rs2=x0, SFENCE.VMA orders all reads and writes made to any level of the page tables for all address spaces.
RULE 18: When SFENCE.VMA has rs1=x0 and rs2=x0, SFENCE.VMA invalidates all address-translation cache entries for all address spaces.
RULE 19: When SFENCE.VMA has rs1=x0 and rs2!=x0, SFENCE.VMA orders all reads and writes made to any level of the page tables only for the address space identified by integer register rs2, and accesses to global mappings are not ordered.
RULE 20: When SFENCE.VMA has rs1=x0 and rs2!=x0, SFENCE.VMA invalidates all address-translation cache entries matching the address space identified by integer register rs2 except for entries containing global mappings.
RULE 21: When SFENCE.VMA has rs1!=x0 and rs2=x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 22: When SFENCE.VMA has rs1!=x0 and rs2=x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 23: When SFENCE.VMA has rs1!=x0 and rs2!=x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for the address space identified by integer register rs2, and accesses to global mappings are not ordered.
RULE 24: When SFENCE.VMA has rs1!=x0 and rs2!=x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 and that match the address space identified by integer register rs2, except for entries containing global mappings.
RULE 25: If the value held in rs1 is not a valid virtual address, SFENCE.VMA raises no exception.
RULE 26: When SFENCE.VMA has rs2!=x0, bits SXLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use.
RULE 27: When SFENCE.VMA has rs2!=x0 and the reserved bits SXLEN-1:ASIDMAX of rs2 are not yet defined by a standard extension, current implementations ignore those bits.
RULE 28: When SFENCE.VMA has rs2!=x0 and ASIDLEN < ASIDMAX, the implementation shall ignore bits ASIDMAX-1:ASIDLEN of the value held in rs2.
RULE 29: An implicit read of the memory-management data structures may return any translation for an address that was valid at any time since the most recent SFENCE.VMA that subsumes that address.
RULE 30: An implementation may use any translation for an address that was valid at any time since the most recent SFENCE.VMA that subsumes that address.
RULE 31: If a leaf PTE is modified and the corresponding virtual address is accessed without a subsuming SFENCE.VMA in between, either the new translation or any older translation that was valid since the last subsuming SFENCE.VMA was executed will be used.
RULE 32: Changes to the sstatus fields SUM and MXR take effect immediately without requiring an SFENCE.VMA instruction.
RULE 33: Changing satp.MODE from Bare to other modes and vice versa takes effect immediately without requiring an SFENCE.VMA instruction.
RULE 34: Changes to satp.ASID take effect immediately without requiring an SFENCE.VMA instruction.
RULE 35: No SFENCE.VMA is required after enabling or disabling pointer masking because pointer masking applies to the effective address only and does not affect any memory-management data structures.
RULE 36: To ensure that implicit reads observe writes to the same memory locations, an SFENCE.VMA instruction must be executed after the writes to flush the relevant cached translations.
RULE 37: If any inconsistencies do exist, then the effect is the same as when SFENCE.VMA is used incorrectly: one of the translations will be chosen, but the choice is unpredictable.
RULE 38: An SFENCE.VMA instruction with given values of rs1 and rs2 has a set of address-translation cache entries that it would invalidate, and a SINVAL.VMA instruction with the same values of rs1 and rs2 invalidates any entries in that set.
RULE 39: When executed in order (but not necessarily consecutively) by a single hart, the sequence SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR has the same effect as a hypothetical SFENCE.VMA instruction whose rs1 and rs2 values are the same as those used in the SINVAL.VMA.
RULE 40: When executed in order (but not necessarily consecutively) by a single hart, the sequence SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR has the same effect as a hypothetical SFENCE.VMA instruction whose rs1 and rs2 values are the same as those used in the SINVAL.VMA and for which reads and writes prior to the SFENCE.W.INVAL are considered prior to the SFENCE.VMA.
RULE 41: When executed in order (but not necessarily consecutively) by a single hart, the sequence SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR has the same effect as a hypothetical SFENCE.VMA instruction whose rs1 and rs2 values are the same as those used in the SINVAL.VMA and for which reads and writes following the SFENCE.INVAL.IR are considered subsequent to the SFENCE.VMA.
RULE 42: An SFENCE.VMA instruction requires the same permissions as a SINVAL.VMA instruction.
RULE 43: An attempt to execute SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 44: An attempt to execute SFENCE.VMA in S-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 45: An attempt to execute SFENCE.VMA in HS-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 46: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 47: When hstatus.VTVM=1, an attempt to execute SFENCE.VMA in VS-mode raises a virtual-instruction exception.
RULE 48: Svvptc guarantees that a change to a PTE from Invalid to Valid is made visible within a bounded time, thereby making execution of SFENCE.VMA redundant for that change.
RULE 49: When VTVM=1, an attempt in VS-mode to execute SFENCE.VMA raises a virtual-instruction exception rather than an illegal-instruction exception.
RULE 50: VTVM affects SFENCE.VMA execution only when SFENCE.VMA is executed in VS-mode.
RULE 51: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp.
RULE 52: When V=0, SFENCE.VMA applies only to the memory-management data structures controlled by the HS-level satp.
RULE 53: When V=1, SFENCE.VMA applies only to the memory-management data structures controlled by vsatp.
RULE 54: When V=0, the virtual-address argument to SFENCE.VMA is an HS-level virtual address.
RULE 55: When V=0, the ASID argument to SFENCE.VMA is an HS-level ASID.
RULE 56: When V=0, SFENCE.VMA orders stores only to HS-level address-translation structures with subsequent HS-level address translations.
RULE 57: When V=1, the virtual-address argument to SFENCE.VMA is a guest virtual address within the current virtual machine.
RULE 58: When V=1, the ASID argument to SFENCE.VMA is a VS-level ASID within the current virtual machine.
RULE 59: When V=1, SFENCE.VMA orders stores only to VS-level address-translation structures with subsequent VS-stage address translations for the same virtual machine only when hgatp.VMID is the same as when the SFENCE.VMA executed.
RULE 60: For HS-level address translation, synchronization of PMP settings with the virtual memory system is accomplished by executing in M-mode an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 after the PMP CSRs are written.
RULE 61: An attempt in VS-mode to execute SFENCE.VMA when V=1 and hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 62: When an attempt in VS-mode to execute SFENCE.VMA when V=1 and hstatus.VTVM=1 raises a virtual-instruction exception, mtval or stval is written the same as for an illegal-instruction trap.
RULE 63: A change to xSSE takes effect immediately without an SFENCE.VMA instruction being required to make the change effective.
RULE 64: No SFENCE.VMA architectural cause-and-effect behavior is explicitly specified in the provided description.

INSTRUCTION: VLE32FF.V
RULE 1: If element 0 raises a synchronous exception during VLE32FF.V execution, VLE32FF.V takes the trap.
RULE 2: If element 0 raises a synchronous exception during VLE32FF.V execution, VLE32FF.V leaves vl unmodified.
RULE 3: If an element after element 0 raises a synchronous exception during VLE32FF.V execution, VLE32FF.V does not take the corresponding trap.
RULE 4: If an element after element 0 raises a synchronous exception during VLE32FF.V execution, VLE32FF.V reduces vl to the index of the element that would have raised the exception.
RULE 5: During VLE32FF.V execution, VLE32FF.V does not update active destination elements past the original vector length.
RULE 6: For VLE32FF.V, if vstart equals 0 and vl is greater than 0, then at least one element must be processed.
RULE 7: When VLE32FF.V takes a trap due to an interrupt, implementations should not reduce vl.
RULE 8: When VLE32FF.V would trigger a debug data-watchpoint trap on an element after the first, implementations should not reduce vl.
RULE 9: When VLE32FF.V would trigger a debug data-watchpoint trap on an element after the first, implementations should trigger the debug trap.
