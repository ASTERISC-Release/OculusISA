INSTRUCTION: CSRRWI
FORMAT: -
RULE 1: CSRRWI performs its CSR read when rd is not x0 and its unconditional write to the same single CSR as one atomic operation.
RULE 2: CSRRWI forms its XLEN-bit CSR write value by zero-extending the 5-bit unsigned immediate uimm[4:0].
RULE 3: When rd is not x0, CSRRWI reads the old value of the selected CSR, zero-extends that value to XLEN bits, and writes the result to rd.
RULE 4: CSRRWI writes the XLEN-bit zero-extended value of uimm[4:0] to the selected CSR.
RULE 5: If CSRRWI specifies rd=x0, then it writes the zero-extended uimm to the selected CSR without reading the CSR or causing any CSR-read side effects.
RULE 6: If CSRRWI is executed with rd=x0, the selected CSR is not read and no CSR-read side effect occurs; CSR write side effects are unaffected.
RULE 7: When rd is x0, CSRRWI still writes the XLEN-bit zero-extended value of uimm[4:0] to the selected CSR.
RULE 8: When uimm[4:0] is zero, CSRRWI still writes zero to the selected CSR regardless of whether rd is x0.
RULE 9: Executing CSRRWI on a CSR triggers the write side effect of every field in that CSR that defines one.
RULE 10: If CSRRWI reads a CSR that may be modified as a side effect of instruction execution, CSRRWI reads the CSR value that existed before execution of the instruction began.
RULE 11: If CSRRWI writes a CSR that may otherwise be updated as a side effect of instruction execution, the explicit CSRRWI write replaces the update that would have resulted from that side effect.
RULE 12: If a CSRRWI instruction has csr=r with r≠x0 and rd≠x0, then the instruction reads register r as a source register.
RULE 13: If CSRRWI names CSR r other than x0 and rd=x0, the instruction does not read r or cause CSR-read side effects, so its architectural result is independent of r’s prior value.
RULE 14: For CSRRWI, if a non-x0 CSR r aliases any source register of the instruction, treat r as a source register and verify that the instruction observes the shared aliased CSR state.
RULE 15: After a CSRRWI executes successfully with rd set to r other than x0, register r contains the CSR value from before the CSRRWI update.
RULE 16: If a CSRRWI instruction specifies register r other than x0 as its destination, then after successful execution r contains the CSR value from before the instruction updated that CSR.

INSTRUCTION: FCVT.W.D
FORMAT: -
RULE 1: FCVT.W.D converts the double-precision floating-point value in floating-point register rs1 to a signed 32-bit integer and writes the result to integer register rd.
RULE 2: On RV64, FCVT.W.D sign-extends the 32-bit integer result before writing it to integer register rd.
RULE 3: FCVT.W.D uses exactly the same valid input range as FCVT.W.S: an input outside that range sets fflags.NV, while an input within that range does not set fflags.NV because of range.
RULE 4: FCVT.W.D produces the same architectural behavior for invalid inputs as FCVT.W.S.
RULE 5: FCVT.W.D rounds the conversion according to the rounding mode specified by the rm field.
RULE 6: For the same input operand, FCVT.W.D raises the same floating-point exception flags as FCVTMOD.W.D.

INSTRUCTION: SFENCE.VMA
FORMAT: -
RULE 1: When TVM=1, attempting to execute SFENCE.VMA in S-mode raises an illegal-instruction exception.
RULE 2: When TVM=0, executing SFENCE.VMA in S-mode is permitted.
RULE 3: If rs1 holds an invalid virtual address, SFENCE.VMA has no effect and raises no exception.
RULE 4: If SFENCE.VMA is executed in a privilege or control state where SINVAL.VMA execution is not permitted, SFENCE.VMA raises the same exception that SINVAL.VMA would raise in that state.
RULE 5: Given identical initial architectural state and operands, SFENCE.VMA raises an exception if and only if SINVAL.VMA would raise an exception, and the exception cause is the same.
RULE 6: An attempt to execute SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 7: An attempt to execute SFENCE.VMA in S-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 8: An attempt to execute SFENCE.VMA in HS-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 9: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 10: An attempt to execute SFENCE.VMA in VS-mode when hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 11: The hstatus.VTVM field affects execution of SFENCE.VMA only in VS-mode.
RULE 12: When hstatus.VTVM=1, an attempt to execute SFENCE.VMA in VS-mode raises a virtual-instruction exception instead of an illegal-instruction exception.
RULE 13: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 14: An attempt to execute SFENCE.VMA in VS-mode when hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 15: When determining whether SFENCE.VMA execution in VS-mode raises an exception, mstatus.TSR is ignored.
RULE 16: When determining whether SFENCE.VMA execution in VS-mode raises an exception, mstatus.TVM is ignored.
RULE 17: When SFENCE.VMA causes a virtual-instruction trap that writes mtval, mtval is written in the same manner as for an illegal-instruction trap.
RULE 18: When SFENCE.VMA causes a virtual-instruction trap that writes stval, stval is written in the same manner as for an illegal-instruction trap.

INSTRUCTION: VLE32FF.V
FORMAT: -
RULE 1: VLE32FF.V performs a unit-stride vector load in which each processed memory element is 32 bits wide.
RULE 2: VLE32FF.V behaves as a regular vector load except that a synchronous exception causes a trap only when the exception occurs on element 0.
RULE 3: If element 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V takes the corresponding trap and leaves vl unmodified.
RULE 4: If an element with an index greater than 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V does not take the corresponding trap and reduces vl to the index of that element.
RULE 5: If no exception is raised during VLE32FF.V and execution begins with vstart = 0 and vl > 0, VLE32FF.V MUST process at least one element.
