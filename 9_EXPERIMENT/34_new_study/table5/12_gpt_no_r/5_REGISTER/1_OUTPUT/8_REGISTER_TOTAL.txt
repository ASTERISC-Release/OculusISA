REGISTER: mseccfg
NUMBER: 0x747
MODE: M-mode
WIDTH: 64
FIELDS: 33..32=PMM, 10..10=MLPE, 9..9=SSEED, 8..8=USEED, 2..2=RLB, 1..1=MMWP, 0..0=MML
EXTENSIONS: Smepmp, Smmpm, Zicfilp, Zkr
RULE 1: If U-mode accesses the seed CSR when mseccfg.USEED=0, or S-mode or HS-mode accesses it when mseccfg.SSEED=0, the access raises an illegal-instruction exception; setting the corresponding field to 1 permits the access.
RULE 2: If the SSEED or USEED field of mseccfg is a read-only constant 0, access to the seed CSR cannot be enabled for the corresponding lower-privilege mode.
RULE 3: Software can determine whether mseccfg permits seed CSR access to be enabled in U mode by writing 1 to USEED and reading back the value.
RULE 4: Software can determine whether mseccfg permits seed CSR access to be enabled in S mode by writing 1 to SSEED and reading back the value.
RULE 5: If writing 1 to a relevant SSEED or USEED field of mseccfg reads back as 1, software can infer that seed CSR access can be enabled for the corresponding mode; if it reads back as 0, it cannot be enabled.
RULE 6: The direct mseccfg.[s,u]seed option allows a security boundary to be established around a component with respect to Sensitive Security Parameter (SSP) flows.
RULE 7: A component protected using the direct mseccfg.[s,u]seed option does not need to operate in M mode.
RULE 8: The direct mseccfg.[s,u]seed option is useful when implementing trusted enclaves.
RULE 9: The direct mseccfg.[s,u]seed option can allow a module to enforce the entire lifecycle of a key within its security boundary.
RULE 10: With the direct mseccfg.[s,u]seed option, the protected key lifecycle can begin at key birth in the entropy source and end at key death through zeroization.
RULE 11: With the direct mseccfg.[s,u]seed option, a module can avoid passing a key across its security boundary to external code.
RULE 12: Direct entropy-source access enabled through mseccfg.[s,u]seed must be evaluated for depletion attacks because active polling can deny entropy to another simultaneous consumer.
RULE 13: In a virtualized system using mseccfg.[s,u]seed for direct entropy access, depletion can delay the initialization of another virtual machine that requires entropy.
RULE 14: Direct entropy-source access through mseccfg.[s,u]seed must be evaluated for covert channels because one consumer can alter whether another consumer observes WAIT instead of ES16.
RULE 15: Interactions resulting from mseccfg.[s,u]seed direct access can potentially establish low-bandwidth communication channels across security boundaries.
RULE 16: Direct entropy-source access through mseccfg.[s,u]seed must account for hardware fingerprinting because an entropy source and its noise-source circuits may possess a uniquely identifiable hardware signature.
RULE 17: When mseccfg.[s,u]seed is used in anonymized virtualized environments or enclaves, a DRBG can mask statistical features that could otherwise reveal an entropy-source hardware signature.
RULE 18: When mseccfg.[s,u]seed permits direct access to a physical entropy source shared among multiple virtual machines, the output should undergo conditioning and DRBG processing.
RULE 19: Conditioning and DRBG processing are recommended with mseccfg.[s,u]seed when the guest operating system receiving entropy is untrusted.
RULE 20: Implementations of mseccfg.[s,u]seed should avoid unnecessary status bits, custom bits, or other mechanisms that create information flows or disable or affect entropy-source output.
RULE 21: All information flows and interaction mechanisms associated with mseccfg.[s,u]seed must be evaluated from an adversarial perspective, and their number should be minimized.
RULE 22: The entropy-polling interface exposed through mseccfg.[s,u]seed should not be assumed to operate in constant time.
RULE 23: Timing behavior associated with mseccfg.[s,u]seed polling must be analyzed as a possible timing oracle, such as by modeling seed generation as a rejection sampler.
RULE 24: A timing oracle associated with mseccfg.[s,u]seed may reveal the noise-source type and entropy-source usage.
RULE 25: A timing oracle associated with mseccfg.[s,u]seed must not reveal the random output entropy bits themselves; if it does, additional countermeasures are required.
RULE 26: A CSR instruction using address 0x747 accesses mseccfg; with sufficient privilege, reads and writes at 0x747 observe mseccfg according to its defined field semantics.
RULE 27: An M-mode CSR read of mseccfg returns its current architectural value, an M-mode CSR write updates its writable fields, and any access to mseccfg from a lower privilege mode raises an illegal-instruction exception.
RULE 28: After writing a 64-bit value to mseccfg, a subsequent read returns the written value, and the corresponding security-feature controls take effect.
RULE 29: If no implemented extension adds a field to mseccfg, any CSR instruction that accesses mseccfg raises an illegal-instruction exception; otherwise, mseccfg is implemented with the fields defined by the implemented extensions.
RULE 30: If S-mode accesses the seed CSR when mseccfg.SSEED=0, or U-mode accesses it when mseccfg.USEED=0, the access raises an illegal-instruction exception; setting the corresponding field to 1 permits access subject to the seed CSR’s normal semantics.
RULE 31: When mseccfg.USEED is 0, any U-mode access to the seed CSR raises an illegal-instruction exception.
RULE 32: When mseccfg.USEED is 1, a read-write access to the seed CSR from U-mode is allowed without an exception, while every other type of access raises an illegal-instruction exception.
RULE 33: When mseccfg.SSEED is 0, any S-mode or HS-mode access to the seed CSR raises an illegal-instruction exception.
RULE 34: When mseccfg.SSEED is 1, a read-write access to the seed CSR from S-mode or HS-mode is allowed without an exception, while every other type of access raises an illegal-instruction exception.
RULE 35: Regardless of mseccfg.SSEED and mseccfg.USEED, the seed CSR is always available in M-mode through a normal CSR read-write instruction.
RULE 36: Regardless of privilege mode and the values of mseccfg.SSEED and mseccfg.USEED, an attempted read of the seed CSR without a write raises an illegal-instruction exception.
RULE 37: When mseccfg.RLB is 1, locked PMP rules may be removed, modified, or edited.
RULE 38: If mseccfg.RLB is 0 and pmpcfg.L is 1 in any PMP rule or entry, including a disabled entry, mseccfg.RLB remains 0 and subsequent attempts to modify mseccfg.RLB are ignored until a PMP reset.
RULE 39: mseccfg.MMWP is sticky: after it is set, it cannot be cleared until a PMP reset.
RULE 40: When mseccfg.MMWP is set, an M-mode access to a memory region with no matching PMP rule is denied rather than ignored.
RULE 41: mseccfg.MML is sticky: after it is set, it cannot be cleared until a PMP reset.
RULE 42: When mseccfg.MML is set, pmpcfg.L no longer simply marks a rule as locked and enforced in all modes; subject to the Shared-Region encodings, a set pmpcfg.L denotes an M-mode-only rule and a clear pmpcfg.L denotes an S/U-mode-only rule.
RULE 43: If mseccfg.MML=1 and a PMP entry is encoded with pmpcfg.RW=01 or pmpcfg.LRWX=1111, PMP access checks interpret that entry as a Shared-Region rule rather than as a reserved encoding.
RULE 44: Under mseccfg.MML, an M-mode-only PMP rule is enforced for M-mode and denies access from Supervisor and User modes.
RULE 45: Under mseccfg.MML, an M-mode-only PMP rule remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 46: Under mseccfg.MML, an S/U-mode-only PMP rule is enforced for Supervisor and User modes and denies access from M-mode.
RULE 47: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L clear is a non-executable data-sharing region between M-mode and S/U-mode.
RULE 48: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L clear gives M-mode read/write access; it gives S/U-mode read-only access when pmpcfg.X is clear and read/write access when pmpcfg.X is set.
RULE 49: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set is a non-writable code-sharing region between M-mode and S/U-mode.
RULE 50: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set gives both M-mode and S/U-mode execute access, and additionally gives M-mode read access when pmpcfg.X is set.
RULE 51: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 52: Under mseccfg.MML, the pmpcfg.LRWX=1111 Shared-Region encoding gives both M-mode and S/U-mode read-only access to the region.
RULE 53: Under mseccfg.MML, a pmpcfg.LRWX=1111 Shared-Region rule remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 54: When mseccfg.MML is set and mseccfg.RLB is not providing a bypass, software cannot add executable privileges to an M-mode-only rule or to a locked Shared-Region rule; attempted pmpcfg writes that do so are ignored and leave pmpcfg unchanged.
RULE 55: Setting mseccfg.RLB temporarily lifts the mseccfg.MML restriction against adding executable M-mode-only rules or executable locked Shared-Region rules, for example during boot.
RULE 56: When mseccfg.MML is set, M-mode code may execute only from a region matching an executable M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 57: When mseccfg.MML is set, M-mode execution from a region without a matching PMP rule is denied.
RULE 58: When mseccfg.MML is set, M-mode execution from a region matching an S/U-mode-only rule is denied.
RULE 59: If Smmpm is not implemented, mseccfg.PMM is read-only zero.
RULE 60: A value of 00 in mseccfg.PMM disables pointer masking and selects PMLEN=0.
RULE 61: If mseccfg.PMM contains 10, pointer masking is enabled with PMLEN=XLEN−57, so on RV64 pointer masking uses PMLEN=7.
RULE 62: A value of 11 in mseccfg.PMM enables pointer masking with PMLEN=XLEN−48, which gives PMLEN=16 on RV64.
RULE 63: When mseccfg.MLPE is 1, Zicfilp is enabled in M-mode.
RULE 64: If mseccfg.MLPE is 0, an indirect control transfer in M-mode to an instruction other than LPAD does not raise a Zicfilp landing-pad exception.
RULE 65: If the hart executes an instruction in M-mode that would update the ELP state while mseccfg.MLPE is 0, then the ELP state is not updated and remains NO_LP_EXPECTED.
RULE 66: When mseccfg.MLPE is 0, the LPAD instruction operates as a no-op in M-mode.
RULE 67: When XLEN=64, mseccfgh does not exist, even when mseccfg is implemented.
RULE 68: If the Zicfilp extension is implemented, the mseccfg.MLPE field must be reset to 0.
RULE 69: If mseccfg.MML reads as 1, physical memory accesses are permitted or denied according to the listed physical memory protection results.
RULE 70: When mseccfg.MML=1 and pmpcfg has L=0, R=0, W=0, X=0, the region is inaccessible and causes an access exception in both M-mode and S/U-mode.
RULE 71: When mseccfg.MML=1 and pmpcfg has L=0, R=0, W=0, X=1, M-mode access causes an access exception, while the region is execute-only in S/U-mode.
RULE 72: When mseccfg.MML=1 and pmpcfg has L=0, R=0, W=1, X=0, the region is a shared data region that is read/write in M-mode and read-only in S/U-mode.
RULE 73: When mseccfg.MML=1 and pmpcfg has L=0, R=0, W=1, X=1, the region is a shared data region that is read/write in both M-mode and S/U-mode.
RULE 74: When mseccfg.MML=1 and pmpcfg has L=0, R=1, W=0, X=0, M-mode access causes an access exception, while the region is read-only in S/U-mode.
RULE 75: When mseccfg.MML=1 and pmpcfg has L=0, R=1, W=0, X=1, M-mode access causes an access exception, while the region is read/execute in S/U-mode.
RULE 76: When mseccfg.MML=1 and pmpcfg has L=0, R=1, W=1, X=0, M-mode access causes an access exception, while the region is read/write in S/U-mode.
RULE 77: When mseccfg.MML=1 and pmpcfg has L=0, R=1, W=1, X=1, M-mode access causes an access exception, while the region is read/write/execute in S/U-mode.

RULE 79: When mseccfg.MML=1 and pmpcfg has L=1, R=0, W=0, X=1, the region is locked and execute-only in M-mode, while S/U-mode access causes an access exception.

RULE 82: When mseccfg.MML=1 and pmpcfg has L=1, R=1, W=0, X=0, the region is locked and read-only in M-mode, while S/U-mode access causes an access exception.

RULE 88: If mseccfg.MLPE=1 and M-mode execution violates a Zicfilp landing-pad requirement, a software-check exception is raised; if mseccfg.MLPE=0, the same execution is not rejected by Zicfilp landing-pad enforcement.

RULE 90: If Zicfilp is not implemented or mseccfg.MLPE=0, executing LPAD in M-mode completes without exception and has no effect other than normal PC advance, and indirect control transfers to non-LPAD targets do not raise forward-edge CFI exceptions.

REGISTER: mstatus
NUMBER: 0x300
MODE: M-mode
WIDTH: MXLEN
FIELDS: 63..63=SD, 42..42=MDT, 41..41=MPELP, 39..39=MPV, 38..38=GVA, 37..37=MBE, 36..36=SBE, 35..34=SXL, 33..32=UXL, 23..23=SPELP, 22..22=TSR, 21..21=TW, 20..20=TVM, 19..19=MXR, 18..18=SUM, 17..17=MPRV, 16..15=XS, 14..13=FS, 12..11=MPP, 10..9=VS, 8..8=SPP, 7..7=MPIE, 6..6=UBE, 5..5=SPIE, 3..3=MIE, 1..1=SIE
EXTENSIONS: F, H, Smdbltrp, Ssdbltrp, V, Zfinx, Zicfilp
RULE 1: If WRS.NTO executes outside M-mode with mstatus.TW=1 and does not complete within an implementation-specific bounded timeout, it raises an illegal-instruction exception; with mstatus.TW=0, execution outside M-mode does not raise an illegal-instruction exception solely because of the privilege mode.
RULE 2: If mstatus.TW=1 and WRS.NTO executes outside M-mode without completing within the implementation-specific bounded time limit, then WRS.NTO raises an illegal-instruction exception.
RULE 3: The mstatus.TW rule for an illegal-instruction exception does not apply when WRS.NTO is executed in M-mode.
RULE 4: The vector context status field mstatus.VS occupies bits mstatus[10:9].
RULE 5: The mstatus.VS field is shadowed in sstatus[10:9].
RULE 6: If mstatus.VS=Off, executing any vector instruction or accessing any vector CSR raises an illegal-instruction exception; if VS=Initial or Clean and an instruction modifies vector state, subsequent mstatus readback reports VS=Dirty, analogously to mstatus.FS behavior for floating-point state.
RULE 7: When mstatus.VS is Off, attempting to execute any vector instruction raises an illegal-instruction exception.
RULE 8: When mstatus.VS is Off, attempting to access any vector CSR raises an illegal-instruction exception.
RULE 9: When mstatus.VS is Initial or Clean, executing an instruction that changes vector state changes mstatus.VS to Dirty.
RULE 10: Changes to vector CSRs count as vector-state changes that cause mstatus.VS to become Dirty when it was Initial or Clean.
RULE 11: If mstatus.VS is Dirty, mstatus.SD is set to 1.
RULE 12: If mstatus.VS is not Dirty, reading mstatus returns SD=1 if either FS or XS is Dirty; otherwise, it returns SD=0.
RULE 13: When V=1, if either mstatus.VS or vsstatus.VS is Off, executing a vector instruction or accessing a vector CSR raises an illegal-instruction exception.
RULE 14: When V=1, executing any vector instruction or accessing any vector CSR raises an illegal-instruction exception if mstatus.VS is Off, regardless of the value of vsstatus.VS.
RULE 15: When V=1, executing any vector instruction or accessing any vector CSR also raises an illegal-instruction exception if vsstatus.VS is Off, even if mstatus.VS is not Off.
RULE 16: When V=1 and neither mstatus.VS nor vsstatus.VS is Off, any instruction that changes vector state, including an instruction that changes a vector CSR, sets both mstatus.VS and vsstatus.VS to Dirty.
RULE 17: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 18: If mstatus.VS is not Dirty, reading mstatus returns SD=1 if either FS or XS is Dirty, and SD=0 otherwise.
RULE 19: If mstatus.FS is Off, attempting to execute any vector floating-point instruction raises an illegal-instruction exception.
RULE 20: Any vector floating-point instruction that modifies floating-point extension state must set mstatus.FS to Dirty.
RULE 21: If an instruction modifies any floating-point CSR or floating-point f register, then after the instruction retires, mstatus.FS reads as Dirty.
RULE 22: If the hypervisor extension is implemented and V=1, executing a vector floating-point instruction when either mstatus.FS or vsstatus.FS is Off raises an illegal-instruction exception.
RULE 23: If the hypervisor extension is implemented and V=1, a vector floating-point instruction raises an illegal-instruction exception when either mstatus.FS or vsstatus.FS is Off.
RULE 24: If the hypervisor extension is implemented and V=1, any vector floating-point instruction that modifies floating-point CSRs or f registers must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 25: Executing a CSR read of address 0x300 places the current value of mstatus in the destination register.
RULE 26: If an instruction executed below M-mode attempts to read or write mstatus, it raises an illegal-instruction exception; in M-mode, CSR instructions can read and write mstatus.
RULE 27: Writing mstatus updates its architecturally writable fields, and a subsequent read returns those fields in an MXLEN-bit value.
RULE 28: Reading sstatus returns the current values of the mstatus fields exposed at S-level and zero in all other bits; writing sstatus updates only those exposed mstatus fields, leaving all other mstatus fields unchanged.
RULE 29: In RV64, mstatus bits 33:32 form the UXL[1:0] field.
RULE 30: In RV64, mstatus bits 35:34 form the SXL[1:0] field.
RULE 31: In RV64, reading mstatus returns the GVA field in bit 38, so (mstatus >> 38) & 1 equals GVA.
RULE 32: In RV64, reading mstatus returns the MPV field in bit 39.
RULE 33: In RV64, reading mstatus returns the MPELP field in bit 41.
RULE 34: In RV64, reading mstatus returns the MDT field in bit 42; therefore, MDT equals (mstatus >> 42) & 1.
RULE 35: In RV64, reading the mstatus CSR returns the SD field in bit 63.
RULE 36: If mstatus.MIE is clear in M-mode or mstatus.SIE is clear in S-mode, an otherwise enabled pending interrupt targeting that mode is not taken; setting the corresponding bit allows the interrupt to be taken.
RULE 37: The global xIE bits are located in the low-order bits of mstatus, allowing software to atomically set or clear them with a single CSR instruction.
RULE 38: The xPIE field in mstatus stores the value of the xIE interrupt-enable bit that was active before a trap was taken.
RULE 39: The xPP field in mstatus stores the privilege mode that was active before a trap was taken.
RULE 40: If software writes an mstatus.xPP encoding for a privilege mode other than x or an implemented mode lower than x, a subsequent read of mstatus.xPP returns a legal encoding for x or an implemented lower privilege mode instead.
RULE 41: Reading mstatus returns MPP as a two-bit field that can encode privilege modes through M-mode.
RULE 42: When a trap is taken into S-mode, mstatus.SPP is set to 0 if the previous privilege mode was U-mode and to 1 if it was S-mode.
RULE 43: When a trap is taken from privilege mode y into privilege mode x, the xPIE field in mstatus is set to the previous value of xIE.
RULE 44: When a trap is taken from privilege mode y into privilege mode x, the xPP field in mstatus is set to y.
RULE 45: When a trap is taken into privilege mode x, mstatus.xPIE records the pre-trap xIE value and mstatus.xPP records the pre-trap privilege mode; executing xRET returns to the privilege mode recorded in xPP and restores xIE from xPIE.
RULE 46: Executing MRET restores the privilege mode and interrupt-enable state from mstatus.MPP and mstatus.MPIE, while executing SRET restores them from mstatus.SPP and mstatus.SPIE.
RULE 47: When an xRET instruction executes and xPP in mstatus contains privilege mode y, xIE is set to the value stored in xPIE.
RULE 48: When an xRET instruction executes and xPP in mstatus contains privilege mode y, the hart's current privilege mode is changed to y.
RULE 49: When an xRET instruction executes, the xPIE field in mstatus is set to 1.
RULE 50: When an xRET instruction executes, the xPP field in mstatus is set to the least-privileged supported mode, specified as U-mode if U-mode is implemented and otherwise M-mode.
RULE 51: If the privilege mode y restored by xRET is not M-mode, xRET also clears the MPRV field in mstatus to zero.
RULE 52: After a legal xRET executes, the corresponding xPP field in mstatus reads as the least-privileged mode supported by the implementation.
RULE 53: The xPP fields in mstatus are WARL fields, meaning written values are constrained to privilege mode x and implemented privilege modes lower than x.
RULE 54: M-mode software can determine whether a privilege mode is implemented by writing that mode's encoding to the MPP field in mstatus and then reading MPP back.
RULE 55: Upon reset, the MDT field associated with mstatus is set to 1.
RULE 56: When an explicit CSR write sets the mstatus MDT bit to 1, the mstatus MIE bit is cleared to 0.
RULE 57: On RV64, setting mstatus.MDT to 1 clears mstatus.MIE to 0 regardless of the value written to mstatus.MIE by the same CSR write.
RULE 58: The mstatus MIE bit can be explicitly set to 1 only when MDT is already 0 or, on RV64, when the same CSR write sets MDT to 0.
RULE 59: When a trap is taken into M-mode while the MDT field associated with mstatus is 0, MDT is set to 1 and the trap is delivered normally.
RULE 60: An MRET instruction executed in M-mode sets the MDT field associated with mstatus to 0.
RULE 61: An SRET instruction executed in M-mode sets the MDT field associated with mstatus to 0.

RULE 64: On an RV64 hart, after writing mstatus.SXL and entering S-mode, S-mode instructions execute using the effective XLEN selected by the read-back value of mstatus.SXL.
RULE 65: When an RV64 hart executes in U-mode, the effective XLEN used for U-mode instruction execution (UXLEN) is the value encoded by mstatus.UXL.
RULE 66: For any XLEN value, mstatus.SXL and mstatus.UXL use the same numeric encoding that misa.MXL uses for that XLEN.
