REGISTER: mseccfg
RULE 1: The Zkr extension adds the SSEED and USEED fields to the mseccfg CSR.
RULE 2: The SSEED and USEED fields of mseccfg control access to the seed CSR from U, S, and HS modes.
RULE 3: Systems using the mseccfg access-control fields should implement carefully considered policies governing lower-privilege access to physical entropy sources.
RULE 4: Instead of permitting direct access through mseccfg to an SP 800-90B or PTG.2 physical entropy source, a system may trap an attempted seed CSR access and provide virtual entropy-source data to the less-privileged client.
RULE 5: When access controlled by mseccfg is trapped and seed data is emulated, the emulated data must be generated using an appropriately seeded, secure software DRBG.
RULE 6: An implementation may implement the SSEED and USEED fields of mseccfg as read-only fields whose constant value is 0.
RULE 7: If the SSEED or USEED field of mseccfg is a read-only constant 0, access to the seed CSR cannot be enabled for the corresponding lower-privilege mode.
RULE 8: Software can determine whether mseccfg permits seed CSR access to be enabled in U mode by writing 1 to USEED and reading back the value.
RULE 9: Software can determine whether mseccfg permits seed CSR access to be enabled in S mode by writing 1 to SSEED and reading back the value.
RULE 10: If writing 1 to a relevant SSEED or USEED field of mseccfg reads back as 1, software can infer that seed CSR access can be enabled for the corresponding mode; if it reads back as 0, it cannot be enabled.
RULE 11: The direct mseccfg.[s,u]seed option allows a security boundary to be established around a component with respect to Sensitive Security Parameter (SSP) flows.
RULE 12: A component protected using the direct mseccfg.[s,u]seed option does not need to operate in M mode.
RULE 13: The direct mseccfg.[s,u]seed option is useful when implementing trusted enclaves.
RULE 14: The direct mseccfg.[s,u]seed option can allow a module to enforce the entire lifecycle of a key within its security boundary.
RULE 15: With the direct mseccfg.[s,u]seed option, the protected key lifecycle can begin at key birth in the entropy source and end at key death through zeroization.
RULE 16: With the direct mseccfg.[s,u]seed option, a module can avoid passing a key across its security boundary to external code.
RULE 17: Direct entropy-source access enabled through mseccfg.[s,u]seed must be evaluated for depletion attacks because active polling can deny entropy to another simultaneous consumer.
RULE 18: In a virtualized system using mseccfg.[s,u]seed for direct entropy access, depletion can delay the initialization of another virtual machine that requires entropy.
RULE 19: Direct entropy-source access through mseccfg.[s,u]seed must be evaluated for covert channels because one consumer can alter whether another consumer observes WAIT instead of ES16.
RULE 20: Interactions resulting from mseccfg.[s,u]seed direct access can potentially establish low-bandwidth communication channels across security boundaries.
RULE 21: Direct entropy-source access through mseccfg.[s,u]seed must account for hardware fingerprinting because an entropy source and its noise-source circuits may possess a uniquely identifiable hardware signature.
RULE 22: When mseccfg.[s,u]seed is used in anonymized virtualized environments or enclaves, a DRBG can mask statistical features that could otherwise reveal an entropy-source hardware signature.
RULE 23: When mseccfg.[s,u]seed permits direct access to a physical entropy source shared among multiple virtual machines, the output should undergo conditioning and DRBG processing.
RULE 24: Conditioning and DRBG processing are recommended with mseccfg.[s,u]seed when the guest operating system receiving entropy is untrusted.
RULE 25: A virtual entropy source used in conjunction with mseccfg access is more resistant to depletion attacks and reduces covert-channel risk compared with unmediated physical entropy access.
RULE 26: Implementations of mseccfg.[s,u]seed should avoid unnecessary status bits, custom bits, or other mechanisms that create information flows or disable or affect entropy-source output.
RULE 27: All information flows and interaction mechanisms associated with mseccfg.[s,u]seed must be evaluated from an adversarial perspective, and their number should be minimized.
RULE 28: The entropy-polling interface exposed through mseccfg.[s,u]seed should not be assumed to operate in constant time.
RULE 29: Timing behavior associated with mseccfg.[s,u]seed polling must be analyzed as a possible timing oracle, such as by modeling seed generation as a rejection sampler.
RULE 30: A timing oracle associated with mseccfg.[s,u]seed may reveal the noise-source type and entropy-source usage.
RULE 31: A timing oracle associated with mseccfg.[s,u]seed must not reveal the random output entropy bits themselves; if it does, additional countermeasures are required.
RULE 32: mseccfg is a currently allocated RISC-V machine-level control and status register (CSR).
RULE 33: mseccfg is assigned CSR address 0x747.
RULE 34: mseccfg has the privilege/access designation MRW.
RULE 35: mseccfg is the Machine Security Configuration Register.
RULE 36: mseccfg belongs to the Machine Configuration register category.
RULE 37: mseccfg is a 64-bit read/write CSR that controls security features.
RULE 38: mseccfg is implemented if any implemented extension adds a field to mseccfg; otherwise, mseccfg is reserved.
RULE 39: The Zkr extension adds the SSEED and USEED fields to mseccfg to control access to the seed CSR from privilege modes less privileged than M-mode.
RULE 40: When mseccfg.USEED is 0, any U-mode access to the seed CSR raises an illegal-instruction exception.
RULE 41: When mseccfg.USEED is 1, a read-write access to the seed CSR from U-mode is allowed without an exception, while every other type of access raises an illegal-instruction exception.
RULE 42: If either Zkr or U-mode is not implemented, mseccfg.USEED is read-only zero.
RULE 43: When mseccfg.SSEED is 0, any S-mode or HS-mode access to the seed CSR raises an illegal-instruction exception.
RULE 44: When mseccfg.SSEED is 1, a read-write access to the seed CSR from S-mode or HS-mode is allowed without an exception, while every other type of access raises an illegal-instruction exception.
RULE 45: If either Zkr or S-mode is not implemented, mseccfg.SSEED is read-only zero.
RULE 46: Regardless of mseccfg.SSEED and mseccfg.USEED, the seed CSR is always available in M-mode through a normal CSR read-write instruction.
RULE 47: Regardless of privilege mode and the values of mseccfg.SSEED and mseccfg.USEED, an attempted read of the seed CSR without a write raises an illegal-instruction exception.
RULE 48: When the H extension is implemented and mseccfg.SSEED is 0, any VS-mode or VU-mode access to the seed CSR raises an illegal-instruction exception.
RULE 49: When the H extension is implemented and mseccfg.SSEED is 1, a read-write seed CSR access from an HS-qualified instruction in VS-mode or VU-mode raises a virtual-instruction exception, while other seed CSR access conditions raise an illegal-instruction exception.
RULE 50: The Smepmp extension adds the RLB, MMWP, and MML fields to mseccfg.
RULE 51: mseccfg.RLB, named Rule Locking Bypass, is a WARL field that provides a mechanism for temporarily modifying locked PMP rules.
RULE 52: When mseccfg.RLB is 1, locked PMP rules may be removed, modified, or edited.
RULE 53: If mseccfg.RLB is 0 and pmpcfg.L is 1 in any PMP rule or entry, including a disabled entry, mseccfg.RLB remains 0 and subsequent attempts to modify mseccfg.RLB are ignored until a PMP reset.
RULE 54: mseccfg.RLB is intended for debugging or as a temporary boot-time workaround that simplifies software and optimizes allocation of memory and PMP rules.
RULE 55: Use of mseccfg.RLB during normal operation after boot should be avoided because it weakens the protection of M-mode-only rules.
RULE 56: An implementation that does not need Rule Locking Bypass functionality may hardwire mseccfg.RLB to 0.
RULE 57: mseccfg.MMWP, named Machine-Mode Allowlist Policy, is a WARL field.
RULE 58: mseccfg.MMWP is sticky: after it is set, it cannot be cleared until a PMP reset.
RULE 59: When mseccfg.MMWP is set, an M-mode access to a memory region with no matching PMP rule is denied rather than ignored.
RULE 60: mseccfg.MML, named Machine Mode Lockdown, is a WARL field.
RULE 61: mseccfg.MML is sticky: after it is set, it cannot be cleared until a PMP reset.
RULE 62: When mseccfg.MML is set, pmpcfg.L no longer simply marks a rule as locked and enforced in all modes; subject to the Shared-Region encodings, a set pmpcfg.L denotes an M-mode-only rule and a clear pmpcfg.L denotes an S/U-mode-only rule.
RULE 63: When mseccfg.MML is set, the formerly reserved pmpcfg.RW=01 encoding and the pmpcfg.LRWX=1111 encoding represent Shared-Region rules.
RULE 64: Under mseccfg.MML, an M-mode-only PMP rule is enforced for M-mode and denies access from Supervisor and User modes.
RULE 65: Under mseccfg.MML, an M-mode-only PMP rule remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 66: Under mseccfg.MML, an S/U-mode-only PMP rule is enforced for Supervisor and User modes and denies access from M-mode.
RULE 67: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L clear is a non-executable data-sharing region between M-mode and S/U-mode.
RULE 68: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L clear gives M-mode read/write access; it gives S/U-mode read-only access when pmpcfg.X is clear and read/write access when pmpcfg.X is set.
RULE 69: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set is a non-writable code-sharing region between M-mode and S/U-mode.
RULE 70: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set gives both M-mode and S/U-mode execute access, and additionally gives M-mode read access when pmpcfg.X is set.
RULE 71: Under mseccfg.MML, a Shared-Region rule with pmpcfg.L set remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 72: Under mseccfg.MML, the pmpcfg.LRWX=1111 Shared-Region encoding gives both M-mode and S/U-mode read-only access to the region.
RULE 73: Under mseccfg.MML, a pmpcfg.LRWX=1111 Shared-Region rule remains locked, so changes to its associated PMP configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 74: When mseccfg.MML is set and mseccfg.RLB is not providing a bypass, software cannot add executable privileges to an M-mode-only rule or to a locked Shared-Region rule; attempted pmpcfg writes that do so are ignored and leave pmpcfg unchanged.
RULE 75: Setting mseccfg.RLB temporarily lifts the mseccfg.MML restriction against adding executable M-mode-only rules or executable locked Shared-Region rules, for example during boot.
RULE 76: When mseccfg.MML is set, M-mode code may execute only from a region matching an executable M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 77: When mseccfg.MML is set, M-mode execution from a region without a matching PMP rule is denied.
RULE 78: When mseccfg.MML is set, M-mode execution from a region matching an S/U-mode-only rule is denied.
RULE 79: When mseccfg.MML is clear, the pmpcfg.RW=01 encoding remains reserved for future standard use.
RULE 80: If the Smmpm extension is implemented, mseccfg.PMM is a WARL field that enables or disables pointer masking for M-mode.
RULE 81: If Smmpm is not implemented, mseccfg.PMM is read-only zero.

REGISTER: satp
RULE 1: satp is a currently allocated RISC-V supervisor-level CSR.
RULE 2: satp has CSR address 0x180.
RULE 3: satp has SRW privilege, indicating supervisor-level read/write access.
RULE 4: satp belongs to the Supervisor Protection and Translation category.
RULE 5: satp is the supervisor address translation and protection register.
RULE 6: All S-mode instruction fetches implicitly read the satp CSR.
RULE 7: Unless otherwise specified, an implicit read of satp returns the same value that an explicit read of satp would return using a CSR-access instruction executed in a sufficient privilege mode.
RULE 8: The satp register contains a MODE field.
RULE 9: If satp.MODE is read-only 0, the SUM bit in the mstatus register is also read-only 0.
RULE 10: satp is a CSR associated with supervisor virtual-memory management operations.
RULE 11: The mstatus.TVM bit is a WARL field that controls whether S-mode accesses to satp are intercepted.
RULE 12: When mstatus.TVM=1, an attempt to read satp while executing in S-mode raises an illegal-instruction exception.
RULE 13: When mstatus.TVM=1, an attempt to write satp while executing in S-mode raises an illegal-instruction exception.
RULE 14: When mstatus.TVM=0, reading satp while executing in S-mode is permitted.
RULE 15: When mstatus.TVM=0, writing satp while executing in S-mode is permitted.
RULE 16: When S-mode is not supported, the mstatus.TVM control governing S-mode satp accesses is read-only zero.
RULE 17: Trapping satp accesses provides virtualization software with hooks needed to populate shadow page tables lazily.
RULE 18: Intercepting satp accesses through mstatus.TVM helps guest operating systems execute in S-mode instead of requiring them to be virtualized in U-mode.
RULE 19: Selectively trapping satp accesses helps avoid trapping accesses to most other S-mode CSRs.
RULE 20: The satp register contains a MODE field that selects the S-mode address-translation mode.
RULE 21: If satp.MODE is read-only zero, satp is permanently configured for Bare address translation.
RULE 22: If S-mode is unsupported or satp.MODE is read-only zero, the implementation may make menvcfg.FIOM read-only zero.
RULE 23: The satp register can point to page tables used for S-mode address translation.
RULE 24: The menvcfg.PBMTE bit controls whether the Svpbmt extension is available for page tables pointed to by satp.
RULE 25: When menvcfg.PBMTE is 1, Svpbmt is available for S-mode address translation through page tables pointed to by satp.
RULE 26: When menvcfg.PBMTE is 0, the implementation behaves as though Svpbmt were not implemented for address translation through page tables pointed to by satp.
RULE 27: If Svpbmt is not implemented, menvcfg.PBMTE is read-only zero, so Svpbmt cannot be enabled for page tables pointed to by satp.
RULE 28: After menvcfg.PBMTE changes, executing SFENCE.VMA with rs1=x0 and rs2=x0 is sufficient to synchronize address-translation caches with the changed interpretation of PBMT fields in page-table entries associated with satp.
RULE 29: The menvcfg.PBMTE control applies both to S-mode page tables pointed to by satp and to G-stage page tables pointed to by hgatp.
RULE 30: If satp.MODE is read-only zero, the SUM bit in the sstatus register must also be read-only zero.
RULE 31: When satp.MODE is read-only zero, software cannot set sstatus.SUM to 1.
RULE 32: satp contains a MODE field, referenced as satp.MODE.
RULE 33: If satp.MODE is read-only zero, the address-translation mode is always Bare.
RULE 34: When satp.MODE is read-only zero and therefore always Bare, the implementation may make senvcfg.FIOM read-only zero.
RULE 35: The satp CSR is an SXLEN-bit read/write register that controls supervisor-mode address translation and protection.
RULE 36: Access to satp is subject to the CSR access rules described in Section 3.1.6.6.
RULE 37: The satp register contains a MODE field, an ASID field, and a physical page number (PPN) field.
RULE 38: The satp.PPN field contains the physical page number of the root page table, calculated as its supervisor physical address divided by 4 KiB.
RULE 39: The satp.PPN field might not be able to represent every physical page number supported by a system.
RULE 40: Platform standards may constrain the values permitted in satp.PPN, such as requiring satp.PPN to represent every physical page number belonging to main memory.
RULE 41: The satp.ASID field identifies an address space and facilitates address-translation fences on a per-address-space basis.
RULE 42: The satp.MODE field selects the current address-translation scheme.
RULE 43: When SXLEN=64, satp[63:60] is the 4-bit WARL MODE field, satp[59:44] is the 16-bit WARL ASID field, and satp[43:0] is the 44-bit WARL PPN field.

RULE 45: Atomically changing satp.ASID and satp.PPN prevents a non-atomic context switch from polluting the old virtual address space with new translations or the new virtual address space with old translations.
RULE 46: Storing the ASID and root-page-table PPN together in satp slightly reduces context-switch cost.
RULE 47: When satp.MODE=Bare, supervisor virtual addresses are equal to supervisor physical addresses.
RULE 48: When satp.MODE=Bare, satp provides no additional memory protection beyond the applicable physical memory protection scheme.
