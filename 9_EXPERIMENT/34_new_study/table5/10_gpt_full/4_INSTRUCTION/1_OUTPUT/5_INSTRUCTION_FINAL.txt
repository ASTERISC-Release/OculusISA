INSTRUCTION: CSRRWI
FORMAT: csrrwi rd, csr, zimm5
RULE 1: If CSRRWI is interrupted or otherwise architecturally observed during execution, the observer sees either none or all of its applicable read and write effects on the addressed CSR, never a partially completed state.
RULE 2: CSRRWI derives its XLEN-bit CSR write value by zero-extending the 5-bit unsigned immediate uimm[4:0] rather than obtaining a value from an integer source register.
RULE 3: When rd is not x0, CSRRWI reads the value of the CSR that existed before the CSR write.
RULE 4: When rd is not x0, CSRRWI zero-extends the old CSR value to XLEN bits and writes the result to integer register rd.
RULE 5: If CSRRWI specifies rd=x0, the CSR is not read and no architecturally observable CSR-read side effects occur.
RULE 6: If CSRRWI is executed with rd=x0, no CSR read is performed and no side effect attributable to reading the CSR occurs.
RULE 7: CSRRWI writes the XLEN-bit value obtained by zero-extending uimm[4:0] to the CSR regardless of the values of rd and uimm[4:0].
RULE 8: When uimm[4:0] is zero, CSRRWI attempts to write zero to the CSR.
RULE 9: If CSRRWI writes a CSR containing fields with write side effects, then the architecturally defined write side effect of every such field occurs.
RULE 10: If CSRRWI reads a standard CSR, the read causes no architectural state change other than placing the CSR’s pre-write value in rd; any other CSR state change results only from the write.
RULE 11: When CSRRWI reads a CSR that may also be modified as a side effect of instruction execution, CSRRWI reads the CSR value that existed before execution of CSRRWI.
RULE 12: When CSRRWI writes a CSR that would otherwise be modified as a side effect of instruction execution, the explicit CSRRWI write occurs instead of the side-effect update.
RULE 13: When CSRRWI writes a value to instret, the following instruction reads that written value from instret.
RULE 14: For a CSRRWI with rd ≠ x0, rd contains the pre-instruction value of the CSR selected by the csr field.
RULE 15: For CSRRWI with rd other than x0, the addressed CSR is read as an implicit source, and rd receives the CSR value from before the instruction’s CSR write.
RULE 16: If a CSRRWI instruction executes successfully with rd naming r other than x0, then r contains the CSR value from before the instruction updated that CSR.
RULE 17: If a CSRRWI instruction implicitly designates CSR r as a destination and r is not x0, executing the instruction updates r, and a subsequent read of r returns the value written by the instruction.

INSTRUCTION: FCVT.W.D
FORMAT: fcvt.w.d rd, fs1, rm
RULE 1: When the double-precision floating-point value in floating-point register rs1 is finite and rounds according to the rm field to an integer in the range -2^31 through 2^31-1, FCVT.W.D writes that signed 32-bit integer to integer register rd.
RULE 2: When the finite double-precision floating-point value in rs1 rounds according to the rm field to a value less than -2^31, FCVT.W.D writes -2^31 to rd and sets the invalid operation exception flag.
RULE 3: When the finite double-precision floating-point value in rs1 rounds according to the rm field to a value greater than 2^31-1, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 4: When the double-precision floating-point value in rs1 is negative infinity, FCVT.W.D writes -2^31 to rd and sets the invalid operation exception flag.
RULE 5: When the double-precision floating-point value in rs1 is positive infinity, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 6: When the double-precision floating-point value in rs1 is any NaN, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 7: On RV64, FCVT.W.D sign-extends the signed 32-bit conversion result through the upper 32 bits of integer register rd.
RULE 8: For the same input operand, FCVT.W.D MUST raise the same floating-point exception flags as FCVTMOD.W.D.

INSTRUCTION: SFENCE.VMA
FORMAT: sfence.vma rs1, rs2
RULE 1: When TVM=1, an attempt to execute SFENCE.VMA in S-mode raises an illegal-instruction exception.
RULE 2: When TVM=0, execution of SFENCE.VMA is permitted in S-mode.
RULE 3: When rs1 contains a value that is not a valid virtual address, SFENCE.VMA raises no exception.
RULE 4: For any privilege mode and control-CSR state, SINVAL.VMA raises an illegal-instruction exception for lack of execution permission exactly when SFENCE.VMA would do so.
RULE 5: SFENCE.VMA and SINVAL.VMA raise the same exceptions under the same execution conditions.
RULE 6: An attempt to execute SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 7: An attempt to execute SFENCE.VMA in S-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 8: An attempt to execute SFENCE.VMA in HS-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 9: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 10: An attempt to execute SFENCE.VMA in VS-mode when hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 11: When VTVM is 1, an attempt to execute SFENCE.VMA in VS-mode raises a virtual-instruction exception.
RULE 12: When V=1 and execution is in VU-mode, an attempt to execute SFENCE.VMA raises a virtual-instruction exception with exception code 22.
RULE 13: When V=1, execution is in VS-mode, and hstatus.VTVM=1, an attempt to execute SFENCE.VMA raises a virtual-instruction exception with exception code 22.
RULE 14: When determining whether SFENCE.VMA raises an exception in VS-mode, mstatus.TSR is ignored.
RULE 15: When determining whether SFENCE.VMA raises an exception in VS-mode, mstatus.TVM is ignored.
RULE 16: On a virtual-instruction trap caused by SFENCE.VMA, mtval or stval, as applicable, is written with the same value as for an illegal-instruction trap.

INSTRUCTION: VLE32FF.V
FORMAT: vle32ff.v vd, (rs1), vm
RULE 1: If VLE32FF.V completes normally, each loaded 32-bit destination element vd[i] contains the value read from memory address x[rs1] + 4×i.
RULE 2: VLE32FF.V executes as a regular vector load except that a synchronous exception can cause a trap only when the exception occurs on element 0.
RULE 3: If element 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST take the corresponding trap.
RULE 4: If element 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST leave vl unmodified.
RULE 5: If an element with an index greater than 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST NOT take the trap corresponding to that exception.
RULE 6: If an element with an index greater than 0 would raise a synchronous exception during VLE32FF.V, VLE32FF.V MUST reduce vl to the index of that element.
RULE 7: When an element causes VLE32FF.V to trim vl, VLE32FF.V MUST NOT update destination elements past the original vector length.
RULE 8: When VLE32FF.V raises no exception and begins with vstart equal to 0 and vl greater than 0, VLE32FF.V MUST process at least one element.
