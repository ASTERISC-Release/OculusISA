INSTRUCTION: CSRRWI
RULE 1: CSRRWI atomically performs all applicable read and write operations on a single CSR.
RULE 2: CSRRWI derives its XLEN-bit CSR write value by zero-extending the 5-bit unsigned immediate uimm[4:0] rather than obtaining a value from an integer source register.
RULE 3: When rd is not x0, CSRRWI reads the value of the CSR that existed before the CSR write.
RULE 4: When rd is not x0, CSRRWI zero-extends the old CSR value to XLEN bits and writes the result to integer register rd.
RULE 5: When rd is x0, CSRRWI MUST NOT read the CSR.
RULE 6: When rd is x0, CSRRWI MUST NOT cause any side effect that could result from reading the CSR.
RULE 7: CSRRWI writes the XLEN-bit value obtained by zero-extending uimm[4:0] to the CSR regardless of the values of rd and uimm[4:0].
RULE 8: When uimm[4:0] is zero, CSRRWI attempts to write zero to the CSR.
RULE 9: When a CSR contains fields that have side effects when written, CSRRWI triggers the write side effects of all such fields within the written CSR.
RULE 10: When CSRRWI reads a standard CSR, the read has no side effects.
RULE 11: When CSRRWI reads a CSR that may also be modified as a side effect of instruction execution, CSRRWI reads the CSR value that existed before execution of CSRRWI.
RULE 12: When CSRRWI writes a CSR that would otherwise be modified as a side effect of instruction execution, the explicit CSRRWI write occurs instead of the side-effect update.
RULE 13: When CSRRWI writes a value to instret, the following instruction reads that written value from instret.
RULE 14: When dependencies involving a CSRRWI instruction are determined, a general-purpose register is treated as an entire register.
RULE 15: When dependencies involving a CSRRWI instruction are determined, a register that identifies a CSR may denote either a portion of the CSR or the entire CSR.
RULE 16: Dependency tracking through a CSR for a CSRRWI instruction uses the dependency granularity defined individually for that CSR.
RULE 17: For a CSRRWI instruction i whose rd field is not set to x0, a register r other than x0 is a source register when the csr field of i is set to r.
RULE 18: For a CSRRWI instruction i whose rd field is set to x0, a register r other than x0 is not classified as a source register solely because the csr field of i is set to r.
RULE 19: For a CSRRWI instruction, a register r other than x0 is a source register when r is a CSR that is an implicit source register of the CSRRWI instruction.
RULE 20: For a CSRRWI instruction, a register r other than x0 is a source register when r is a CSR that aliases another source register of the CSRRWI instruction.
RULE 21: For a CSRRWI instruction i, a register r other than x0 is a destination register when the rd field of i is set to r.
RULE 22: For a CSRRWI instruction i, a register r other than x0 is a destination register when the csr field of i is set to r, including when the rd field of i is set to x0.
RULE 23: For a CSRRWI instruction, a register r other than x0 is a destination register when r is a CSR that is an implicit destination register of the CSRRWI instruction.
RULE 24: For a CSRRWI instruction, a register r other than x0 is a destination register when r is a CSR that aliases another destination register of the CSRRWI instruction.
RULE 25: An instruction j has a syntactic dependency on a CSRRWI instruction i via destination register s of i and source register r of j when s and r are the same register and no instruction program-ordered between i and j has r as a destination register.
RULE 26: An instruction j has a syntactic dependency on a CSRRWI instruction i via destination register s of i and source register r of j when there is an instruction m program-ordered between i and j, a destination register q of m, and a source register p of m such that j has a syntactic dependency on m via q and r, m has a syntactic dependency on i via s and p, and m carries a dependency from p to q.
RULE 27: A CSRRWI instruction j has a syntactic dependency on an instruction i via destination register s of i and source register r of j when s and r are the same register and no instruction program-ordered between i and j has r as a destination register.
RULE 28: A CSRRWI instruction j has a syntactic dependency on an instruction i via destination register s of i and source register r of j when there is an instruction m program-ordered between i and j, a destination register q of m, and a source register p of m such that j has a syntactic dependency on m via q and r, m has a syntactic dependency on i via s and p, and m carries a dependency from p to q.

INSTRUCTION: FCVT.W.D
RULE 1: When the double-precision floating-point value in floating-point register rs1 is finite and rounds according to the rm field to an integer in the range -2^31 through 2^31-1, FCVT.W.D writes that signed 32-bit integer to integer register rd.
RULE 2: When the finite double-precision floating-point value in rs1 rounds according to the rm field to a value less than -2^31, FCVT.W.D writes -2^31 to rd and sets the invalid operation exception flag.
RULE 3: When the finite double-precision floating-point value in rs1 rounds according to the rm field to a value greater than 2^31-1, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 4: When the double-precision floating-point value in rs1 is negative infinity, FCVT.W.D writes -2^31 to rd and sets the invalid operation exception flag.
RULE 5: When the double-precision floating-point value in rs1 is positive infinity, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 6: When the double-precision floating-point value in rs1 is any NaN, FCVT.W.D writes 2^31-1 to rd and sets the invalid operation exception flag.
RULE 7: On RV64, FCVT.W.D sign-extends the signed 32-bit conversion result through the upper 32 bits of integer register rd.
RULE 8: For the same input operand, FCVT.W.D MUST raise the same floating-point exception flags as FCVTMOD.W.D.

INSTRUCTION: SFENCE.VMA
RULE 1: If any supervisor-level memory-management data structures, such as page tables, remain in use across a change to SBE, M-mode software MUST execute SFENCE.VMA with rs1 = x0 and rs2 = x0 after changing SBE.
RULE 2: If SBE is changed at runtime during a world switch and neither the old nor the new memory-management data structure will be reinterpreted with a different endianness, no SFENCE.VMA execution is required beyond the SFENCE.VMA execution ordinarily required for the world switch.
RULE 3: When TVM=1, an attempt to execute SFENCE.VMA in S-mode raises an illegal-instruction exception.
RULE 4: When TVM=0, execution of SFENCE.VMA is permitted in S-mode.
RULE 5: After menvcfg.PBMTE is changed, executing SFENCE.VMA with rs1 = x0 and rs2 = x0 is sufficient to synchronize address-translation caches with the altered interpretation of page-table-entry PBMT fields.
RULE 6: After menvcfg.ADUE is changed, executing SFENCE.VMA with rs1 = x0 and rs2 = x0 is sufficient to synchronize address-translation caches with the altered interpretation of page-table-entry A/D bits.
RULE 7: When PMP settings are modified on a system implementing page-based virtual memory, M-mode software MUST execute SFENCE.VMA with rs1 = x0 and rs2 = x0 after writing the PMP CSRs to synchronize the PMP settings with the virtual memory system and any PMP or address-translation caches.
RULE 8: When page-based virtual memory is not implemented, SFENCE.VMA is not needed after modifying PMP settings because memory accesses check the PMP settings synchronously.
RULE 9: If a translation began while satp was active and satp later becomes inactive, the translation is not required to complete or terminate unless an SFENCE.VMA matching the translation's address and ASID is executed.
RULE 10: Software must execute SFENCE.VMA to ensure that updates to address-translation data structures are observed by a hart's subsequent implicit reads of those structures.
RULE 11: Writing satp does not provide the ordering between page-table updates and subsequent address translations for which SFENCE.VMA may be required.
RULE 12: Writing satp does not invalidate address-translation caches, so SFENCE.VMA may still be required after a satp write.
RULE 13: If the page tables of a new address space have been modified, it may be necessary to execute SFENCE.VMA after writing satp or, in some cases, before writing satp.
RULE 14: If an ASID is reused, it may be necessary to execute SFENCE.VMA after writing satp or, in some cases, before writing satp.
RULE 15: Executing SFENCE.VMA guarantees that previous stores already visible to the current hart are ordered before subsequent implicit references by that hart to the memory-management data structures selected by rs1 and rs2.
RULE 16: When rs1 is x0 or contains a valid virtual address, SFENCE.VMA invalidates the local hart's address-translation cache entries selected by rs1 and rs2.
RULE 17: When rs1 is x0 or contains a valid virtual address, SFENCE.VMA flushes the local hart's hardware cache state related to address translation within the scope selected by rs1 and rs2.
RULE 18: SFENCE.VMA orders implicit references to memory-management data structures only for the hart that executes the instruction and does not order implicit references made by other harts.
RULE 19: When memory-management data structures are modified, executing SFENCE.VMA on one hart does not notify other harts, so the other harts MUST be notified separately.
RULE 20: When rs1 = x0 and rs2 = x0, SFENCE.VMA orders previous stores already visible to the current hart before all subsequent implicit reads and writes by that hart to every page-table level in every address space.
RULE 21: When rs1 = x0 and rs2 = x0, SFENCE.VMA invalidates all address-translation cache entries associated with the local hart for all address spaces.
RULE 22: When rs1 = x0 and rs2 != x0, SFENCE.VMA orders previous stores already visible to the current hart before all subsequent implicit reads and writes by that hart to every page-table level for the address space identified by the value in rs2.
RULE 23: When rs1 = x0 and rs2 != x0, SFENCE.VMA does not guarantee ordering for accesses to global mappings.
RULE 24: When rs1 = x0 and rs2 != x0, SFENCE.VMA invalidates all local address-translation cache entries that match the address space identified by the value in rs2 and do not contain global mappings.
RULE 25: When rs1 = x0 and rs2 != x0, SFENCE.VMA does not require local address-translation cache entries containing global mappings to be invalidated.
RULE 26: When rs1 != x0, rs1 contains a valid virtual address, and rs2 = x0, SFENCE.VMA orders previous stores already visible to the current hart before subsequent implicit reads and writes by that hart to leaf page-table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 27: When rs1 != x0, rs1 contains a valid virtual address, and rs2 = x0, SFENCE.VMA invalidates all local address-translation cache entries containing leaf page-table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 28: When rs1 != x0, rs1 contains a valid virtual address, and rs2 != x0, SFENCE.VMA orders previous stores already visible to the current hart before subsequent implicit reads and writes by that hart to leaf page-table entries corresponding to the virtual address in rs1 for the address space identified by the value in rs2.
RULE 29: When rs1 != x0, rs1 contains a valid virtual address, and rs2 != x0, SFENCE.VMA does not guarantee ordering for accesses to global mappings.
RULE 30: When rs1 != x0, rs1 contains a valid virtual address, and rs2 != x0, SFENCE.VMA invalidates all local address-translation cache entries that contain leaf page-table entries corresponding to the virtual address in rs1, match the address space identified by the value in rs2, and do not contain global mappings.
RULE 31: When rs1 != x0, rs1 contains a valid virtual address, and rs2 != x0, SFENCE.VMA does not require local address-translation cache entries containing global mappings to be invalidated.
RULE 32: When rs1 contains a value that is not a valid virtual address, SFENCE.VMA has no effect.
RULE 33: When rs1 contains a value that is not a valid virtual address, SFENCE.VMA raises no exception.
RULE 34: An implementation may legally over-fence an SFENCE.VMA by using only a subset of the bits in rs1, rs2, or both to determine the fence scope.
RULE 35: An implementation may legally treat every SFENCE.VMA as if rs1 = x0.
RULE 36: An implementation may legally treat every SFENCE.VMA as if rs2 = x0.
RULE 37: An implementation may ignore both the virtual address in rs1 and the ASID in rs2 for every SFENCE.VMA and always perform a global fence.
RULE 38: When rs2 != x0 for SFENCE.VMA, bits SXLEN-1:ASIDMAX of the value in rs2 are reserved for future standard use.
RULE 39: Until a standard extension defines a use for bits SXLEN-1:ASIDMAX of a nonzero rs2 value for SFENCE.VMA, software should set those bits to zero.
RULE 40: Until a standard extension defines a use for bits SXLEN-1:ASIDMAX of a nonzero rs2 value for SFENCE.VMA, current implementations ignore those bits.
RULE 41: If ASIDLEN < ASIDMAX, an implementation MUST ignore bits ASIDMAX-1:ASIDLEN of the value in rs2 when executing SFENCE.VMA.
RULE 42: An implicit read of memory-management data structures may return any translation for an address that was valid at any time since the most recent SFENCE.VMA whose rs1 and rs2 scope includes that address and translation context.
RULE 43: SFENCE.VMA does not require its ordered implicit reads and writes to memory-management data structures to participate in the global memory order according to the standard RVWMO ordering rules.
RULE 44: SFENCE.VMA orders prior explicit accesses before subsequent implicit accesses that fall within the scope selected by rs1 and rs2.
RULE 45: Each implicit access ordered by SFENCE.VMA is ordered before the explicit access whose address translation depends on that implicit access.
RULE 46: SFENCE.VMA does not necessarily order prior explicit accesses before subsequent explicit accesses in the global memory order.
RULE 47: SFENCE.VMA does not require implicit loads from memory-management data structures to obey normal program order relative to prior loads or stores to the same address.
RULE 48: If a leaf PTE is modified and its virtual address is accessed before an SFENCE.VMA whose scope includes that virtual address and translation context is executed, the access uses either the new translation or any older translation that was valid since the most recent SFENCE.VMA whose scope included that virtual address and translation context.
RULE 49: If a leaf PTE is modified and its virtual address is accessed before an SFENCE.VMA whose scope includes that virtual address and translation context is executed, the choice among the permitted new and older translations is unpredictable.
RULE 50: If a leaf PTE is modified and its virtual address is accessed before an SFENCE.VMA whose scope includes that virtual address and translation context is executed, successive accesses to the same virtual address may use different permitted translations.
RULE 51: If a leaf PTE is modified and its virtual address is accessed before an SFENCE.VMA whose scope includes that virtual address and translation context is executed, the behavior is well defined except for the permitted unpredictable choice of translation.
RULE 52: For a given virtual address and ASID, an implementation may use any translation that was valid since the most recent SFENCE.VMA whose scope includes that virtual address and ASID, even if the translation used a different virtual-address width.
RULE 53: For a given virtual address, an implementation may use any global translation that was valid since the most recent SFENCE.VMA whose scope includes that virtual address, regardless of the ASID or virtual-address width used by the translation.
RULE 54: If a page is upgraded to a superpage without first clearing the original non-leaf PTE's valid bit and executing SFENCE.VMA with rs1 = x0, it is unpredictable whether address translation uses the old non-leaf PTE or the new leaf PTE.
RULE 55: If a page is upgraded to a superpage without first clearing the original non-leaf PTE's valid bit and executing SFENCE.VMA with rs1 = x0, the behavior is well defined except for the unpredictable choice between the old non-leaf PTE and the new leaf PTE.
RULE 56: A change to sstatus.SUM takes effect immediately without requiring SFENCE.VMA.
RULE 57: A change to sstatus.MXR takes effect immediately without requiring SFENCE.VMA.
RULE 58: Changing satp.MODE from Bare to another mode takes effect immediately without requiring SFENCE.VMA.
RULE 59: Changing satp.MODE from a non-Bare mode to Bare takes effect immediately without requiring SFENCE.VMA.
RULE 60: A change to satp.ASID takes effect immediately without depending on execution of SFENCE.VMA.
RULE 61: After increasing the permissions of a leaf PTE or changing an invalid PTE into a valid leaf PTE but before executing a subsuming SFENCE.VMA, an access may use either the old permissions or the new permissions.
RULE 62: After increasing the permissions of a leaf PTE or changing an invalid PTE into a valid leaf PTE but before executing a subsuming SFENCE.VMA, use of the old permissions may cause a page-fault exception.
RULE 63: On an implementation where satp.MODE is read-only zero and therefore always Bare, an attempt to execute SFENCE.VMA may raise an illegal-instruction exception.
RULE 64: Enabling pointer masking does not require SFENCE.VMA because pointer masking applies only to the effective address and does not affect memory-management data structures.
RULE 65: Disabling pointer masking does not require SFENCE.VMA because pointer masking applies only to the effective address and does not affect memory-management data structures.
RULE 66: When SFENCE.VMA is executed with rs2 != x0, global mappings need not be flushed from local address-translation caches.
RULE 67: After writes to memory-management tables, SFENCE.VMA must be executed to flush the relevant cached translations so that subsequent implicit reads observe writes to the same memory locations.
RULE 68: If SFENCE.VMA is not executed between a write to a memory-management table and a subsequent implicit read of the same address, either the old non-leaf PTE or the new leaf PTE may unpredictably be used, but the behavior is otherwise well defined.
RULE 69: A speculative execution of the address-translation algorithm must not create an address-translation cache entry if that entry would have been invalidated by any SFENCE.VMA executed by the hart after that speculative execution began.
RULE 70: For both non-speculative and speculative executions of the address-translation algorithm, it is illegal to begin translation, read the level 2 page table, pause while the hart executes SFENCE.VMA with rs1 = rs2 = x0, and then resume using the now-stale level 2 PTE, because subsequent implicit reads could populate the address-translation cache with stale PTEs.
RULE 71: SFENCE.VMA with rs1 = x0 must either terminate all previously launched speculative executions of the address-translation algorithm for the specified ASID, if applicable, or wait for all such executions to complete.
RULE 72: If SFENCE.VMA with rs1 = x0 waits for previously launched speculative executions of the address-translation algorithm for the specified ASID, if applicable, to complete, SFENCE.VMA invalidates any address-translation cache entries created by those executions as appropriate.
RULE 73: SFENCE.VMA with rs1 != x0 generally must either prevent previously launched speculative executions of the address-translation algorithm for the specified ASID, if applicable, from creating new address-translation cache entries that map leaf PTEs, or wait for those executions to complete.
RULE 74: If translation inconsistencies exist because SFENCE.VMA was used incorrectly or because of a PTE update involving SFENCE.VMA, one of the inconsistent translations is chosen, but the choice is unpredictable.
RULE 75: For identical rs1 and rs2 values, SFENCE.VMA invalidates the same address-translation cache entries as SINVAL.VMA.
RULE 76: When a single hart executes SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR in that order but not necessarily consecutively, the sequence has the same effect as a hypothetical SFENCE.VMA whose rs1 and rs2 values equal those used by SINVAL.VMA.
RULE 77: When a single hart executes SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR in that order but not necessarily consecutively, reads and writes before SFENCE.W.INVAL are considered to occur before the equivalent hypothetical SFENCE.VMA.
RULE 78: When a single hart executes SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR in that order but not necessarily consecutively, reads and writes after SFENCE.INVAL.IR are considered to occur after the equivalent hypothetical SFENCE.VMA.
RULE 79: SFENCE.VMA and SINVAL.VMA have identical execution-permission requirements.
RULE 80: SFENCE.VMA and SINVAL.VMA raise the same exceptions under the same execution conditions.
RULE 81: An attempt to execute SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 82: An attempt to execute SFENCE.VMA in S-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 83: An attempt to execute SFENCE.VMA in HS-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 84: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 85: An attempt to execute SFENCE.VMA in VS-mode when hstatus.VTVM=1 raises a virtual-instruction exception.
RULE 86: SFENCE.VMA normally synchronizes a hart's address-translation caches after a memory-resident PTE is changed from Invalid to Valid.
RULE 87: When the Svvptc extension is implemented, an operating system need not execute SFENCE.VMA after an explicit store changes the Valid bit of a leaf or non-leaf PTE from 0 to 1 and the store is visible to the hart, because the change will become visible within a bounded timeframe to subsequent implicit accesses by that hart to the PTE.
RULE 88: The Svvptc extension makes SFENCE.VMA redundant only for making a PTE change from Invalid to Valid visible within a bounded timeframe.
RULE 89: The Svvptc extension does not make SFENCE.VMA or another suitable memory-management instruction redundant for synchronizing a hart's address-translation caches after other forms of updates to a memory-resident PTE, including changing a PTE from Valid to Invalid.
RULE 90: When VTVM is 1, an attempt to execute SFENCE.VMA in VS-mode raises a virtual-instruction exception.
RULE 91: When V=0, SFENCE.VMA applies only to memory-management data structures controlled by the current HS-level satp.
RULE 92: When V=1, SFENCE.VMA applies only to memory-management data structures controlled by the current vsatp.
RULE 93: When V=0, SFENCE.VMA interprets its virtual-address argument as an HS-level virtual address.
RULE 94: When V=0, SFENCE.VMA interprets its ASID argument as an HS-level ASID.
RULE 95: When V=0, SFENCE.VMA orders only stores to HS-level address-translation structures with subsequent HS-level address translations.
RULE 96: When V=1, SFENCE.VMA interprets its virtual-address argument as a guest virtual address within the current virtual machine identified by hgatp.VMID.
RULE 97: When V=1, SFENCE.VMA interprets its ASID argument as a VS-level ASID within the current virtual machine identified by hgatp.VMID.
RULE 98: When V=1, SFENCE.VMA treats the effective ASID as the combination of hgatp.VMID and the VS-level ASID.
RULE 99: When V=1, SFENCE.VMA orders only stores to VS-level address-translation structures with subsequent VS-stage address translations for which hgatp.VMID equals the value of hgatp.VMID when SFENCE.VMA executed.
RULE 100: When PMP settings are modified in a manner that affects physical memory holding page tables used for HS-level address translation, M-mode software must synchronize the PMP settings with the virtual memory system by executing SFENCE.VMA in M-mode with rs1 = x0 and rs2 = x0 after writing the PMP CSRs.
RULE 101: When PMP settings are modified in a manner that affects physical memory to which page tables used for HS-level address translation point, M-mode software must synchronize the PMP settings with the virtual memory system by executing SFENCE.VMA in M-mode with rs1 = x0 and rs2 = x0 after writing the PMP CSRs.
RULE 102: When V=1 and execution is in VU-mode, an attempt to execute SFENCE.VMA raises a virtual-instruction exception with exception code 22.
RULE 103: When V=1, execution is in VS-mode, and hstatus.VTVM=1, an attempt to execute SFENCE.VMA raises a virtual-instruction exception with exception code 22.
RULE 104: When determining whether SFENCE.VMA raises an exception in VS-mode, mstatus.TSR is ignored.
RULE 105: When determining whether SFENCE.VMA raises an exception in VS-mode, mstatus.TVM is ignored.

RULE 108: When SFENCE.VMA is executed, pointer masking is not applied to its address operand.

INSTRUCTION: VLE32FF.V
RULE 1: VLE32FF.V loads 32-bit elements from unit-stride memory addresses based on rs1 into the destination vector register group vd.
RULE 2: VLE32FF.V executes as a regular vector load except that a synchronous exception can cause a trap only when the exception occurs on element 0.
RULE 3: If element 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST take the corresponding trap.
RULE 4: If element 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST leave vl unmodified.
RULE 5: If an element with an index greater than 0 raises a synchronous exception during VLE32FF.V, VLE32FF.V MUST NOT take the trap corresponding to that exception.
RULE 6: If an element with an index greater than 0 would raise a synchronous exception during VLE32FF.V, VLE32FF.V MUST reduce vl to the index of that element.
RULE 7: VLE32FF.V may overwrite active elements in the destination vector register group whose indices are greater than the element index at which a trap is reported.
RULE 8: When an element causes VLE32FF.V to trim vl, VLE32FF.V may update active destination elements after that element if those elements are not past the original vector length.
RULE 9: When an element causes VLE32FF.V to trim vl, VLE32FF.V MUST NOT update destination elements past the original vector length.
RULE 10: When VLE32FF.V updates active destination elements after an element that caused vl trimming, the values written by those spurious updates need not equal the memory values at the corresponding addressed locations.
RULE 11: VLE32FF.V may access a non-idempotent memory location only when it is known that the corresponding element load will not be restarted because of a trap or vector-length trimming.
RULE 12: When VLE32FF.V raises no exception, an implementation may process fewer than vl elements and reduce vl accordingly.
RULE 13: When VLE32FF.V raises no exception and begins with vstart equal to 0 and vl greater than 0, VLE32FF.V MUST process at least one element.
RULE 14: When VLE32FF.V takes a trap due to an interrupt, an implementation SHOULD NOT reduce vl.
RULE 15: When VLE32FF.V takes a trap due to an interrupt, an implementation SHOULD set vstart to an appropriate value.
RULE 16: When VLE32FF.V would trigger a debug data-watchpoint trap on an element after the first element, an implementation SHOULD NOT reduce vl.
RULE 17: When VLE32FF.V would trigger a debug data-watchpoint trap on an element after the first element, an implementation SHOULD trigger the debug trap.
