REGISTER: mseccfg
RULE 1: Software may discover whether access to the seed CSR can be enabled in U and S modes by writing 1 to the mseccfg [s,u]seed fields and reading back the result.
RULE 2: mseccfg has MRW access.
RULE 3: mseccfg is a 64-bit register.
RULE 4: mseccfg is a read/write register.
RULE 5: mseccfg exists if any implemented extension adds a field to mseccfg.
RULE 6: When mseccfg.USEED is 0, any access to the seed CSR from U-mode raises an illegal-instruction exception.
RULE 7: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed.
RULE 8: When mseccfg.USEED is 1, an access to the seed CSR from U-mode other than a read-write access raises an illegal-instruction exception.
RULE 9: If Zkr or U-mode is not implemented, mseccfg.USEED is read-only zero.
RULE 10: When mseccfg.SSEED is 0, any access to the seed CSR from S-mode or HS-mode raises an illegal-instruction exception.
RULE 11: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-mode or HS-mode is allowed.
RULE 12: When mseccfg.SSEED is 1, an access to the seed CSR from S-mode or HS-mode other than a read-write access raises an illegal-instruction exception.
RULE 13: If Zkr or S-mode is not implemented, mseccfg.SSEED is read-only zero.
RULE 14: When the H extension is implemented and mseccfg.SSEED is 0, any access to the seed CSR from VS-mode or VU-mode raises an illegal-instruction exception.
RULE 15: When the H extension is implemented and mseccfg.SSEED is 1, a read-write access to the seed CSR from an HS-qualified instruction in VS-mode or VU-mode raises a virtual-instruction exception.
RULE 16: When the H extension is implemented and mseccfg.SSEED is 1, an access to the seed CSR from VS-mode or VU-mode other than a read-write access raises an illegal-instruction exception.
RULE 17: Regardless of mseccfg.SSEED and mseccfg.USEED, the seed CSR is always available in M-mode through a CSR read-write instruction.
RULE 18: An attempted read of the seed CSR without a write raises an illegal-instruction exception in every mode regardless of mseccfg.SSEED and mseccfg.USEED.
RULE 19: When mseccfg.RLB is 1, locked PMP rules may be removed, modified, or edited.
RULE 20: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any PMP rule or entry, including a disabled entry, mseccfg.RLB remains 0 until a PMP reset.
RULE 21: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any PMP rule or entry, including a disabled entry, further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 22: mseccfg.MMWP is a sticky bit that cannot be unset after being set until a PMP reset.
RULE 23: When mseccfg.MMWP is set, the default PMP policy for M-mode access to a memory region without a matching PMP rule is denied instead of ignored.
RULE 24: mseccfg.MML is a sticky bit that cannot be unset after being set until a PMP reset.
RULE 25: When mseccfg.MML is set, a set pmpcfg.L bit marks a PMP rule as M-mode-only instead of marking it as locked and enforced in all modes.
RULE 26: When mseccfg.MML is set, an unset pmpcfg.L bit marks a PMP rule as S/U-mode-only.
RULE 27: When mseccfg.MML is set, the formerly reserved pmpcfg.RW=01 encoding encodes a Shared-Region.
RULE 28: When mseccfg.MML is set, the pmpcfg.LRWX=1111 encoding encodes a Shared-Region.
RULE 29: When mseccfg.MML is set, an M-mode-only PMP rule is enforced on M-mode.
RULE 30: When mseccfg.MML is set, an M-mode-only PMP rule denies access from S-mode and U-mode.
RULE 31: When mseccfg.MML is set, an M-mode-only PMP rule remains locked so that modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 32: When mseccfg.MML is set, an S/U-mode-only PMP rule is enforced on S-mode and U-mode.
RULE 33: When mseccfg.MML is set, an S/U-mode-only PMP rule denies access from M-mode.
RULE 34: When mseccfg.MML is set, a Shared-Region PMP rule is enforced on all modes.
RULE 35: When mseccfg.MML is set, a Shared-Region PMP rule encoded with pmpcfg.RW=01 and an unset pmpcfg.L bit is not executable.
RULE 36: When mseccfg.MML is set, M-mode has read/write access to a Shared-Region PMP rule encoded with pmpcfg.RW=01 and an unset pmpcfg.L bit.
RULE 37: When mseccfg.MML is set, S-mode and U-mode have read access to a Shared-Region PMP rule encoded with pmpcfg.RW=01, an unset pmpcfg.L bit, and an unset pmpcfg.X bit.
RULE 38: When mseccfg.MML is set, S-mode and U-mode have read/write access to a Shared-Region PMP rule encoded with pmpcfg.RW=01, an unset pmpcfg.L bit, and a set pmpcfg.X bit.
RULE 39: When mseccfg.MML is set, a Shared-Region PMP rule encoded with pmpcfg.RW=01 and a set pmpcfg.L bit is not writable.
RULE 40: When mseccfg.MML is set, M-mode, S-mode, and U-mode have execute access to a Shared-Region PMP rule encoded with pmpcfg.RW=01 and a set pmpcfg.L bit.
RULE 41: When mseccfg.MML is set, M-mode also has read access to a Shared-Region PMP rule encoded with pmpcfg.RW=01 and set pmpcfg.L and pmpcfg.X bits.
RULE 42: When mseccfg.MML is set, a Shared-Region PMP rule encoded with pmpcfg.RW=01 and a set pmpcfg.L bit remains locked so that modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 43: When mseccfg.MML is set, M-mode, S-mode, and U-mode have only read-only access to a Shared-Region PMP rule encoded with pmpcfg.LRWX=1111.
RULE 44: When mseccfg.MML is set, a Shared-Region PMP rule encoded with pmpcfg.LRWX=1111 remains locked so that modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 45: When mseccfg.MML is set, adding an executable M-mode-only PMP rule or an executable locked Shared-Region PMP rule is not possible unless mseccfg.RLB is set.
RULE 46: When mseccfg.MML is set and mseccfg.RLB is not set, a pmpcfg write that attempts to add an executable M-mode-only PMP rule or an executable locked Shared-Region PMP rule is ignored and leaves pmpcfg unchanged.
RULE 47: When mseccfg.MML is set, setting mseccfg.RLB can temporarily lift the restriction on adding an executable M-mode-only PMP rule or an executable locked Shared-Region PMP rule, such as during the boot process.
RULE 48: When mseccfg.MML is set, executing code with M-mode privileges is possible only from a memory region with a matching M-mode-only PMP rule or a matching locked Shared-Region PMP rule with executable privileges.
RULE 49: When mseccfg.MML is set, executing code with M-mode privileges from a memory region without a matching PMP rule is denied.
RULE 50: When mseccfg.MML is set, executing code with M-mode privileges from a memory region with a matching S/U-mode-only PMP rule is denied.
RULE 51: When mseccfg.MML is not set, the pmpcfg.RW=01 encoding remains reserved for future standard use.
RULE 52: If the Smmpm extension is implemented, mseccfg.PMM enables or disables pointer masking for M-mode according to its encoded value.
RULE 53: If the Smmpm extension is not implemented, mseccfg.PMM is read-only zero.
RULE 54: The mseccfg.PMM value 00 disables pointer masking and sets PMLEN to 0.
RULE 55: The mseccfg.PMM value 01 is reserved.
RULE 56: The mseccfg.PMM value 10 enables pointer masking with PMLEN equal to XLEN - 57, which is 7 on RV64.
RULE 57: The mseccfg.PMM value 11 enables pointer masking with PMLEN equal to XLEN - 48, which is 16 on RV64.
RULE 58: When mseccfg.MLPE is 1, the Zicfilp extension is enabled in M-mode.
RULE 59: When mseccfg.MLPE is 0, the Zicfilp extension is not enabled in M-mode.
RULE 60: When mseccfg.MLPE is 0, the hart does not update the ELP state during M-mode execution, and the ELP state remains NO_LP_EXPECTED.
RULE 61: When mseccfg.MLPE is 0, the LPAD instruction operates as a no-op in M-mode.
RULE 62: When XLEN=64, mseccfgh does not exist as an alias of mseccfg.
RULE 63: Upon reset, if the Zicfilp extension is implemented, the mseccfg.MLPE field is reset to 0.
RULE 64: Upon reset, the mseccfg.MML field is set to 0 unless the platform mandates a different reset value.
RULE 65: Upon reset, the mseccfg.MMWP field is set to 0 unless the platform mandates a different reset value.
RULE 66: Upon reset, the mseccfg.RLB field is set to 0 unless the platform mandates a different reset value.
RULE 67: Upon reset, the mseccfg.USEED field MUST have a defined reset value.
RULE 68: Upon reset, the mseccfg.SSEED field MUST have a defined reset value.
RULE 69: When mseccfg.MML is set to 1 and pmpcfg.L, pmpcfg.R, pmpcfg.W, and pmpcfg.X are all 0, the region is inaccessible in M-mode and the M-mode result is an access exception.
RULE 70: When mseccfg.MML is set to 1 and pmpcfg.L, pmpcfg.R, pmpcfg.W, and pmpcfg.X are all 0, the region is inaccessible in S/U-mode and the S/U-mode result is an access exception.

RULE 73: When mseccfg.MML is set to 1, pmpcfg.L and pmpcfg.R are 0, pmpcfg.W is 1, and pmpcfg.X is 0, the region is a shared data region with read/write access in M-mode.
RULE 74: When mseccfg.MML is set to 1, pmpcfg.L and pmpcfg.R are 0, pmpcfg.W is 1, and pmpcfg.X is 0, the region is a shared data region with read-only access in S/U-mode.
RULE 75: When mseccfg.MML is set to 1, pmpcfg.L and pmpcfg.R are 0, and pmpcfg.W and pmpcfg.X are 1, the region is a shared data region with read/write access in M-mode.

REGISTER: mstatus
RULE 1: When the TW bit in mstatus is set, WRS.NTO is executed in any privilege mode other than M mode, and WRS.NTO does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause an illegal-instruction exception.
RULE 2: When executing in VS or VU mode, if the VTW bit in hstatus is set, the TW bit in mstatus is clear, and WRS.NTO does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause a virtual-instruction exception.
RULE 3: Like a load or store instruction, a CMO instruction may or may not be permitted to access a cache block based on the states of the MPRV, MPV, MPP, SUM, and MXR bits in mstatus.
RULE 4: If the Zfinx extension is implemented, the mstatus field FS is hardwired to 0.
RULE 5: If the Zfinx extension is implemented, the mstatus field FS no longer affects the trapping behavior of floating-point instructions or fcsr accesses.
RULE 6: The vector context status field mstatus.VS occupies mstatus[10:9].
RULE 7: The mstatus.VS field is shadowed in sstatus[10:9].
RULE 8: When mstatus.VS is Off, an attempt to execute any vector instruction or access any vector CSR raises an illegal-instruction exception.
RULE 9: When mstatus.VS is Initial or Clean, executing any instruction that changes vector state, including an instruction that changes a vector CSR, changes mstatus.VS to Dirty.
RULE 10: The mstatus.VS field may change from Initial or Clean to Dirty at any time, even when vector state has not changed.
RULE 11: When mstatus.VS is Dirty, mstatus.SD is 1.
RULE 12: When mstatus.VS is not Dirty, mstatus.VS makes no Dirty-state contribution to mstatus.SD.
RULE 13: The mstatus.VS field may exist even when misa.V is clear.
RULE 14: When V=1, an attempt to execute any vector instruction raises an illegal-instruction exception if either vsstatus.VS or mstatus.VS is set to Off.
RULE 15: When V=1, an attempt to access any vector CSR raises an illegal-instruction exception if either vsstatus.VS or mstatus.VS is set to Off.
RULE 16: When V=1 and neither vsstatus.VS nor mstatus.VS is set to Off, executing any instruction that changes vector state, including an instruction that changes the vector CSRs, changes both mstatus.VS and vsstatus.VS to Dirty.
RULE 17: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 18: If mstatus.VS is not Dirty, mstatus.SD is set according to the otherwise applicable mstatus.SD specifications.
RULE 19: If mstatus.FS is Off, any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 20: Any vector floating-point instruction that modifies floating-point extension state, comprising floating-point CSRs or f registers, must set mstatus.FS to Dirty.
RULE 21: If the hypervisor extension is implemented, V=1, and either vsstatus.FS or mstatus.FS is Off, any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 22: If the hypervisor extension is implemented and V=1, any vector floating-point instruction that modifies floating-point extension state, comprising floating-point CSRs or f registers, must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 23: The mstatus register is a machine-level read/write CSR.
RULE 24: The mstatus register is MXLEN bits wide.
RULE 25: The mstatus register is read/write.
RULE 26: In RV64, mstatus bits 62:43 are WPRI.
RULE 27: In RV64, mstatus bit 40 is WPRI.
RULE 28: In RV64, mstatus bits 31:25 are WPRI.
RULE 29: In RV64, mstatus bit 4 is WPRI.
RULE 30: In RV64, mstatus bit 2 is WPRI.
RULE 31: In RV64, mstatus bit 0 is WPRI.
RULE 32: The global xIE bits are located in the low-order bits of mstatus, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 33: If supervisor mode is not implemented, the SIE field in mstatus is read-only 0.
RULE 34: If supervisor mode is not implemented, the SPIE field in mstatus is read-only 0.
RULE 35: Each xPP field in mstatus is a WARL field that can hold only privilege mode x and any implemented privilege mode lower than x.
RULE 36: The MPP field in mstatus is two bits wide.
RULE 37: The SPP field in mstatus is one bit wide.
RULE 38: When a trap is taken from privilege mode y into privilege mode x, the xPIE field in mstatus is set to the value of the xIE field in mstatus.
RULE 39: When a trap is taken from privilege mode y into privilege mode x, the xIE field in mstatus is set to 0.
RULE 40: When a trap is taken from privilege mode y into privilege mode x, the xPP field in mstatus is set to y.

RULE 42: When an xRET instruction executes with the xPP field in mstatus holding privilege mode y, the privilege mode is changed to y.

RULE 45: When an xRET instruction executes with the xPP field in mstatus holding a privilege mode y where y != M, the MPRV field in mstatus is also set to 0.
RULE 46: If privilege mode x is not implemented, the corresponding xPP field in mstatus must be read-only 0.
RULE 47: M-mode software can determine whether a privilege mode is implemented by writing that privilege mode to the MPP field in mstatus and then reading MPP back.
RULE 48: The M-mode-disable-trap (MDT) field represented in mstatus or mstatush is a WARL field.
RULE 49: Upon reset, the MDT field represented in mstatus or mstatush is set to 1.
RULE 50: When an explicit CSR write sets the MDT bit in mstatus or mstatush to 1, the MIE bit in mstatus is cleared to 0.
RULE 51: On RV64, when an explicit CSR write sets mstatus.MDT to 1, mstatus.MIE is cleared to 0 regardless of the value written, if any, to mstatus.MIE by the same write.
RULE 52: An explicit CSR write can set mstatus.MIE to 1 only if the MDT bit in mstatus or mstatush is already 0 or, on RV64, the same write sets mstatus.MDT to 0.
RULE 53: When a trap is to be taken into M-mode and the MDT bit in mstatus or mstatush is currently 0, the MDT bit is set to 1.
RULE 54: When a trap is to be taken into M-mode and the MDT bit in mstatus or mstatush is currently 0, the trap is delivered as expected.
RULE 55: When a trap is to be taken into M-mode and the MDT bit in mstatus or mstatush is already 1, the trap is an unexpected trap.
RULE 56: When the Smrnmi extension is implemented, a trap caused by an RNMI is not considered an unexpected trap irrespective of the state of the MDT bit in mstatus or mstatush.
RULE 57: A trap caused by an RNMI does not set the MDT bit in mstatus or mstatush.
RULE 58: For purposes of the MDT field represented in mstatus or mstatush, a trap that occurs while executing in M-mode with mnstatus.NMIE set to 0 is an unexpected trap.
RULE 59: In the mstatus MDT handling model, when an unexpected trap occurs while the Smrnmi extension is implemented and mnstatus.NMIE is 1, the hart traps to the RNMI handler.
RULE 60: In the mstatus MDT handling model, when an unexpected trap occurs and either the Smrnmi extension is not implemented or the Smrnmi extension is implemented with mnstatus.NMIE set to 0, the hart enters a critical-error state.
RULE 61: In the mstatus MDT handling model, when an unexpected trap occurs and either the Smrnmi extension is not implemented or the Smrnmi extension is implemented with mnstatus.NMIE set to 0, the hart does not update any architectural state, including the pc.
RULE 62: In the mstatus MDT handling model, when an unexpected trap occurs and either the Smrnmi extension is not implemented or the Smrnmi extension is implemented with mnstatus.NMIE set to 0, the hart ceases execution in the critical-error state.

REGISTER: satp
RULE 1: satp is a supervisor-level read/write register at address 0x180.
RULE 2: Every S-mode instruction fetch implicitly reads the satp CSR.
RULE 3: Unless otherwise specified, an implicit read of the satp CSR returns the same value as an explicit read of the satp CSR using a CSR-access instruction in a sufficient privilege mode.
RULE 4: SUM is read-only 0 if S-mode is not supported or if satp.MODE is read-only 0.
RULE 5: When TVM=1, an attempt to read the satp CSR while executing in S-mode raises an illegal-instruction exception.
RULE 6: When TVM=1, an attempt to write the satp CSR while executing in S-mode raises an illegal-instruction exception.
RULE 7: When TVM=0, an attempt to read the satp CSR while executing in S-mode is permitted.
RULE 8: When TVM=0, an attempt to write the satp CSR while executing in S-mode is permitted.
RULE 9: When S-mode is not supported, the mstatus TVM bit that controls S-mode access to the satp CSR is read-only 0.
RULE 10: When menvcfg.PBMTE equals 1, the Svpbmt extension is available for S-mode address translation using page tables pointed to by satp.
RULE 11: When menvcfg.PBMTE equals 0, the implementation behaves as though the Svpbmt extension were not implemented for S-mode address translation using page tables pointed to by satp.
RULE 12: If the Svpbmt extension is not implemented, menvcfg.PBMTE is read-only zero for S-mode address translation using page tables pointed to by satp.
RULE 13: After changing menvcfg.PBMTE, executing an SFENCE.VMA instruction with rs1 equal to x0 and rs2 equal to x0 suffices to synchronize address-translation caches with the altered interpretation of PBMT fields in page-table entries from page tables pointed to by satp.
RULE 14: SUM is read-only 0 if satp.MODE is read-only 0.
RULE 15: A read-only-zero satp.MODE field is always Bare.
RULE 16: The satp CSR is an SXLEN-bit read/write register.
RULE 17: The satp.PPN field holds the physical page number of the root page table, equal to its supervisor physical address divided by 4 KiB.
RULE 18: The satp.MODE field selects the current address-translation scheme.
RULE 19: When SXLEN=64, satp.MODE occupies bits 63:60, has a width of 4 bits, and is WARL.
RULE 20: When SXLEN=64, satp.ASID occupies bits 59:44, has a width of 16 bits, and is WARL.
RULE 21: When SXLEN=64, satp.PPN occupies bits 43:0, has a width of 44 bits, and is WARL.
RULE 22: The satp register stores the ASID and page-table base address together so that software can change the pair atomically during a context switch.
RULE 23: When satp.MODE=Bare, supervisor virtual addresses are equal to supervisor physical addresses.
RULE 24: When satp.MODE=Bare, satp provides no additional memory protection beyond the physical memory protection scheme.
RULE 25: When SXLEN=64, software must write zero to satp bits 59:0 to select satp.MODE=Bare.
RULE 26: When SXLEN=64, all satp encodings with satp.MODE=Bare are reserved for future standard use.
RULE 27: When SXLEN=64, satp.MODE value 0 is named Bare and specifies no address translation or protection.
RULE 28: When SXLEN=64, satp.MODE values 1 through 7 are reserved for standard use.
RULE 29: When SXLEN=64, satp.MODE value 8 selects Sv39 page-based 39-bit virtual addressing.
RULE 30: When SXLEN=64, satp.MODE value 9 selects Sv48 page-based 48-bit virtual addressing.
RULE 31: When SXLEN=64, satp.MODE value 10 selects Sv57 page-based 57-bit virtual addressing.
RULE 32: When SXLEN=64, satp.MODE value 11 is named Sv64 and is reserved for page-based 64-bit virtual addressing.
RULE 33: When SXLEN=64, satp.MODE values 12 and 13 are reserved for standard use.
RULE 34: When SXLEN=64, satp.MODE settings other than Bare, Sv39, Sv48, and Sv57 are reserved for future use and may define different interpretations of the other satp fields.
RULE 35: If satp is written with an unsupported satp.MODE value, the entire write has no effect and no satp field is modified.
RULE 36: The number of implemented bits in satp.ASID is UNSPECIFIED and may be zero.
RULE 37: ASIDLEN may be determined by writing one to every bit position in satp.ASID and then reading satp to determine which satp.ASID bit positions hold one.
RULE 38: The least-significant bits of satp.ASID are implemented first.
RULE 39: If ASIDLEN is greater than zero, satp.ASID[ASIDLEN-1:0] is writable.
RULE 40: When satp.MODE=Sv32, ASIDMAX is 9.
RULE 41: When satp.MODE is Sv39, Sv48, or Sv57, ASIDMAX is 16.
RULE 42: The satp CSR is considered active when the effective privilege mode is S-mode or U-mode.
RULE 43: An execution of the address-translation algorithm may begin using a given satp value only while satp is active.
RULE 44: Translations that began while satp was active are not required to complete or terminate after satp becomes inactive unless an SFENCE.VMA instruction matching the address and ASID is executed.
RULE 45: For address translation controlled by satp, the SFENCE.VMA instruction must be used to ensure that updates to address-translation data structures are observed by subsequent implicit reads of those structures by a hart.
RULE 46: For a given virtual address and ASID, any translation since the last subsuming SFENCE.VMA might be used even if that translation used a virtual-address width different from the width currently specified by satp.MODE.
RULE 47: For a given virtual address, any global translation since the last subsuming SFENCE.VMA might be used regardless of its ASID and regardless of whether its virtual-address width differs from the width currently specified by satp.MODE.
RULE 48: An implementation must perform implicit reads only from translation data structures pointed to by the current contents of satp or by a subsequent valid translation data structure entry with V=1.
RULE 49: Changing satp.MODE from Bare to any other mode takes effect immediately without requiring execution of an SFENCE.VMA instruction.
RULE 50: Changing satp.MODE from any non-Bare mode to Bare takes effect immediately without requiring execution of an SFENCE.VMA instruction.
RULE 51: Changes to satp.ASID take effect immediately.
RULE 52: If a hart employs an address-translation cache for address translation controlled by satp, that cache must appear to be private to that hart.
RULE 53: The meaning of an ASID stored in satp.ASID is local to a hart.
RULE 54: Software may choose to use the same satp.ASID value to refer to different address spaces on different harts.
RULE 55: If satp.MODE is read-only zero so that satp is always in Bare mode, an attempt to execute an SFENCE.VMA instruction might raise an illegal-instruction exception.
RULE 56: When Sv32 is written to the MODE field of satp, supervisor and user virtual addresses are translated into supervisor physical addresses by traversing a radix-tree page table.
RULE 57: When Sv32 virtual memory mode is selected in the MODE field of satp, supervisor virtual addresses are translated into supervisor physical addresses through a two-level page table.
