INSTRUCTION: CSRRWI
RULE 1: When rd is not x0, CSRRWI atomically reads, modifies, and writes the single CSR specified by the instruction.
RULE 2: CSRRWI updates the specified CSR using an XLEN-bit value obtained by zero-extending the 5-bit unsigned immediate uimm[4:0] instead of using a value from an integer register.
RULE 3: When rd is x0, CSRRWI atomically writes the single CSR specified by the instruction.
RULE 4: When rd is x0, CSRRWI does not read the specified CSR.
RULE 5: When rd is x0, CSRRWI does not cause any side effects that might occur on a CSR read.
RULE 6: CSRRWI causes side effects for all fields within the written CSR that have side effects when written.
RULE 7: CSRRWI causes the side effects that occur as a consequence of writing the specified CSR.
RULE 8: When rd is not x0, CSRRWI causes the side effects that occur as a consequence of reading the specified CSR.
RULE 9: Under the RVWMO syntactic-dependency source-register definition, for a register r other than x0, if CSRRWI is a CSR instruction, the csr field of the CSRRWI opcode is set to r, and rd is not set to x0, then r is a source register for CSRRWI.

INSTRUCTION: FCVT.W.D
RULE 1: FCVT.W.D converts a double-precision floating-point number in floating-point register rs1 to a signed 32-bit integer in integer register rd.
RULE 2: FCVT.W.D rounds according to the rm field.
RULE 3: For RV64, FCVT.W.D sign-extends the 32-bit result.
RULE 4: As an FCVT.int.D form, FCVT.W.D has the same range of valid inputs as FCVT.int.S.
RULE 5: As an FCVT.int.D form, FCVT.W.D has the same behavior for invalid inputs as FCVT.int.S.
RULE 6: For a given input operand, FCVT.W.D raises the same floating-point exception flags as FCVTMOD.W.D raises for that same input operand.

INSTRUCTION: SFENCE.VMA
RULE 1: SFENCE.VMA orders stores.
RULE 2: When TVM=1, an attempt to execute an SFENCE.VMA instruction while executing in S-mode raises an illegal-instruction exception.
RULE 3: When TVM=0, an attempt to execute an SFENCE.VMA instruction while executing in S-mode is permitted.
RULE 4: After menvcfg.PBMTE is changed, executing SFENCE.VMA with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields.
RULE 5: After menvcfg.ADUE is changed, executing SFENCE.VMA with rs1 = x0 and rs2 = x0 suffices to synchronize address-translation caches with respect to the altered interpretation of page-table entries' A/D bits.
RULE 6: If page-based virtual memory is not implemented, no SFENCE.VMA instruction is needed because memory accesses check the PMP settings synchronously.
RULE 7: The SFENCE.VMA instruction must be used to ensure that updates to the address translation data structures are observed by subsequent implicit reads to those structures by a hart.
RULE 8: Executing SFENCE.VMA guarantees that any previous stores already visible to the current RISC-V hart are ordered before certain implicit references by subsequent instructions in that hart to memory-management data structures.
RULE 9: SFENCE.VMA invalidates entries in the address-translation cache associated with a hart.
RULE 10: SFENCE.VMA orders only the local hart's implicit references to memory-management data structures.
RULE 11: If rs1 is x0 and rs2 is x0, SFENCE.VMA orders all reads and writes made to any level of the page tables for all address spaces.
RULE 12: If rs1 is x0 and rs2 is x0, SFENCE.VMA invalidates all address-translation cache entries for all address spaces.
RULE 13: If rs1 is x0 and rs2 is not x0, SFENCE.VMA orders all reads and writes made to any level of the page tables only for the address space identified by integer register rs2.
RULE 14: If rs1 is x0 and rs2 is not x0, SFENCE.VMA invalidates all address-translation cache entries matching the address space identified by integer register rs2 except for entries containing global mappings.
RULE 15: If rs1 is not x0 and rs2 is x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 16: If rs1 is not x0 and rs2 is x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 17: If rs1 is not x0 and rs2 is not x0, SFENCE.VMA orders only reads and writes made to leaf page table entries corresponding to the virtual address in rs1 for the address space identified by integer register rs2.
RULE 18: If rs1 is not x0 and rs2 is not x0, SFENCE.VMA invalidates all address-translation cache entries that contain leaf page table entries corresponding to the virtual address in rs1 and that match the address space identified by integer register rs2 except for entries containing global mappings.
RULE 19: If the value held in rs1 is not a valid virtual address, SFENCE.VMA has no effect.
RULE 20: If the value held in rs1 is not a valid virtual address, SFENCE.VMA raises no exception.
RULE 21: When rs2 is not x0, the bits SXLEN-1:ASIDMAX of the value held in rs2 for SFENCE.VMA are reserved for future standard use.
RULE 22: Until their use is defined by a standard extension, current implementations should ignore bits SXLEN-1:ASIDMAX of the rs2 value for SFENCE.VMA when rs2 is not x0.
RULE 23: When rs2 is not x0 and ASIDLEN is less than ASIDMAX, an implementation of SFENCE.VMA shall ignore bits ASIDMAX-1:ASIDLEN of the value held in rs2.
RULE 24: SFENCE.VMA orders prior explicit accesses before subsequent implicit accesses.
RULE 25: Implicit accesses ordered by SFENCE.VMA are ordered before their associated explicit accesses.
RULE 26: Changes to the sstatus SUM field take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 27: Changes to the sstatus MXR field take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 28: Changing satp.MODE from Bare to another mode and vice versa takes effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 29: Changes to satp.ASID take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 30: When an SFENCE.VMA instruction is executed with rs2 != x0, global mappings need not be flushed from local address-translation caches.
RULE 31: After writes to memory locations, an SFENCE.VMA instruction must be executed to ensure that subsequent implicit reads of the same memory locations observe those writes.
RULE 32: When an OS needs to issue SFENCE.VMA instruction(s) covering all 4 KiB regions within the range of an update, a single SFENCE.VMA with rs1=x0 can be used to cover all 4 KiB regions within the range of the update.
RULE 33: When an OS needs to issue SFENCE.VMA instruction(s) covering all 4 KiB regions within the range of an update, multiple SFENCE.VMA instructions with rs1 != x0 can be used to cover all 4 KiB regions within the range of the update.
RULE 34: For the same values of rs1 and rs2, SFENCE.VMA invalidates the same address-translation cache entries that SINVAL.VMA invalidates.
RULE 35: When SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR are executed in order but not necessarily consecutively by a single hart, their combined effect is the same as a hypothetical SFENCE.VMA whose rs1 and rs2 values equal those used in the SINVAL.VMA.
RULE 36: When SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR are executed in order but not necessarily consecutively by a single hart and are equivalent to a hypothetical SFENCE.VMA whose rs1 and rs2 values equal those used in the SINVAL.VMA, reads and writes prior to the SFENCE.W.INVAL are considered prior to the hypothetical SFENCE.VMA.
RULE 37: When SFENCE.W.INVAL, SINVAL.VMA, and SFENCE.INVAL.IR are executed in order but not necessarily consecutively by a single hart and are equivalent to a hypothetical SFENCE.VMA whose rs1 and rs2 values equal those used in the SINVAL.VMA, reads and writes following the SFENCE.INVAL.IR are considered subsequent to the hypothetical SFENCE.VMA.
RULE 38: SFENCE.VMA requires the same permissions as SINVAL.VMA.
RULE 39: SFENCE.VMA raises the same exceptions as SINVAL.VMA.
RULE 40: An attempt to execute SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 41: An attempt to execute SFENCE.VMA in S-mode or HS-mode when mstatus.TVM=1 raises an illegal-instruction exception.
RULE 42: An attempt to execute SFENCE.VMA in VU-mode raises a virtual-instruction exception.
RULE 43: When hstatus.VTVM=1, an attempt to execute SFENCE.VMA in VS-mode raises a virtual-instruction exception.
RULE 44: When VTVM=1, an attempt in VS-mode to execute SFENCE.VMA raises a virtual-instruction exception.
RULE 45: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp.
RULE 46: For SFENCE.VMA when V=0, the current satp is the HS-level satp, so SFENCE.VMA applies only to the memory-management data structures controlled by the HS-level satp.
RULE 47: For SFENCE.VMA when V=1, the current satp is vsatp, so SFENCE.VMA applies only to the memory-management data structures controlled by vsatp.
RULE 48: When V=0, SFENCE.VMA orders stores only to the HS-level address-translation structures with subsequent HS-level address translations.
RULE 49: When V=1, SFENCE.VMA orders stores only to the VS-level address-translation structures with subsequent VS-stage address translations for the same virtual machine, and this ordering applies only when hgatp.VMID is the same as when the SFENCE.VMA executed.
RULE 50: When V=1, in VS-mode, an attempt to execute an SFENCE.VMA instruction when hstatus.VTVM=1 raises a virtual-instruction exception with code 22.
RULE 51: If an SFENCE.VMA instruction causes a virtual-instruction trap, mtval or stval is written the same as for an illegal-instruction trap.
RULE 52: Pointer masking is not applied to the address used by an SFENCE.VMA instruction.

INSTRUCTION: VLE32FF.V
RULE 1: VLE32FF.V executes as a regular load except that VLE32FF.V takes a trap caused by a synchronous exception only on element 0.
RULE 2: If element 0 of VLE32FF.V raises an exception, vl is not modified and the trap is taken.
RULE 3: If an element with index greater than 0 of VLE32FF.V raises an exception, the corresponding trap is not taken and vl is reduced to the index of that element.
RULE 4: VLE32FF.V may update active destination elements past the element that causes trimming of vl but not past the original vl.
RULE 5: VLE32FF.V can access non-idempotent memory locations only when the corresponding element load operation is known not to be restarted due to a trap or vector-length trimming.
RULE 6: When VLE32FF.V raises no exception and vstart equals 0 and vl is greater than 0, VLE32FF.V must process at least one element.
RULE 7: When VLE32FF.V takes a trap due to an interrupt, implementations should not reduce vl and should instead set a vstart value.
RULE 8: When VLE32FF.V would trigger a debug data-watchpoint trap on an element after the first element, implementations should not reduce vl and should instead trigger the debug trap so that the event is not lost.
