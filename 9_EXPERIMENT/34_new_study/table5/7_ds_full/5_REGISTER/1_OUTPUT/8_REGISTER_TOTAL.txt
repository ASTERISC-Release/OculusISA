REGISTER: mseccfg
NUMBER: 0x747
MODE: M-mode
WIDTH: 64
FIELDS: 33..32=PMM, 10..10=MLPE, 9..9=SSEED, 8..8=USEED, 2..2=RLB, 1..1=MMWP, 0..0=MML
EXTENSIONS: Smepmp, Smmpm, Zicfilp, Zkr
RULE 1: If a U-mode access to the seed CSR occurs while mseccfg.USEED is clear, or an S-mode or HS-mode access to the seed CSR occurs while mseccfg.SSEED is clear, then the access raises an illegal-instruction exception and mcause is set to the illegal-instruction cause; if the applicable mseccfg field is set, the seed CSR access is permitted.
RULE 2: Software may discover whether access to the seed CSR can be enabled in U and S modes by writing 1 to the [s,u]seed fields of the mseccfg CSR and reading back the result.
RULE 3: mseccfg has privilege MRW.
RULE 4: When mseccfg.USEED is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 5: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed.
RULE 6: When mseccfg.USEED is 1, seed CSR accesses from U-mode other than read-write accesses raise an illegal-instruction exception.
RULE 7: When mseccfg.SSEED is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 8: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-/HS-mode is allowed.
RULE 9: When mseccfg.SSEED is 1, seed CSR accesses from S-/HS-mode other than read-write accesses raise an illegal-instruction exception.
RULE 10: In M-mode, the seed CSR is always available as normal with a CSR read-write instruction regardless of the mseccfg.SSEED and mseccfg.USEED access-control bits.
RULE 11: When mseccfg.SSEED is 0, any access to the seed CSR from VS or VU mode raises an illegal-instruction exception.
RULE 12: When mseccfg.SSEED is 1, seed CSR access conditions from VS or VU mode other than read-write access raise an illegal-instruction exception.
RULE 13: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any rule or entry including disabled entries, mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 14: mseccfg.MMWP is a sticky bit that cannot be unset once set until a PMP reset.
RULE 15: When mseccfg.MMWP is set, the default PMP policy for M-mode when accessing memory regions without a matching PMP rule is denied instead of ignored.
RULE 16: mseccfg.MML is a sticky bit that cannot be unset once set until a PMP reset.
RULE 17: When mseccfg.MML is set and pmpcfg.L is set, pmpcfg.L marks a rule as M-mode-only instead of marking the rule as locked and enforced in all modes.
RULE 18: When mseccfg.MML=1, a PMP entry with pmpcfg.L=0 is S/U-mode-only: if an M-mode access matches that entry, the entry does not apply to the M-mode access, while an S/U-mode access matching it is checked against its R/W/X permissions and a permission violation raises the corresponding instruction/load/store access-fault exception.
RULE 19: If mseccfg.MML is 1, then a pmpcfg entry with RW=01 encodes a Shared-Region and is used as such in PMP permission checks; if mseccfg.MML is 0, then the same RW=01 encoding remains reserved and does not encode a Shared-Region.
RULE 20: If mseccfg.MML=1 and a pmpcfg byte is written as L=1, R=1, W=1, X=1, then that byte reads back as 1111 and its PMP entry is interpreted as a Shared-Region; if mseccfg.MML=0, the same 1111 encoding is not a Shared-Region and is interpreted as a normal locked RWX PMP entry.
RULE 21: When mseccfg.MML is set, an M-mode-only rule is enforced on Machine mode and denied in Supervisor or User mode.
RULE 22: When mseccfg.MML is set, an M-mode-only rule remains locked so that further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 23: If mseccfg.MML is set and a Machine-mode access matches an S/U-mode-only rule, then the access is denied and raises an instruction access-fault, load access-fault, or store/AMO access-fault exception according to the access type, while matching Supervisor- and User-mode accesses are enforced by that rule.
RULE 24: When mseccfg.MML is set, a Shared-Region rule with pmpcfg.L not set can be used for sharing data between M-mode and S/U-mode and is not executable.
RULE 25: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L not set, M-mode has read/write access to the region.
RULE 26: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L not set and pmpcfg.X is not set, S/U-mode has read access to the region.
RULE 27: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L not set and pmpcfg.X is set, S/U-mode has read/write access to the region.
RULE 28: If mseccfg.MML=1 and a PMP entry matching an address has pmpcfg.L=1 with R=0, W=0, X=1, then instruction fetches from that address are allowed in both M-mode and S/U-mode, and any store to that address is denied and raises a store/AMO access fault.
RULE 29: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L set, both M-mode and S/U-mode have execute access on the region.
RULE 30: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L set and pmpcfg.X is set, M-mode also has read access on the region.
RULE 31: When mseccfg.MML is set and a Shared-Region rule has pmpcfg.L set, the rule remains locked so that further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 32: When mseccfg.MML is set, the pmpcfg.LRWX=1111 encoding can be used for sharing data between M-mode and S/U-mode with both modes having only read-only access to the region.
RULE 33: When mseccfg.MML is set and the pmpcfg.LRWX=1111 encoding is used for a Shared-Region rule, the rule remains locked so that further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 34: When mseccfg.MML is set, adding a rule with executable privileges that either is M-mode-only or a locked Shared-Region is not possible and such pmpcfg writes are ignored, leaving pmpcfg unchanged.
RULE 35: If mseccfg.MML is 1 and mseccfg.RLB is set to 1, then an attempted PMP rule addition with executable privileges that is either M-mode-only or a locked Shared-Region is allowed to take effect and the new rule is observable in pmpcfg/pmpaddr readback; with mseccfg.MML still 1, if mseccfg.RLB is 0, that restriction is not lifted, so the same attempted addition does not take effect and the pmpcfg/pmpaddr readback remains unchanged.
RULE 36: When mseccfg.MML is set, executing code with Machine mode privileges is only possible from memory regions with a matching M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 37: When mseccfg.MML is set, executing code with Machine mode privileges from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 38: If Smmpm is not implemented, mseccfg.PMM is read-only zero.
RULE 39: If mseccfg.MLPE is 1, then M-mode execution enforces Zicfilp landing-pad checks, so an M-mode indirect call or jump to a target that does not satisfy the Zicfilp landing-pad requirement raises a software-check exception and sets mcause to 18; if mseccfg.MLPE is 0, those M-mode Zicfilp checks are disabled and the same transfer does not raise that software-check exception.
RULE 40: If mseccfg.MLPE is 0, then Zicfilp landing-pad enforcement is disabled in M-mode, so an M-mode indirect control-flow transfer to a non-landing-pad target does not raise the Zicfilp software-check exception.
RULE 41: When mseccfg.MLPE is 0, in M-mode the hart does not update the ELP state and it remains as NO_LP_EXPECTED.
RULE 42: When mseccfg.MLPE is 0, in M-mode the LPAD instruction operates as a no-op.
RULE 43: When XLEN=64, the mseccfg high-alias register mseccfgh does not exist.
RULE 44: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=0, and X=0, the M-mode result is an inaccessible region with an access exception.
RULE 45: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=0, and X=0, the S/U-mode result is an inaccessible region with an access exception.
RULE 46: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=0, and X=1, the M-mode result is an access exception.
RULE 47: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=0, and X=1, the S/U-mode result is an execute-only region.
RULE 48: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=1, and X=0, the M-mode result is a shared data region that is read/write on M-mode and read-only on S/U-mode.
RULE 49: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=1, and X=0, the S/U-mode result is a shared data region that is read/write on M-mode and read-only on S/U-mode.
RULE 50: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=1, and X=1, the M-mode result is a shared data region that is read/write for both M-mode and S/U-mode.
RULE 51: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=0, W=1, and X=1, the S/U-mode result is a shared data region that is read/write for both M-mode and S/U-mode.
RULE 52: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=0, and X=0, the M-mode result is an access exception.
RULE 53: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=0, and X=0, the S/U-mode result is a read-only region.
RULE 54: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=0, and X=1, the M-mode result is an access exception.
RULE 55: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=0, and X=1, the S/U-mode result is a read/execute region.
RULE 56: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=1, and X=0, the M-mode result is an access exception.
RULE 57: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=1, and X=0, the S/U-mode result is a read/write region.
RULE 58: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=1, and X=1, the M-mode result is an access exception.
RULE 59: When mseccfg.MML is set to 1 and pmpcfg has L=0, R=1, W=1, and X=1, the S/U-mode result is a read/write/execute region.
RULE 60: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=0, and X=0, the M-mode result is a locked inaccessible region with an access exception.
RULE 61: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=0, and X=0, the S/U-mode result is a locked inaccessible region with an access exception.
RULE 62: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=0, and X=1, the M-mode result is a locked execute-only region.
RULE 63: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=0, and X=1, the S/U-mode result is an access exception.
RULE 64: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=1, and X=0, the M-mode result is a locked shared code region that is execute-only on both M-mode and S/U-mode.
RULE 65: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=1, and X=0, the S/U-mode result is a locked shared code region that is execute-only on both M-mode and S/U-mode.
RULE 66: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=1, and X=1, the M-mode result is a locked shared code region that is execute-only on S/U-mode and read/execute on M-mode.
RULE 67: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=0, W=1, and X=1, the S/U-mode result is a locked shared code region that is execute-only on S/U-mode and read/execute on M-mode.
RULE 68: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=0, and X=0, the M-mode result is a locked read-only region.
RULE 69: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=0, and X=0, the S/U-mode result is an access exception.
RULE 70: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=0, and X=1, the M-mode result is a locked read/execute region.
RULE 71: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=0, and X=1, the S/U-mode result is an access exception.
RULE 72: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=1, and X=0, the M-mode result is a locked read/write region.
RULE 73: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=1, and X=0, the S/U-mode result is an access exception.
RULE 74: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=1, and X=1, the M-mode result is a locked shared data region that is read-only on both M-mode and S/U-mode.
RULE 75: When mseccfg.MML is set to 1 and pmpcfg has L=1, R=1, W=1, and X=1, the S/U-mode result is a locked shared data region that is read-only on both M-mode and S/U-mode.
RULE 76: If S-mode is implemented and the current privilege mode is M, then xLPE for PMP checks is mseccfg.MLPE: when mseccfg.MLPE=1, an M-mode access that violates the permissions of a matching locked PMP entry raises the corresponding instruction, load, or store/AMO access-fault exception, and when mseccfg.MLPE=0, that locked entry is not enforced for M-mode and the access does not raise a PMP access-fault exception solely due to that violation.
RULE 77: For privilege mode M, xLPE is the value read from mseccfg.MLPE; if mseccfg.MLPE reads 0, Zicfilp forward-edge CFI using landing pads is disabled in M-mode, and if mseccfg.MLPE reads 1, Zicfilp forward-edge CFI using landing pads is enabled in M-mode.
RULE 78: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 79: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 80: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 81: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 82: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 83: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 84: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 85: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 86: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
NUMBER: 0x300
MODE: M-mode
WIDTH: MXLEN
FIELDS: 63..63=SD, 42..42=MDT, 41..41=MPELP, 39..39=MPV, 38..38=GVA, 37..37=MBE, 36..36=SBE, 35..34=SXL, 33..32=UXL, 23..23=SPELP, 22..22=TSR, 21..21=TW, 20..20=TVM, 19..19=MXR, 18..18=SUM, 17..17=MPRV, 16..15=XS, 14..13=FS, 12..11=MPP, 10..9=VS, 8..8=SPP, 7..7=MPIE, 6..6=UBE, 5..5=SPIE, 3..3=MIE, 1..1=SIE
EXTENSIONS: F, H, Smdbltrp, Smrnmi, Ssdbltrp, V, Zfinx, Zicfilp
RULE 1: If mstatus.TW is set and WRS.NTO is executed in any privilege mode other than M mode and does not complete within the implementation-specific bounded time limit, then WRS.NTO raises an illegal-instruction exception.
RULE 2: The vector context status field VS is added to mstatus bits [10:9].
RULE 3: The mstatus.VS field is shadowed in sstatus bits [10:9].
RULE 4: An attempt to execute any vector instruction raises an illegal-instruction exception when mstatus.VS is set to Off.
RULE 5: An attempt to access the vector CSRs raises an illegal-instruction exception when mstatus.VS is set to Off.
RULE 6: When mstatus.VS is set to Initial, executing any instruction that changes vector state, including the vector CSRs, will change mstatus.VS to Dirty.
RULE 7: When mstatus.VS is set to Clean, executing any instruction that changes vector state, including the vector CSRs, will change mstatus.VS to Dirty.
RULE 8: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 9: When V=1 and either mstatus.VS or vsstatus.VS is set to Off, an attempt to execute any vector instruction raises an illegal-instruction exception.
RULE 10: When V=1 and either mstatus.VS or vsstatus.VS is set to Off, an attempt to access the vector CSRs raises an illegal-instruction exception.
RULE 11: When V=1 and neither vsstatus.VS nor mstatus.VS is set to Off, executing any instruction that changes vector state, including the vector CSRs, will change both mstatus.VS and vsstatus.VS to Dirty.
RULE 12: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 13: If the floating-point unit status field mstatus.FS is Off, then any attempt to execute a vector floating-point instruction raises an illegal-instruction exception.
RULE 14: Any vector floating-point instruction that modifies any floating-point extension state (i.e., floating-point CSRs or f registers) must set mstatus.FS to Dirty.
RULE 15: If the hypervisor extension is implemented and V=1, then for a vector floating-point instruction both mstatus.FS and vsstatus.FS apply, so if either field is Off, executing that instruction raises an illegal-instruction exception.
RULE 16: If vsstatus.FS or mstatus.FS is Off, then any attempt to execute a vector floating-point instruction raises an illegal-instruction exception.
RULE 17: Any vector floating-point instruction that modifies any floating-point extension state (i.e., floating-point CSRs or f registers) must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 18: In the listing of currently allocated RISC-V machine-level CSR addresses under Machine Trap Setup, mstatus has privilege MRW.
RULE 19: If software writes mstatus, then the write does not raise an illegal-instruction exception and a subsequent read of mstatus returns an MXLEN-bit value in which each writable bit reflects the value written; if software reads mstatus, then the read returns an MXLEN-bit value.
RULE 20: The global xIE bits in mstatus can be atomically set or cleared with a single CSR instruction because they are located in the low-order bits of mstatus.
RULE 21: For each privilege mode x, mstatus.xPP can hold only privilege mode x and any implemented privilege mode lower than x.
RULE 22: If mstatus is written and then read, the mstatus.MPP readback is exactly the two-bit field mstatus[12:11] and therefore is in the range 0–3; any observed MPP value outside 0–3 would mean the field was not limited to those two bits.
RULE 23: mstatus.SPP is one bit wide.
RULE 24: When a trap is taken from privilege mode y into privilege mode x, mstatus.xPIE is set to the value of mstatus.xIE.
RULE 25: When a trap is taken from privilege mode y into privilege mode x, mstatus.xIE is set to 0.
RULE 26: When a trap is taken from privilege mode y into privilege mode x, mstatus.xPP is set to y.
RULE 27: When executing an xRET instruction with mstatus.xPP holding value y, mstatus.xIE is set to mstatus.xPIE.
RULE 28: When executing an xRET instruction with mstatus.xPP holding value y, the privilege mode is changed to y.
RULE 29: When executing an xRET instruction with mstatus.xPP holding value y, mstatus.xPIE is set to 1.
RULE 30: When executing an xRET instruction with mstatus.xPP holding value y, mstatus.xPP is set to the least-privileged supported mode, which is U if U-mode is implemented and otherwise M.
RULE 31: When executing an xRET instruction with mstatus.xPP holding value y and y != M, mstatus.MPRV is set to 0.
RULE 32: M-mode software can determine whether a privilege mode is implemented by writing that privilege mode to mstatus.MPP and reading mstatus.MPP back.
RULE 33: When an explicit CSR write sets the MDT bit to 1, the mstatus MIE bit is cleared to 0.
RULE 34: For RV64, when an explicit CSR write sets the MDT bit to 1, the mstatus MIE bit is cleared to 0 regardless of the value written, if any, to the MIE bit by the same write.
RULE 35: When a trap is to be taken into M-mode and the MDT bit that constrains the mstatus MIE bit is currently 0, that MDT bit is then set to 1, and the trap is delivered as expected.
RULE 36: The MRET instruction, when executed in M-mode, sets the MDT bit that constrains the mstatus MIE bit to 0.
RULE 37: The SRET instruction, when executed in M-mode, sets the MDT bit that constrains the mstatus MIE bit to 0.
RULE 38: When MXLEN=64 and S-mode is supported, a read of mstatus.SXL returns the encoding of the current SXLEN; if software writes an unsupported or reserved SXL encoding, the write does not raise an illegal-instruction exception solely because of that SXL value and a subsequent read of mstatus.SXL returns a legal encoding of the current SXLEN.
RULE 39: If MXLEN=64 and U-mode is supported, then a read of mstatus.UXL returns a WARL-legal encoding of the current UXLEN, and a write of an unsupported or illegal UXL value is legalized so that a subsequent read returns a supported legal UXL encoding.
RULE 40: If S-mode is implemented, the set of legal values of mstatus.UXL excludes those that would cause UXLEN to be greater than SXLEN.
RULE 41: When the MPRV bit of mstatus is 1, endianness is applied as though the current privilege mode were set to the privilege mode specified by the MPP field of mstatus.
RULE 42: If an MRET or SRET instruction changes the privilege mode to a mode less privileged than M, it also sets the MPRV bit of mstatus to 0.
RULE 43: The SUM bit of mstatus is read-only 0 if S-mode is not supported or if satp.MODE is read-only 0.
RULE 44: The MXR and SUM mechanisms of mstatus have no impact on whether access-fault exceptions are raised due to PMAs or PMP.
RULE 45: If a multi-byte data access other than an instruction fetch is performed in M-mode, then mstatus.MBE=0 makes the access little-endian and mstatus.MBE=1 makes it big-endian; if performed in S-mode use mstatus.SBE, and if performed in U-mode use mstatus.UBE, with the same 0/1 mapping, observable in the loaded destination register or the stored memory bytes.
RULE 46: When mstatus.MPRV=0 and mstatus.MBE=0, non-instruction-fetch memory accesses made from M-mode are little-endian.
RULE 47: When mstatus.MPRV=0 and mstatus.MBE=1, non-instruction-fetch memory accesses made from M-mode are big-endian.
RULE 48: If S-mode is supported and mstatus.SBE=0, explicit load and store memory accesses made from S-mode are little-endian.
RULE 49: If S-mode is supported and mstatus.SBE=1, explicit load and store memory accesses made from S-mode are big-endian.
RULE 50: If U-mode is supported and mstatus.UBE=0, explicit load and store memory accesses made from U-mode are little-endian.
RULE 51: If U-mode is supported and mstatus.UBE=1, explicit load and store memory accesses made from U-mode are big-endian.
RULE 52: An implementation supports only little-endian memory accesses if mstatus.MBE, mstatus.SBE, and mstatus.UBE are all read-only 0.
RULE 53: An implementation supports only big-endian memory accesses aside from instruction fetches if mstatus.MBE is read-only 1, mstatus.SBE is read-only 1 when S-mode is supported, and mstatus.UBE is read-only 1 when U-mode is supported.
RULE 54: When the TVM bit in mstatus is 1 and an attempt is made to read the satp CSR while executing in S-mode, that attempt will raise an illegal-instruction exception.
RULE 55: When the TVM bit in mstatus is 1 and an attempt is made to write the satp CSR while executing in S-mode, that attempt will raise an illegal-instruction exception.
RULE 56: When the TVM bit in mstatus is 1 and an attempt is made to execute an SFENCE.VMA instruction while executing in S-mode, that attempt will raise an illegal-instruction exception.
RULE 57: When the TVM bit in mstatus is 1 and an attempt is made to execute a SINVAL.VMA instruction while executing in S-mode, that attempt will raise an illegal-instruction exception.
RULE 58: When the TVM bit in mstatus is 0, reading the satp CSR in S-mode is permitted.
RULE 59: When the TVM bit in mstatus is 0, writing the satp CSR in S-mode is permitted.
