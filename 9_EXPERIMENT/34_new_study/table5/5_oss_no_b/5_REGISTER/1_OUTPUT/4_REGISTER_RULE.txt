REGISTER: mseccfg
RULE 1: Software may discover if access to the seed CSR can be enabled in U and S mode by writing a 1 to the [s,u]seed fields of mseccfg and reading back the result.
RULE 2: The CSR located at address 0x747 is named mseccfg, is a machine-mode read-write register, and provides machine security configuration.
RULE 3: The CSR located at address 0x757 is named mseccfgh, is a machine-mode read-write register, and supplies the upper 32 bits of mseccfg.
RULE 4: When mseccfg.USEED is 0, any access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 5: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed and all other types of accesses raise an illegal-instruction exception.
RULE 6: If the Zkr extension or U-mode is not implemented, the USEED field in mseccfg is read-only zero.
RULE 7: When mseccfg.SSEED is 0, any access to the seed CSR from S-mode or HS-mode raises an illegal-instruction exception.
RULE 8: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-mode or HS-mode is allowed and all other types of accesses raise an illegal-instruction exception.
RULE 9: If the Zkr extension or S-mode is not implemented, the SSEED field in mseccfg is read-only zero.
RULE 10: In M-mode, the seed CSR is always available as a normal read-write CSR instruction; a read-only access to the seed CSR raises an illegal-instruction exception regardless of mseccfg bits.
RULE 11: In U-mode with mseccfg.USEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 12: In U-mode with mseccfg.USEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 13: In S-/HS-mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 14: In S-/HS-mode with mseccfg.SSEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 15: In VS-/VU-mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 16: In VS-/VU-mode with mseccfg.SSEED = 1, a read-write seed CSR access raises a virtual-instruction exception while all other access types raise an illegal-instruction exception.
RULE 17: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 18: When mseccfg.RLB is 0 and any pmpcfg.L bit is 1 in any rule or entry (including disabled entries), mseccfg.RLB remains 0 and further writes to mseccfg.RLB are ignored until a PMP reset.
RULE 19: mseccfg.MMWP is a WARL field and a sticky bit, meaning that once mseccfg.MMWP is set it cannot be cleared until a PMP reset.
RULE 20: When mseccfg.MMWP is set, the default PMP policy for Machine mode on memory accesses that lack a matching PMP rule changes from ignored to denied.
RULE 21: mseccfg.MML is a WARL field and a sticky bit, meaning that once mseccfg.MML is set it cannot be cleared until a PMP reset.
RULE 22: When mseccfg.MML is set, the meaning of pmpcfg.L changes so that a set pmpcfg.L marks a rule as M-mode-only and a cleared pmpcfg.L marks a rule as S/U-mode-only, and the previously reserved encoding pmpcfg.RW=01 and the encoding pmpcfg.LRWX=1111 denote a Shared-Region.
RULE 23: When mseccfg.MML is set, an M-mode-only PMP rule is enforced in Machine mode, denied in Supervisor and User modes, and remains locked against further modifications until a PMP reset unless mseccfg.RLB is set.
RULE 24: When mseccfg.MML is set, an S/U-mode-only PMP rule is enforced in Supervisor and User modes and denied in Machine mode.
RULE 25: When mseccfg.MML is set, a Shared-Region PMP rule with pmpcfg.L clear is non-executable; Machine mode has read/write access, and Supervisor/User mode has read-only access if pmpcfg.X is clear or read/write access if pmpcfg.X is set.
RULE 26: When mseccfg.MML is set, a Shared-Region PMP rule with pmpcfg.L set is used for code sharing, is non-writable, provides execute access to both Machine and Supervisor/User modes, gives Machine mode additional read access if pmpcfg.X is set, and remains locked unless mseccfg.RLB is set.
RULE 27: When mseccfg.MML is set, a PMP rule encoded as pmpcfg.LRWX=1111 denotes a Shared-Region for data sharing where both Machine and Supervisor/User modes have read-only access, and the rule remains locked unless mseccfg.RLB is set.
RULE 28: When mseccfg.MML is set, attempts to write a PMP rule with executable privileges that would be M-mode-only or a locked Shared-Region are ignored and leave pmpcfg unchanged, unless mseccfg.RLB is set which can temporarily lift the restriction.
RULE 29: When mseccfg.MML is set, execution of Machine-mode code is permitted only from regions governed by a matching M-mode-only PMP rule or a locked Shared-Region rule with executable privileges; execution from regions without such a rule or governed by an S/U-mode-only rule is denied.
RULE 30: When mseccfg.MML is not set, the encoding pmpcfg.RW=01 remains reserved for future standard use.
RULE 31: When mseccfg.PMM = 00, pointer masking is disabled (PMLEN = 0).
RULE 32: When mseccfg.PMM = 10, pointer masking is enabled with PMLEN = XLEN − 57 (PMLEN = 7 on RV64).
RULE 33: When mseccfg.PMM = 11, pointer masking is enabled with PMLEN = XLEN − 48 (PMLEN = 16 on RV64).
RULE 34: When the MLPE field in mseccfg is 1, the Zicfilp extension is enabled in Machine mode.
RULE 35: When the MLPE field in mseccfg is 0, the Zicfilp extension is not enabled in Machine mode, the hart does not update the ELP state (it remains NO_LP_EXPECTED), and the LPAD instruction operates as a no-op.
RULE 36: If the Zicfilp extension is implemented, the mseccfg.MLPE field is reset to 0.
RULE 37: The mseccfg.MML field is set to 0 unless the platform mandates a different reset value.
RULE 38: The mseccfg.MMWP field is set to 0 unless the platform mandates a different reset value.
RULE 39: The mseccfg.RLB field is set to 0 unless the platform mandates a different reset value.
RULE 40: Physical memory protection rules that depend on the mseccfg.MML field are applied only when the mseccfg.MML field is set to 1.
RULE 41: When mseccfg.MML is 1 and the pmpcfg L, R, W, and X bits are 0, 0, 0, and 0 respectively, the region is inaccessible and an Access Exception is generated in both M-mode and S/U mode.
RULE 42: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=0, W=0, X=1, an Access Exception is generated in M-mode and the region is Execute-only in S/U mode.
RULE 43: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=0, W=1, X=0, the region is a shared data region that permits read/write access in M-mode and read-only access in S/U mode.
RULE 44: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=0, W=1, X=1, the region is a shared data region that permits read/write access in both M-mode and S/U mode.
RULE 45: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=1, W=0, X=0, an Access Exception is generated in M-mode and the region is read-only in S/U mode.
RULE 46: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=1, W=0, X=1, an Access Exception is generated in M-mode and the region is read/execute in S/U mode.
RULE 47: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=1, W=1, X=0, an Access Exception is generated in M-mode and the region is read/write in S/U mode.
RULE 48: When mseccfg.MML is 1 and the pmpcfg bits are L=0, R=1, W=1, X=1, an Access Exception is generated in M-mode and the region is read/write/execute in S/U mode.
RULE 49: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=0, W=0, X=0, the region is a locked inaccessible region that generates an Access Exception in both M-mode and S/U mode.
RULE 50: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=0, W=0, X=1, the region is a locked Execute-only region that generates an Access Exception in S/U mode and a locked Execute-only region in M-mode.
RULE 51: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=0, W=1, X=0, the region is a locked shared code region that permits execute-only access in both M-mode and S/U mode.
RULE 52: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=0, W=1, X=1, the region is a locked shared code region that permits execute-only access in S/U mode and read/execute access in M-mode.
RULE 53: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=1, W=0, X=0, the region is a locked read-only region that generates an Access Exception in S/U mode and is read-only in M-mode.
RULE 54: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=1, W=0, X=1, the region is a locked read/execute region that generates an Access Exception in S/U mode and is read/execute in M-mode.
RULE 55: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=1, W=1, X=0, the region is a locked read/write region that generates an Access Exception in S/U mode and is read/write in M-mode.
RULE 56: When mseccfg.MML is 1 and the pmpcfg bits are L=1, R=1, W=1, X=1, the region is a locked shared data region that is read-only in both M-mode and S/U mode.
RULE 57: The xLPE status for privilege mode M is determined by the ML field of the mseccfg register (mseccfg.MLPE).

RULE 1: When the TW bit in mstatus is set, WRS.NTO is executed in any privilege mode other than M mode, and the instruction does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause an illegal-instruction exception.
RULE 2: When executing in VS or VU mode, if the VTW bit is set in hstatus, the TW bit in mstatus is clear, and the WRS.NTO instruction does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause a virtual-instruction exception.

RULE 4: The permission of a cache-block management instruction to access a cache block may be granted or denied based on the state of the MPV bit in mstatus.

RULE 6: The permission of a cache-block management instruction to access a cache block may be granted or denied based on the state of the SUM bit in mstatus.
RULE 7: The permission of a cache-block management instruction to access a cache block may be granted or denied based on the state of the MXR bit in mstatus.

RULE 14: When V=1 and both vsstatus.VS and mstatus.VS are not Off, execution of any instruction that changes vector state, including accesses to vector CSRs, changes both mstatus.VS and vsstatus.VS to Dirty.
RULE 15: If mstatus.VS is Dirty, then mstatus.SD is 1; otherwise, mstatus.SD is set according to the existing specifications.
RULE 16: If mstatus.FS is Off, any attempt to execute a vector floating-point instruction MUST raise an illegal-instruction exception.
RULE 17: Any vector floating-point instruction that modifies any floating-point extension state MUST set mstatus.FS to Dirty.
RULE 18: If either vsstatus.FS or mstatus.FS is Off, any attempt to execute a vector floating-point instruction MUST raise an illegal-instruction exception.
RULE 19: Any vector floating-point instruction that modifies any floating-point extension state MUST set both mstatus.FS and vsstatus.FS to Dirty.
RULE 20: The mstatus CSR is defined with machine-mode read/write (MRW) privilege.

RULE 53: The MIE and SIE bits reside in the low-order bits of mstatus, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 54: If supervisor mode is not implemented, the SIE and SPIE bits in mstatus are read-only 0.

RULE 59: If privilege mode x is not implemented, the corresponding xPP field in mstatus must be read-only 0.

RULE 64: The MIE bit in mstatus can be set to 1 by an explicit CSR write only if the MDT bit in mstatus is already 0, or for RV64 only if the MDT bit is being set to 0 by the same write.
RULE 65: When a trap is taken into M-mode and the MDT bit in mstatus is 0, the MDT bit in mstatus is set to 1 before the trap is delivered.
RULE 66: A trap caused by an RNMI does not set the MDT bit in mstatus.

RULE 68: The SRET instruction, when executed in M-mode, sets the MDT bit in mstatus to 0.

RULE 73: If the new privilege mode after executing MNRET is VU, the vsstatus.SDT field is also set to 0 and the mstatus register's MDT bit has been set to 0 by that instruction.

RULE 75: When MXLEN = 64 and S-mode is not supported, SXL is read-only zero in the mstatus register.

RULE 77: When MXLEN = 64 and U-mode is not supported, UXL is read-only zero in the mstatus register.
RULE 78: When MXLEN = 64 and U-mode is supported, UXL is a WARL field in the mstatus register that encodes the current value of UXLEN.
RULE 79: If S-mode is implemented, the set of legal values that the UXL field in the mstatus register may assume excludes those that would cause UXLEN to be greater than SXLEN.
RULE 80: The MPRV bit in mstatus modifies the effective privilege mode for explicit memory accesses.
RULE 81: When mstatus.MPRV = 0, explicit memory accesses use the translation and protection mechanisms of the current privilege mode.
RULE 82: When mstatus.MPRV = 1, load and store memory addresses are translated and protected, and endianness is applied as though the current privilege mode were set to the value in the MPP field of mstatus.
RULE 83: Instruction address-translation and protection are unaffected by the setting of mstatus.MPRV.
RULE 84: mstatus.MPRV is read-only 0 if U-mode is not supported.
RULE 85: An MRET or SRET instruction that changes the privilege mode to a mode less privileged than M also sets mstatus.MPRV = 0.
RULE 86: The MXR bit in mstatus modifies the privilege with which loads access virtual memory.
RULE 87: When mstatus.MXR = 0, only loads from pages marked readable (R = 1) will succeed.
RULE 88: When mstatus.MXR = 1, loads from pages marked either readable or executable (R = 1 or X = 1) will succeed.
RULE 89: mstatus.MXR has no effect when page-based virtual memory is not in effect.
RULE 90: mstatus.MXR is read-only 0 if S-mode is not supported.

RULE 93: When mstatus.SUM = 0, S-mode memory accesses to pages that are accessible by U-mode (U = 1) will fault.
RULE 94: When mstatus.SUM = 1, S-mode memory accesses to pages that are accessible by U-mode are permitted.
RULE 95: mstatus.SUM has no effect when page-based virtual memory is not in effect.

RULE 102: When S-mode is not supported, the SBE bit in mstatus is read-only 0.

RULE 34: When satp.MODE = Bare, supervisor virtual addresses are equal to supervisor physical addresses and no additional memory protection beyond the physical memory protection scheme is provided.

RULE 36: Implementations are not required to support all satp.MODE settings, and if satp is written with an unsupported MODE the entire write has no effect and no satp fields are modified.
RULE 37: The implemented number of ASID bits (ASIDLEN) may be discovered by writing ones to every bit position in the satp ASID field and reading back which bits retain a one.
RULE 38: The least-significant bits of the satp ASID field are implemented first, so that if ASIDLEN > 0 then the bits ASID[ASIDLEN-1:0] are writable.
RULE 39: The maximal ASIDLEN (ASIDMAX) is 9 for Sv32 and 16 for Sv39, Sv48, and Sv57.
RULE 40: The satp CSR is considered active when the effective privilege mode is S-mode or U-mode.
RULE 41: Executions of the address-translation algorithm may only begin using a given satp value when satp is active.
RULE 42: Translations that began while satp was active are not required to complete or terminate when satp is no longer active, unless an SFENCE.VMA instruction matching the address and ASID is executed.
RULE 43: The SFENCE.VMA instruction must be used to ensure that updates to address-translation data structures are observed by subsequent implicit reads to those structures by a hart.
RULE 44: Writing satp does not imply any ordering constraints between page-table updates and subsequent address translations, nor does it imply any invalidation of address-translation caches.
RULE 45: Implementations MUST only raise exceptions for implicit accesses that are generated as a result of instruction execution, not for those performed speculatively.
RULE 46: Changing satp.MODE from Bare to another mode or from another mode to Bare takes effect immediately without executing an SFENCE.VMA instruction.
RULE 47: Changes to satp.ASID take effect immediately.
RULE 48: For implementations that make satp.MODE read-only zero (always Bare), attempts to execute an SFENCE.VMA instruction might raise an illegal-instruction exception.
RULE 49: The ASID field of satp is local to a hart, and software may use the same ASID value in satp to refer to different address spaces on different harts.
RULE 50: The physical page number of the root page table is stored in satp.
RULE 51: When satp.MODE is Sv32, a physical address of the implementation's full physical-address width is produced directly and therefore no zero-extension is needed.
RULE 52: The value of the satp.ppn field is multiplied by the system page size to produce the base physical address used as the root page-table address for page-table walks.
RULE 53: The satp register MUST be active, meaning that the effective privilege mode must be S-mode or U-mode.
RULE 54: The ASID field contained in satp, loaded at step 0, is used to match address-translation cache entries; a cache entry satisfies a subsequent read if its ASID matches this satp-loaded ASID or if the entry is associated with a global mapping.
RULE 55: For the address space identified in satp as loaded by step 1, implicit reads of NAPOT page-table entries may create address-translation cache entries that map a + j × PTESIZE to a copy of the PTE in which pte.ppn[i][pte.napot_bits-1:0] is replaced by vpn[i][pte.napot_bits-1:0] for any j satisfying j>>napot_bits = vpn[i]>>napot_bits.
RULE 56: When VTVM=1, accesses to the satp CSR in VS-mode cause virtual-instruction exceptions instead of illegal-instruction exceptions.
RULE 57: When VTVM=1, any attempt in VS-mode to access the satp CSR raises a virtual-instruction exception.
RULE 58: If a write to the satp register specifies a MODE field value that is not supported, the write is ignored.
RULE 59: When V=1, any instruction that normally reads or modifies satp actually accesses vsatp instead.
RULE 60: When V=1, a write to satp with an unsupported MODE value is ignored and no write to vsatp is effected.
RULE 61: A write to satp with an unsupported MODE value is ignored.
RULE 62: SFENCE.VMA must apply only to memory-management data structures that are controlled by the current satp.
RULE 63: The current satp is the HS-level satp when the V field of satp is 0.
RULE 64: The current satp is the virtualized satp (vsatp) when the V field of satp is 1.
RULE 65: During conversion of a guest physical address using an Sv32x4, Sv39x4, Sv48x4, or Sv57x4 translation scheme, the hgatp register substitutes for the satp register.
RULE 66: When V=1 and the processor is executing in VS-mode and an instruction attempts to access satp, a virtual-instruction exception is taken if hstatus.VTVM=1.
RULE 67: When V=1 and the processor is executing in VU-mode and an instruction attempts to access satp (a non-high-half supervisor CSR), a virtual-instruction exception is taken if the same read or write would be permitted in HS-mode assuming mstatus.TVM=0.
RULE 68: If satp.MODE is set to Bare, or if V=1 and vsatp.MODE is set to Bare, and the effective privilege mode is less than M, then shadow stack instructions raise a store/AMO access-fault exception.
RULE 69: When the active satp register's MODE field is Bare, the ignore transformation applied to a physical address, including guest-physical addresses, replaces the upper PMLEN bits of the address with 0 (zero-extension).

REGISTER: scounteren
RULE 1: The scounteren CSR resides at supervisor privilege level.
RULE 2: The scounteren CSR has SRW access type, meaning it is readable and writable by supervisor mode.
RULE 3: When any CY, TM, IR, or HPM n bit in scounteren is clear, an attempt to read the corresponding cycle, time, instret, or hpmcountern register while executing in U-mode causes an illegal-instruction exception.
RULE 4: When any of these bits in scounteren is set, access to the corresponding counter register is permitted.
RULE 5: Any bit in scounteren may be read-only zero, which causes reads to the corresponding counter to generate an exception when executing in U-mode.
RULE 6: The setting of a bit in mcounteren does not affect whether the corresponding bit in scounteren is writable.
RULE 7: U-mode may only access a counter if the corresponding bits in both scounteren and mcounteren are set.
RULE 8: When V=1, scounteren continues to have its usual function and accessibility.
RULE 9: When V=1, VS-mode and VU-mode substitute for HS-mode and U-mode for scounteren.
RULE 10: In VU-mode, a counter MUST NOT be readable unless the applicable bits are set in both hcounteren and scounteren.
RULE 11: When V = 1 and an HS-qualified instruction is prevented from executing because the instruction is disabled by the scounteren CSR, a virtual-instruction exception with exception code 22 is normally raised instead of an illegal-instruction exception.
RULE 12: In VU-mode, if a non-high-half counter CSR is accessed and the corresponding bit in scounteren is 0 while the same bit in mcounteren is 1, a virtual-instruction exception is raised.
