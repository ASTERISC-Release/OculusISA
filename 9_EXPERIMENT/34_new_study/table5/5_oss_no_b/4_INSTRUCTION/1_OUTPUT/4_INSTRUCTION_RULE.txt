INSTRUCTION: CSRRWI
RULE 1: CSRRWI updates the targeted CSR with an XLEN-bit value that is produced by zero-extending the 5-bit unsigned immediate field uimm[4:0] encoded in the rs1 field.
RULE 2: CSRRWI atomically reads and then writes the CSR specified by the 12-bit csr field encoded in bits 31-20 of the instruction.
RULE 3: If the destination register rd of a CSRRWI instruction is x0, the instruction shall not read the CSR.
RULE 4: If the destination register rd of a CSRRWI instruction is not x0, the instruction shall read the CSR and supply the read value to rd.
RULE 5: A CSRRWI instruction shall always write the CSR.
RULE 6: The value written by a CSRRWI instruction shall be the XLEN-bit result of zero-extending the 5-bit immediate uimm[4:0].
RULE 7: CSRRWI shall cause the side effects defined for all fields within the CSR that is written.
RULE 8: If rd is x0, a CSRRWI instruction shall not cause any side effects that could arise from a CSR read.
RULE 9: CSRRWI is subject to the general CSR access rules, including raising an illegal-instruction exception when it attempts to write a read-only CSR.
RULE 10: For a CSRRWI instruction, if the destination register rd is x0, the CSR identified by the csr field MUST NOT be treated as a source register.
RULE 11: For a CSRRWI instruction, if the destination register rd is not x0, the CSR identified by the csr field MUST be treated as a source register.

INSTRUCTION: FCVT.W.D
RULE 1: FCVT.W.D MUST convert the double-precision floating-point value in floating-point register rs1 to a signed 32-bit integer and write the result to integer register rd.
RULE 2: On RV64 implementations, FCVT.W.D MUST sign-extend the 32-bit integer result to XLEN bits before writing it to rd.
RULE 3: FCVT.W.D MUST round the conversion result according to the rounding-mode field rm encoded in the instruction.
RULE 4: The floating-point exception flags for FCVT.W.D MUST be raised in accordance with the conversion semantics of FCVT.W.D for the given input operand.

INSTRUCTION: SFENCE.VMA
RULE 1: SFENCE.VMA MUST order store operations.
RULE 2: SFENCE.VMA MUST NOT order invalidate, clean, or flush operations.
RULE 3: If the TVM bit in the mstatus register is 1, executing an SFENCE.VMA instruction while the processor is in S-mode MUST raise an illegal-instruction exception.
RULE 4: If the TVM bit in the mstatus register is 0, executing an SFENCE.VMA instruction while the processor is in S-mode MUST NOT raise an illegal-instruction exception.
RULE 5: If the implementation does not support S-mode, the TVM bit is read-only zero, and executing an SFENCE.VMA instruction is not subject to the TVM-related illegal-instruction restriction.
RULE 6: After a change to menvcfg.PBMTE, execution of SFENCE.VMA with rs1 = x0 and rs2 = x0 is sufficient to synchronize address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields.
RULE 7: If the hypervisor extension is implemented, additional synchronization actions in addition to SFENCE.VMA with rs1 = x0 and rs2 = x0 are required after a change to menvcfg.PBMTE.
RULE 8: After a change to menvcfg.ADUE, execution of SFENCE.VMA with rs1 = x0 and rs2 = x0 is sufficient to synchronize address-translation caches with respect to the altered interpretation of page-table entries' A/D bits.
RULE 9: If the hypervisor extension is implemented, additional synchronization actions in addition to SFENCE.VMA with rs1 = x0 and rs2 = x0 are required after a change to menvcfg.ADUE.
RULE 10: A hart MUST execute an SFENCE.VMA instruction to ensure that any prior updates to address-translation data structures become observable to subsequent implicit reads of those structures by that hart.
RULE 11: If an SFENCE.VMA instruction that matches the address and ASID is executed after satp becomes inactive, translations that began while satp was active must complete or terminate.
RULE 12: An SFENCE.VMA instruction guarantees that any previous stores already visible to the current hart are ordered before implicit references by subsequent instructions in that hart to the memory-management data structures, as determined by the values in rs1 and rs2.
RULE 13: If rs1 = x0 and rs2 = x0, an SFENCE.VMA orders all reads and writes made to any level of the page tables for all address spaces and also invalidates all address-translation cache entries for all address spaces.
RULE 14: If rs1 = x0 and rs2 ≠ x0, an SFENCE.VMA orders all reads and writes made to any level of the page tables for the address space identified by rs2, does not order accesses to global mappings, and invalidates all address-translation cache entries matching that address space except entries containing global mappings.
RULE 15: If rs1 ≠ x0 and rs2 = x0, an SFENCE.VMA orders only reads and writes made to leaf page-table entries corresponding to the virtual address in rs1 for all address spaces and invalidates all address-translation cache entries that contain leaf page-table entries for that virtual address for all address spaces.
RULE 16: If rs1 ≠ x0 and rs2 ≠ x0, an SFENCE.VMA orders only reads and writes made to leaf page-table entries corresponding to the virtual address in rs1 for the address space identified by rs2, does not order accesses to global mappings, and invalidates all address-translation cache entries that contain leaf page-table entries for that virtual address and that address space except entries containing global mappings.
RULE 17: If the value held in rs1 is not a valid virtual address, an SFENCE.VMA instruction has no effect and no exception is raised.
RULE 18: When rs2 ≠ x0, bits SXLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use; software should zero them and implementations must ignore them.
RULE 19: If ASIDLEN < ASIDMAX, an implementation shall ignore bits ASIDMAX-1:ASIDLEN of the value held in rs2.
RULE 20: Changes to the sstatus fields SUM and MXR take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 21: Changes to satp.MODE from Bare to another mode or vice versa take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 22: Changes to satp.ASID take effect immediately without the need to execute an SFENCE.VMA instruction.
RULE 23: For implementations that make satp.MODE read-only zero (always Bare), attempts to execute an SFENCE.VMA instruction might raise an illegal-instruction exception.
RULE 24: When SFENCE.VMA is used incorrectly, or when inconsistencies remain after the SFENCE.VMA sequence, the architectural effect is that one of the possible virtual-to-physical translations will be chosen nondeterministically.
RULE 25: An SFENCE.VMA instruction invalidates the set of address-translation cache entries determined by the values in its rs1 and rs2 fields.
RULE 26: When a single hart executes in order (not necessarily consecutively) the three instructions SFENCE.W.INVAL, SINVAL.VMA with the same rs1 and rs2 that would be used by an SFENCE.VMA, and SFENCE.INVAL.IR, the resulting architectural effect is identical to that of an SFENCE.VMA with those rs1 and rs2 values.
RULE 27: When a single hart executes the ordered sequence SFENCE.W.INVAL, SINVAL.VMA (using particular rs1 and rs2 values), and SFENCE.INVAL.IR, all memory reads and writes performed before the SFENCE.W.INVAL are ordered before the SFENCE.VMA with those rs1 and rs2 values, and all reads and writes performed after the SFENCE.INVAL.IR are ordered after that SFENCE.VMA.
RULE 28: If an SFENCE.VMA instruction is executed while the processor is in U-mode, an illegal-instruction exception MUST be raised.
RULE 29: If an SFENCE.VMA instruction is executed while the processor is in S-mode or HS-mode and the mstatus.TVM bit is 1, an illegal-instruction exception MUST be raised.
RULE 30: If an SFENCE.VMA instruction is executed while the processor is in VS-mode or VU-mode and the hstatus.VTVM bit is 1, a virtual-instruction exception MUST be raised.
RULE 31: If an SFENCE.VMA instruction is executed while the processor is in VS-mode or VU-mode and the hstatus.VTVM bit is 0, a virtual-instruction exception MUST be raised.
RULE 32: If an SFENCE.VMA instruction is executed in any privilege mode not covered by the preceding exception rules, no exception is specified and the instruction is permitted.
RULE 33: SFENCE.VMA is a supervisor-level instruction and its permission checks and exception behavior are identical to those of the SINVAL-based instructions (SINVAL.VMA, HINVAL.VVMA, and HINVAL.GVMA).
RULE 34: SFENCE.VMA synchronizes a hart's address-translation caches when a memory-resident page-table entry has been changed from Invalid to Valid.
RULE 35: SFENCE.VMA synchronizes a hart's address-translation caches when a memory-resident page-table entry has been changed from Valid to Invalid.
RULE 36: SFENCE.VMA may be used to synchronize a hart's address-translation caches for any other update to a memory-resident page-table entry.
RULE 37: When the Svvptc extension is implemented, execution of SFENCE.VMA is redundant for making a change to a page-table entry from Invalid to Valid visible within a bounded time.
RULE 38: The VTVM field (Virtual Guest-Mode Virtual-Memory) controls the execution of SFENCE.VMA in VS-mode.
RULE 39: When VTVM = 1, an attempt in VS-mode to execute SFENCE.VMA MUST raise a virtual-instruction exception.
RULE 40: SFENCE.VMA MUST target only the memory-management data structures that are controlled by the current satp when the virtualisation mode bit V is 0, i.e., the HS-level satp.
RULE 41: SFENCE.VMA MUST target only the memory-management data structures that are controlled by the current satp when the virtualisation mode bit V is 1, i.e., the vsatp.
RULE 42: When the current virtualization mode V is 0, the SFENCE.VMA instruction MUST interpret the rs1 operand as an HS-level virtual address and the rs2 operand as an HS-level ASID.
RULE 43: When V = 0, the SFENCE.VMA instruction MUST order stores only to HS-level address-translation structures and MUST ensure that subsequent HS-level address translations observe those stores.
RULE 44: When the current virtualization mode V is 1, the SFENCE.VMA instruction MUST interpret the rs1 operand as a guest virtual address within the current virtual machine and the rs2 operand as a VS-level ASID belonging to that virtual machine.
RULE 45: When V = 1, the effective ASID used by the SFENCE.VMA instruction MUST be considered the concatenation of the VMID field of CSR hgatp and the VS-level ASID supplied in rs2.
RULE 46: When V = 1, the SFENCE.VMA instruction MUST order stores only to VS-level address-translation structures and MUST ensure that subsequent VS-stage address translations for the same virtual machine (i.e., with the same hgatp.VMID as at execution) observe those stores.
RULE 47: The core ordering behavior defined for the SFENCE.VMA instruction remains unchanged by the existence of the hypervisor instructions HFENCE.VVMA and HFENCE.GVMA.
RULE 48: In VS-mode, if hstatus.VTVM=1 and an SFENCE.VMA instruction is attempted, a virtual-instruction exception MUST be raised.
RULE 49: In VU-mode, any attempt to execute an SFENCE.VMA instruction causes a virtual-instruction exception.
RULE 50: When a virtual-instruction exception is taken as a result of an SFENCE.VMA instruction, the mtval or stval CSR is written with the same value that would be written for an illegal-instruction trap.
RULE 51: Changes to xSSE take effect immediately and therefore do not require execution of SFENCE.VMA for the changes to become architecturally visible.
RULE 52: Address-translation caches need not be synchronized with SFENCE.VMA after modifications to xSSE.
RULE 53: The 32-bit encoding of SFENCE.VMA MUST have funct7 bits [31:25] equal to 0001001.
RULE 54: The 32-bit encoding of SFENCE.VMA MUST have the rs2 field [24:20] specify the source register that holds the page address.
RULE 55: The 32-bit encoding of SFENCE.VMA MUST have the rs1 field [19:15] specify the source register that holds the address space identifier.
RULE 56: The 32-bit encoding of SFENCE.VMA MUST have funct3 bits [14:12] equal to 000.
RULE 57: The 32-bit encoding of SFENCE.VMA MUST have the rd field [11:7] equal to zero, indicating no destination register.
RULE 58: The 32-bit encoding of SFENCE.VMA MUST have opcode bits [6:0] equal to 1110011, designating a SYSTEM instruction.

INSTRUCTION: VLE32FF.V
RULE 1: VLE32FF.V loads 32-bit elements with unit stride from the address formed by adding 4 times the element index to the scalar register rs1, and stores each loaded element into the corresponding element of the destination vector register group vd.
RULE 2: VLE32FF.V applies the mask encoding supplied by the vm field, loading only elements whose mask bit is true and leaving masked-off elements unchanged.
RULE 3: VLE32FF.V takes a trap only for a synchronous exception that occurs while loading element 0; exceptions on any other element do not cause a trap.
RULE 4: If a synchronous exception occurs on element 0 of VLE32FF.V, the trap is taken and the architectural vector length register vl is not modified.
RULE 5: If a synchronous exception would occur on any element with index greater than zero during VLE32FF.V, the trap is not taken and the hardware reduces vl to the index of the first such element.
RULE 6: VLE32FF.V may write to active destination elements whose indices are greater than the element index at which a trap is reported, but it must never write beyond the original vl value present at the start of the instruction.
RULE 7: VLE32FF.V may also update active destination elements whose indices exceed the element that caused vl trimming, yet it must never modify elements beyond the original vl specified at instruction entry.
RULE 8: When vstart equals zero and the initial vl is greater than zero, VLE32FF.V must process at least one element.
RULE 9: If VLE32FF.V takes a trap because of an interrupt, the implementation should not reduce vl and should set vstart to the index of the next element to be executed.
RULE 10: If VLE32FF.V would trigger a debug data-watchpoint trap on any element with index greater than zero, the implementation should not reduce vl and should deliver the debug trap so that the event is not lost.
