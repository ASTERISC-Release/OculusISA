REGISTER: mseccfg
RULE 1: The mseccfg CSR includes the SSEED and USEED fields added by the Zkr extension, and these fields control access to the seed CSR from U, S, and HS privilege modes.
RULE 2: Implementations may configure the mseccfg register so that the [s,u]seed fields are read-only constant zero, thereby permanently disabling direct access to the seed CSR from S and U modes.
RULE 3: Software can probe the mseccfg register to determine if seed CSR access is permitted in U or S mode by writing a value of 1 to the [s,u]seed fields and then reading back the result.
RULE 4: The mseccfg register can be used by a system to enforce access-control policies for the seed CSR, such that attempted accesses from lower-privilege modes may be trapped and replaced with virtual entropy data generated by a secure software DRBG instead of invoking a physical entropy source.
RULE 5: The direct mseccfg.[s,u]seed option allows a designer to draw a security boundary around a component with respect to Sensitive Security Parameter (SSP) flows, even when that component is not operating in M-mode.
RULE 6: The mseccfg register can be used to enforce the complete key lifecycle—from generation in the entropy source (birth) to zeroization (death)—without the key ever crossing the security boundary to external code.
RULE 7: The mseccfg facility is particularly helpful when implementing trusted enclaves, providing a mechanism to contain SSPs and keys inside the enclave.
RULE 8: The mseccfg register governs direct hardware access to the entropy source and therefore must be considered a Sensitive Security Parameter (SSP) control point.
RULE 9: Implementers should avoid adding unnecessary status or custom bits to the mseccfg register, as any extra information-flow mechanisms can create side-channel or covert-channel vulnerabilities.
RULE 10: The mseccfg register is a machine-level CSR located at address 0x747.
RULE 11: The mseccfg CSR has Machine-Read/Write (MRW) privilege, meaning it can be read and written in machine mode.
RULE 12: The official name of the CSR at address 0x747 is "mseccfg".
RULE 13: The description of the mseccfg register is "Machine security configuration register".
RULE 14: The mseccfg register belongs to the Machine Configuration group of CSRs.
RULE 15: Both mseccfg and its upper-half counterpart mseccfgh are machine-level CSRs and are not accessible from lower privilege modes.
RULE 16: mseccfg is a 64-bit read/write CSR that configures machine-level security features.
RULE 17: mseccfg is implemented only if at least one architectural extension adds a field to it; otherwise the CSR is reserved.
RULE 18: The Zkr extension adds the fields USEED and SSEED to mseccfg.
RULE 19: In mseccfg, USEED = 0 causes any seed-CSR access from U-mode to raise an illegal-instruction exception; USEED = 1 permits normal read-write access from U-mode while all other access types still raise illegal-instruction exceptions.
RULE 20: If the Zkr extension or U-mode is not present, the mseccfg.USEED field is hard-wired read-only zero.
RULE 21: In mseccfg, SSEED = 0 causes any seed-CSR access from S- or HS-mode to raise an illegal-instruction exception; SSEED = 1 permits normal read-write access from S-/HS-mode while all other access types still raise illegal-instruction exceptions.
RULE 22: If the Zkr extension or S-mode is not present, the mseccfg.SSEED field is hard-wired read-only zero.
RULE 23: When the H extension is also implemented, an HS-qualified instruction that accesses the seed CSR triggers a virtual-instruction exception in VS and VU modes; all other access types still raise illegal-instruction exceptions, as governed by mseccfg.
RULE 24: The Smepmp extension adds the WARL fields RLB, MMWP, and MML to mseccfg.
RULE 25: mseccfg.RLB (Rule Locking Bypass) is a WARL bit; when set to 1 it allows temporary modification or removal of locked PMP rules, and when 0 and any pmpcfg.L = 1 the bit remains 0 and further writes to mseccfg.RLB are ignored until a PMP reset.
RULE 26: Vendors may hard-wire the mseccfg.RLB field to 0 if the debug/boot-time bypass functionality is not required.
RULE 27: mseccfg.MMWP (Machine-Mode Allowlist Policy) is a sticky WARL bit; once set it cannot be cleared until a PMP reset and changes the default PMP policy for M-mode accesses to unmapped regions from "ignored" to "denied".
RULE 28: mseccfg.MML (Machine Mode Lockdown) is a sticky WARL bit; once set it cannot be cleared until a PMP reset and reinterprets pmpcfg.L so that a locked rule becomes M-mode-only (or S/U-mode-only when cleared) and introduces Shared-Region encodings as described.
RULE 29: When mseccfg.MML is set, adding a PMP rule that is executable and either M-mode-only or a locked Shared-Region is ignored unless mseccfg.RLB is also set; execution is only permitted from regions that match an M-mode-only rule or a locked executable Shared-Region rule.
RULE 30: The Zicfilp extension adds the MLPE field to mseccfg; MLPE = 1 enables Zicfilp in M-mode, while MLPE = 0 disables it, causing the hart not to update ELP state and making LPAD a no-op.
RULE 31: Upon reset, the MML, MMWP, and RLB fields of the mseccfg register are set to 0, unless the platform explicitly mandates a different reset value.
RULE 32: If the Zicfilp extension is implemented, the MLPE field of the mseccfg register is reset to 0.
RULE 33: The USEED field of the mseccfg CSR must have a defined reset value; the system must ensure it is never left in an undefined state after reset.
RULE 34: The SSEED field of the mseccfg CSR must have a defined reset value; the system must ensure it is never left in an undefined state after reset.
RULE 35: The mseccfg CSR contains the RLB, MMWP, and MML fields that are introduced by the physical memory protection extension.
RULE 36: When the mseccfg.MML bit is set to 1, the memory-access behavior of PMP entries is governed by the truth-table shown in the specification (i.e., the "MMode" and "S/U Mode" result columns).
RULE 37: The mseccfg.MML = 1 setting distinguishes two privilege classes—machine mode (MMode) and supervisor/user mode (S/U Mode)—and applies the corresponding result for each combination of PMP configuration bits L,R,W,X.
RULE 38: For any PMP entry where mseccfg.MML = 1 and the L (bit) is 0, the region is *unlocked* and the access permissions follow the standard PMP semantics indicated in the table (e.g., 0-0-1-0 -> shared data region, read/write in MMode and read-only in S/U Mode).
RULE 39: For any PMP entry where mseccfg.MML = 1 and the L (bit) is 1, the region becomes *locked* (marked with "*" in the table), and the access rights are fixed for both MMode and S/U Mode as described (e.g., 1-0-0-0 -> locked inaccessible region).
RULE 40: The presence of the mseccfg.MML field therefore enables a mode-specific physical memory protection scheme that can enforce shared, read-only, execute-only, or fully locked regions, depending on the PMP L,R,W,X bits.
RULE 41: The mseccfg register is the central control point for configuring these additional protection fields (RLB, MMWP, MML) and thus directly influences the enforcement of the physical memory protection rules defined for the system.
RULE 42: In M privilege mode, the landing-pad-enabled state (xLPE) is determined by the MLPE field of the mseccfg register.
RULE 43: The field in the mseccfg register used for xLPE determination is named MLPE.
RULE 44: The mseccfg.MLPE field is consulted for xLPE regardless of whether S-mode is implemented; it always controls the M-mode landing-pad status.
RULE 45: Setting the MLPE bit in the mseccfg register enables forward-edge CFI with Zicfilp landing pads for code executing in M-mode.
RULE 46: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 47: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 48: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 49: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 50: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 51: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 52: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 53: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 54: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 55: In M-mode, accessing mseccfg register while Zicfilp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zicfilp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 56: In M-mode, accessing mseccfg register while Zkr extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zkr; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
RULE 1: If the TW (Timeout Wait) bit in mstatus is set and a WRS.NTO instruction is executed in any privilege mode other than M mode, and the instruction does not complete within the implementation-specific bounded time limit, the instruction must raise an illegal-instruction exception.
RULE 2: When executing in VS or VU mode, if the VTW bit in hstatus is set **and** the TW bit in mstatus is clear, and a WRS.NTO instruction fails to complete within the implementation-specific bounded time limit, the instruction must raise a virtual-instruction exception.
RULE 3: If the TW bit in mstatus is clear (0), executing a WRS.NTO instruction in U mode does **not** cause an illegal-instruction exception.
RULE 4: Whether a CMO instruction can access a cache block is determined by the states of the MPRV, MPV, and MPP bits in mstatus.
RULE 5: The SUM bit in mstatus (as well as the matching bits in sstatus and vsstatus) influences the permission checks for CMO instructions.
RULE 6: The MXR bit in mstatus (along with the equivalent bits in sstatus and vsstatus) influences the permission checks for CMO instructions.
RULE 7: When the MPRV bit in mstatus is set, address translation for memory accesses (including CMO instructions) uses the privilege mode encoded in the MPP field rather than the current execution mode.
RULE 8: The MPV bit in mstatus modifies the effective privilege for memory accesses, thereby affecting whether a CMO instruction is allowed to access a given cache block.
RULE 9: The MPP field in mstatus records the previous privilege mode and is consulted (in conjunction with MPRV) to decide the access rights of CMO instructions.
RULE 10: In a system that implements the Zfinx extension, the mstatus field FS (Floating-point Status) is hard-wired to 0.
RULE 11: When the Zfinx extension is implemented, the mstatus FS field no longer influences the trapping behavior of floating-point instructions or accesses to the fcsr register.
RULE 12: The vector context status field VS occupies bits [10:9] of the mstatus register and is shadowed in the same bit positions of the sstatus register.
RULE 13: The VS field in mstatus is defined analogously to the floating-point context status field FS.
RULE 14: If mstatus.VS is set to Off, any attempt to execute a vector instruction or to access any vector CSR triggers an illegal-instruction exception.
RULE 15: When mstatus.VS holds the value Initial or Clean, the execution of any instruction that modifies vector state—including accesses to vector CSRs—automatically updates mstatus.VS to Dirty.
RULE 16: Implementations are permitted to change mstatus.VS from Initial or Clean to Dirty at any time, even when no vector-state-changing instruction has been executed.
RULE 17: Accurate maintenance of mstatus.VS is an optimization technique; software typically uses the VS field to minimise context-swap overhead.
RULE 18: If mstatus.VS is Dirty, the mstatus.SD bit is set to 1; otherwise, mstatus.SD follows the rules defined in the existing specification for non-vector status.
RULE 19: Implementations may provide a writable misa.V field; however, the mstatus.VS field may still be present even when misa.V is cleared.
RULE 20: Allowing mstatus.VS to exist while misa.V is cleared enables vector-instruction emulation and simplifies handling of the VS field on systems with a writable misa.V.
RULE 21: When V=1, the mstatus.VS field is active; if mstatus.VS is set to Off, any attempt to execute a vector instruction or access a vector CSR raises an illegal-instruction exception.
RULE 22: When V=1 and neither vsstatus.VS nor mstatus.VS is Off, executing any instruction that modifies vector state (including accesses to vector CSRs) must set mstatus.VS to Dirty.
RULE 23: Implementations are permitted to change mstatus.VS from Initial or Clean to Dirty at any time, even in the absence of a vector-state-changing operation.
RULE 24: If mstatus.VS is Dirty, then mstatus.SD must be 1; otherwise, the value of mstatus.SD follows the existing specification rules.
RULE 25: If mstatus.FS is Off, any attempt to execute a vector floating-point instruction raises an illegal-instruction exception.
RULE 26: Any vector floating-point instruction that modifies floating-point extension state (floating-point CSRs or f registers) must set mstatus.FS to Dirty.
RULE 27: When the hypervisor extension is implemented and V=1, the condition that mstatus.FS is Off (or vsstatus.FS is Off) also raises an illegal-instruction exception for vector floating-point instructions.
RULE 28: When the hypervisor extension is implemented and V=1, any vector floating-point instruction that modifies floating-point extension state must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 29: The mstatus CSR is located at address 0x300 in the RISC-V machine-level CSR map.
RULE 30: The mstatus CSR has the MRW privilege type, allowing it to be both read and written in Machine mode.
RULE 31: The mstatus CSR is classified under the "Machine Trap Setup" group of machine-level CSRs.
RULE 32: The official description of the mstatus CSR is "Machine status register".
RULE 33: The mstatus register is an MXLEN-bit read/write register that records and controls the current operating state of a hart.
RULE 34: The low-order bits of mstatus (bits 0-31) contain the fields XS[1:0], FS[1:0], MPP[1:0], VS[1:0], SPP, MPIE, UBE, SPIE, MIE, SIE and various WPRI (reserved) positions as defined in the figures.
RULE 35: In the RV64 version of mstatus, bits 32-63 add the fields SXL[1:0], UXL[1:0], SBE, MBE, GVA, MPV, MPELP, MDT and SD, together with additional WPRI fields.
RULE 36: The XS[1:0] and FS[1:0] fields in mstatus encode the status of the user-mode extensions and the floating-point extensions, respectively.
RULE 37: The MPP[1:0] field in mstatus records the previous privilege mode before a trap, and the VS[1:0] field records the previous virtual-supervisor mode.
RULE 38: The single-bit fields SPP, MPIE, SPIE, MIE, SIE, UBE and TW in mstatus control supervisor-mode previous privilege, machine-mode interrupt enable after trap, supervisor-mode interrupt enable after trap, global machine-mode interrupt enable, global supervisor-mode interrupt enable, user-mode byte ordering, and timeout-wait, respectively.
RULE 39: The fields MXR, SUM, MPRV, TVM, TSR and TW in mstatus govern memory-access permissions and virtual-memory behavior (e.g., make-executable-readable, permit supervisor access to user memory).
RULE 40: Bits labelled WPRI in mstatus are "write-preserve read-only" reserved bits; software must write them with zero and ignore their value.
RULE 41: A restricted view of the mstatus register appears as the sstatus register in the S-level ISA, exposing only a subset of mstatus fields.
RULE 42: The global interrupt-enable bits MIE (machine-mode) and SIE (supervisor-mode) are located in the low-order bits of the mstatus register, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 43: If the implementation does not include supervisor mode, the SIE and SPIE bits in mstatus are hard-wired to 0 (read-only).
RULE 44: When a trap is taken from privilege mode y into privilege mode x, the hardware performs the following updates in mstatus: xPIE <- xIE, xIE <- 0, and xPP <- y.
RULE 45: The xPP fields (MPP for machine mode, SPP for supervisor mode) are stored in the mstatus register, are WARL (Write-Any-Legal-Value) fields, and can hold only the current privilege mode x and any implemented lower privilege modes.
RULE 46: An MRET or SRET instruction restores the previous privilege state by reading the xPP and xPIE fields from mstatus, setting xIE to xPIE, setting xPIE to 1, and updating the current privilege mode to the value held in xPP.
RULE 47: If the privilege mode restored by an xRET instruction is not machine mode (y ≠ M), the MPRV bit in mstatus is also cleared to 0 as part of the return sequence.
RULE 48: Software can discover which privilege modes are implemented by writing a candidate mode value to the MPP field in mstatus and then reading it back; if the read-back value differs, the mode is not implemented.
RULE 49: When only user (U) and machine (M) modes are implemented, the MPP field in mstatus requires only a single hardware storage bit, representing either the value 00 (U) or 11 (M).
RULE 50: The xPP fields in mstatus must be read-only 0 if the corresponding privilege mode x is not implemented in the hardware.
RULE 51: The mstatus register contains the MIE (Machine Interrupt Enable) bit.
RULE 52: On reset, the MDT field in mstatus is initialized to 1.
RULE 53: Writing 1 to the MDT bit in mstatus clears the MIE bit in mstatus to 0.
RULE 54: For RV64, a CSR write that sets MDT to 1 clears MIE to 0 regardless of any value written to MIE in the same instruction.
RULE 55: The MIE bit in mstatus may be set to 1 only if the MDT bit is currently 0, or (for RV64) if the same CSR write simultaneously clears MDT to 0.
RULE 56: When a trap is taken into M-mode and the MDT bit in mstatus is 0, hardware sets MDT to 1 as part of the trap entry; if MDT is already 1 the trap is classified as an unexpected (double) trap.
RULE 57: The MRET instruction executed in M-mode clears the MDT bit in mstatus to 0.
RULE 58: The SRET instruction executed in M-mode also clears the MDT bit in mstatus to 0 (in addition to affecting sstatus.SDT for lower-privilege modes).
RULE 59: The MNRET instruction (provided by the Smrnmi extension) clears the MDT bit in mstatus to 0 whenever the return-target privilege mode is not M.
RULE 60: In the mstatus register of RV64 harts, the SXL and UXL fields are WARL (Write-Any-Legal-Value) fields that control the effective XLEN for S-mode (SXLEN) and U-mode (UXLEN) respectively, using the same encoding as the MXL field of the misa register.
RULE 61: When MXLEN = 64 and S-mode is not implemented, the SXL field in the mstatus register is a read-only zero; otherwise SXL is a WARL field that encodes the current SXLEN. An implementation may also make SXL read-only with a value that forces SXLEN = MXLEN.
RULE 62: When MXLEN = 64 and U-mode is not implemented, the UXL field in the mstatus register is a read-only zero; otherwise UXL is a WARL field that encodes the current UXLEN. An implementation may also make UXL read-only with a value that forces UXLEN = MXLEN or UXLEN = SXLEN.
RULE 63: If S-mode is implemented, the set of legal values that the UXL field in the mstatus register may assume excludes any value that would cause UXLEN to be greater than SXLEN.
RULE 64: Whenever the XLEN configured by the mstatus register for any privilege mode is less than the widest supported XLEN, all architectural operations must ignore source-operand register bits above the configured XLEN and must sign-extend results to fill the full widest XLEN in the destination register.
RULE 65: When the XLEN set by the mstatus register is less than the widest supported XLEN, PC bits above the configured XLEN are ignored on fetch and, when the PC is written, those bits are sign-extended to fill the widest XLEN.
RULE 66: The architecture imposes no hardware checks that the XLEN settings encoded in the mstatus register for lower-privilege modes are less than or equal to those of higher-privilege modes; machine operation remains well-defined even if a lower-privilege XLEN exceeds a higher-privilege XLEN.
RULE 67: For HINT instructions that write back the destination register with its own value, if the current XLEN (as set in the mstatus register) is less than MXLEN and the upper bits (MXLEN-1 … XLEN) of the destination are not all equal to bit XLEN-1, it is implementation-defined whether those upper bits are left unchanged or overwritten with copies of bit XLEN-1.
RULE 68: The behavior described for HINT instructions (RULE 9) is observable only by privilege modes whose XLEN setting in the mstatus register is greater than the current XLEN; it is invisible to the mode executing the HINT.
RULE 69: In the mstatus register, the MPRV (Modify PRiVilege) bit controls the effective privilege level for explicit load and store memory accesses, making them behave as if the current privilege mode were set to the value in MPP when MPRV=1.
RULE 70: When MPRV=0 in the mstatus register, explicit memory accesses use the translation and protection mechanisms of the current privilege mode as normal.
RULE 71: The instruction address-translation and protection mechanisms are not affected by the MPRV setting in the mstatus register.
RULE 72: The MPRV bit in the mstatus register is hard-wired to 0 (read-only) if U-mode is not implemented in the processor.
RULE 73: Executing an MRET or SRET instruction that lowers the privilege mode below M clears the MPRV bit (sets MPRV=0) in the mstatus register.
RULE 74: The MXR (Make eXecutable Readable) bit in the mstatus register alters the privilege with which loads access virtual memory: MXR=0 permits loads only from pages marked readable (R=1), while MXR=1 permits loads from pages marked readable or executable (R=1 or X=1).
RULE 75: The MXR bit in the mstatus register has no effect when page-based virtual memory is not active, and it is read-only 0 if S-mode is not supported.
RULE 76: The SUM (permit Supervisor User Memory access) bit in the mstatus register controls S-mode load/store access to pages that are user-accessible: SUM=0 causes a fault for such accesses, whereas SUM=1 permits them.
RULE 77: The SUM bit in the mstatus register is ignored when not executing in S-mode, except when MPRV=1 and MPP=S, in which case SUM is in effect.
RULE 78: The SUM bit in the mstatus register is read-only 0 if S-mode is not supported or if the satp.MODE field is read-only 0.
RULE 79: When MPRV=1 in the mstatus register, load and store memory addresses are treated as though the current XLEN were the XLEN associated with the privilege level indicated by MPP, following the rules of Section 3.1.6.3.
RULE 80: The MXR and SUM mechanisms in the mstatus register affect only the interpretation of permission bits in page-table entries; they do not influence access-fault exceptions caused by Physical Memory Attributes (PMAs) or the Physical Memory Protection (PMP) unit.
RULE 81: The MBE, SBE, and UBE bits are WARL fields in the mstatus (and mstatush) register that control the endianness of all memory accesses except instruction fetches, which are always little-endian.
RULE 82: In mstatus, MBE selects the endianness of non-instruction-fetch memory accesses made from M-mode when mstatus.MPRV = 0: MBE = 0 ⇒ little-endian, MBE = 1 ⇒ big-endian.
RULE 83: If S-mode is implemented, the SBE bit in mstatus controls the endianness of explicit loads and stores issued from S-mode: SBE = 0 ⇒ little-endian, SBE = 1 ⇒ big-endian; if S-mode is not implemented, SBE is a read-only zero.
RULE 84: If U-mode is implemented, the UBE bit in mstatus controls the endianness of explicit loads and stores issued from U-mode: UBE = 0 ⇒ little-endian, UBE = 1 ⇒ big-endian; if U-mode is not implemented, UBE is a read-only zero.
RULE 85: Implicit accesses to supervisor-level memory-management structures (e.g., page tables) always use the endianness defined by the SBE field in mstatus.
RULE 86: When software changes the SBE field in mstatus while any supervisor-level data structures remain in use, M-mode software must execute an SFENCE.VMA with rs1 = x0 and rs2 = x0 after the change.
RULE 87: An implementation may make SBE a read-only copy of MBE in mstatus when S-mode is supported.
RULE 88: An implementation may make UBE a read-only copy of either MBE or SBE in mstatus when U-mode is supported.
RULE 89: An implementation that provides only little-endian memory accesses has MBE, SBE, and UBE in mstatus all hard-wired to zero.
RULE 90: An implementation that provides only big-endian memory accesses (aside from instruction fetches) has MBE in mstatus hard-wired to one and, when S-mode and U-mode are supported, SBE and UBE also hard-wired to one.
RULE 91: The endianness control bits in mstatus permit an OS of one endianness to run user-mode programs of the opposite endianness by flipping the appropriate MBE, SBE, or UBE values.
RULE 92: Because RISC-V instructions are always little-endian, software that encodes or decodes instructions must account for the fact that explicit loads and stores obey the endianness selected by the mstatus MBE/SBE/UBE fields, which may differ from the instruction endianness.
RULE 93: In the mstatus register, the TVM (Trap Virtual Memory) bit is a WARL field that controls trapping of supervisor virtual-memory management operations.
RULE 94: When mstatus.TVM = 1, any attempt in S-mode to read or write the satp CSR or to execute SFENCE.VMA or SINVAL.VMA raises an illegal-instruction exception.
RULE 95: When mstatus.TVM = 0, the above supervisor virtual-memory operations are permitted in S-mode.
RULE 96: The TVM bit in mstatus reads as 0 (read-only zero) on implementations that do not support S-mode.
RULE 97: The TW bit in mstatus reads as 0 (read-only zero) when the processor has no privilege modes less privileged than M.
RULE 98: In the mstatus register, the TSR (Trap SRET) bit is a WARL field that controls trapping of the SRET instruction.
RULE 99: When mstatus.TSR = 1, any attempt to execute SRET while in S-mode raises an illegal-instruction exception.
RULE 100: When mstatus.TSR = 0, execution of SRET in S-mode is permitted.
RULE 101: The TSR bit in mstatus reads as 0 (read-only zero) on implementations that do not support S-mode.
RULE 102: Trapping SRET via mstatus.TSR is required to emulate the hypervisor extension on implementations that lack native support.
RULE 103: The mstatus register contains the FS[1:0], VS[1:0] and XS[1:0] fields that encode the status of the floating-point unit, vector extension, and all other user-mode extensions respectively.
RULE 104: In the mstatus register each of the FS, VS and XS fields uses the four-value encoding defined in Table 13: 0 = Off, 1 = Initial, 2 = Clean, 3 = Dirty.
RULE 105: The mstatus register includes a read-only SD bit that is set to 1 whenever any of FS, VS or XS is in the Dirty state (FS==0b11 OR VS==0b11 OR XS==0b11); otherwise SD is 0.
RULE 106: If FS, VS and XS are all read-only zero in the mstatus register, the SD bit is permanently zero.
RULE 107: When the F extension is implemented, the FS field in the mstatus register shall not be read-only zero.
RULE 108: If neither the F extension nor S-mode is implemented, the FS field in the mstatus register is read-only zero; if S-mode exists but the F extension does not, FS may optionally be read-only zero.
RULE 109: When the vector registers are implemented, the VS field in the mstatus register shall not be read-only zero.
RULE 110: If neither vector registers nor S-mode are implemented, the VS field in the mstatus register is read-only zero; if S-mode exists but vector registers are absent, VS may optionally be read-only zero.
RULE 111: In harts that have no additional user extensions requiring state, the XS field in the mstatus register is read-only zero.

REGISTER: satp
RULE 1: The satp register is a supervisor-level CSR located at address 0x180.
RULE 2: The satp register has SRW privilege, meaning it is readable and writable in supervisor mode.
RULE 3: The satp register implements supervisor address translation and protection.
RULE 4: The satp register is classified under the Supervisor Protection and Translation group.
RULE 5: All S-mode instruction fetches implicitly read the satp CSR.
RULE 6: Implementations may perform implicit reads of the satp register, as they can for other CSRs.
RULE 7: Unless otherwise specified, the value returned by an implicit read of the satp CSR is identical to the value that would be returned by an explicit read of satp using a CSR-access instruction in a sufficiently privileged mode.
RULE 8: The SUM bit is read-only 0 if S-mode is not supported **or if satp.MODE is read-only 0**.
RULE 9: When the TVM bit in the mstatus register is set to 1, any attempt to read or write the satp CSR while executing in S-mode causes an illegal-instruction exception.
RULE 10: When the TVM bit in the mstatus register is 0, reads and writes to the satp CSR are permitted in S-mode.
RULE 11: Trapping satp accesses (enabled by TVM = 1) provides the hooks necessary to lazily populate shadow page tables.
RULE 12: The TVM bit is read-only zero on implementations that do not support S-mode, meaning satp accesses are never trapped in such implementations.
RULE 13: If S-mode is not supported, or if the satp.MODE field is read-only zero (always Bare), the implementation may make the menvcfg.FIOM bit read-only zero.
RULE 14: The PBMTE bit controls the availability of the Svpbmt extension for page tables whose root is referenced by satp (or hgatp); PBMTE = 1 enables Svpbmt for S-mode and G-stage address translation, while PBMTE = 0 causes the implementation to behave as if Svpbmt is not implemented.
RULE 15: If satp.MODE = 0 (page-based virtual memory not in effect), the MXR and SUM bits in sstatus have no effect on memory accesses.
RULE 16: SUM is read-only 0 when satp.MODE is read-only 0.
RULE 17: When satp.MODE ≠ 0 (page-based virtual memory enabled), the SUM bit can be written and controls whether supervisor-mode loads and stores may access user pages.
RULE 18: The privilege checks governed by MXR and SUM are only active when satp.MODE is non-zero; otherwise they are ignored.
RULE 19: If **satp.MODE** is read-only zero (the implementation always forces the Bare address translation mode), then the implementation may make the **FIOM** field in the senvcfg CSR read-only zero.
RULE 20: The satp CSR is an SXLEN-bit read/write register that controls supervisor-mode address translation and protection.
RULE 21: For SXLEN = 64, satp is formatted with a 4-bit MODE field, a 16-bit ASID field, and a 44-bit PPN field.
RULE 22: The satp.PPN field holds the physical page number of the root page table (the supervisor physical address divided by 4 KiB).
RULE 23: The satp.ASID field provides an address-space identifier that enables per-address-space address-translation fences.
RULE 24: The number of implemented ASID bits (ASIDLEN) is discovered by writing all ones to the ASID field and reading back satp; the least-significant bits are implemented first.
RULE 25: ASIDLEN may be zero, and its maximum value (ASIDMAX) is 9 for Sv32 and 16 for Sv39, Sv48, and Sv57.
RULE 26: The satp.MODE field selects the current address-translation scheme; it is a WARL (Write-Any-Read-Legal) field.
RULE 27: When satp.MODE = Bare, supervisor virtual addresses equal supervisor physical addresses and no extra protection beyond physical-memory protection is applied.
RULE 28: MODE encodings 1-7 (SXLEN = 64) and any unspecified values are reserved for standard use; encodings 14-15 are designated for custom use.
RULE 29: Implementations are not required to support all satp.MODE settings; writing an unsupported MODE causes the entire satp write to have no effect and leaves all satp fields unchanged.
RULE 30: The satp register is considered active when the effective privilege mode is S-mode or U-mode; address-translation algorithms may only start using a satp value while it is active.
RULE 31: Translations that began while satp was active may continue after satp becomes inactive, unless an SFENCE.VMA matching the address and ASID is executed.
RULE 32: Writing satp does not impose ordering constraints between page-table updates and subsequent address translations, nor does it automatically invalidate address-translation caches.
RULE 33: After writing satp, software may need to execute an SFENCE.VMA instruction (before or after the write) to ensure that page-table modifications or ASID reuse are observed.
RULE 34: The atomic update of both ASID and page-table base address in satp on a context switch prevents pollution of the old virtual address space with new translations and reduces context-switch overhead.
RULE 35: The satp.PPN field may be constrained by platform standards; some platforms may require that all physical page numbers for main memory be representable in satp.PPN.
RULE 36: The number of ASID bits (ASIDLEN) is unspecified by the ISA; implementations may implement fewer bits than the maximum allowed.
RULE 37: When MODE = Bare, the remaining satp fields (ASID and PPN) are reserved for future use, and their values have unspecified effects.
RULE 38: For SXLEN = 64, all encodings with MODE = Bare are reserved for future standard use.
RULE 39: Implementations must only perform implicit reads of the translation-data structures that are pointed to by the current contents of the satp register (or by a subsequently reachable valid entry).
RULE 40: Any change to satp.MODE (e.g., from Bare to a paging mode or vice-versa) takes effect immediately and does **not** require the execution of an SFENCE.VMA instruction.
RULE 41: Any change to satp.ASID takes effect immediately and does **not** require the execution of an SFENCE.VMA instruction.
RULE 42: When software recycles an ASID, it must first write satp with the new page-table base and the recycled ASID, then execute SFENCE.VMA with rs1 = x0 and rs2 set to that recycled ASID (or alternatively execute SFENCE.VMA while a different ASID is loaded into satp, provided the next satp load simultaneously installs the recycled ASID and the new page-table).
RULE 43: On implementations that do not provide ASIDs, or when software chooses to use only ASID 0, software should execute an SFENCE.VMA after **every** satp write; rs1 = x0 and rs2 should contain a register holding zero (but not x0) so that global translations are not flushed.
RULE 44: On implementations where satp.MODE is read-only zero (i.e., the processor is permanently in Bare mode), attempting to execute an SFENCE.VMA may raise an illegal-instruction exception.
RULE 45: The virtual-address width used for address translation is defined by the value of satp.MODE; translations may still be used even if their virtual-address width differs from the current satp.MODE, as long as the most recent subsuming SFENCE.VMA allows it.
RULE 46: The meaning of an ASID is local to each hart; therefore, the address-translation cache that is indexed by satp.ASID must appear private to that hart.
RULE 47: If a hart employs an address-translation cache, the cache must be private to the hart, and the ASID field of satp is interpreted locally, allowing the same ASID value to refer to different address spaces on different harts.
RULE 48: Software that modifies page-table entries must ensure that satp points to the correct page-table before executing the appropriate SFENCE.VMA; otherwise, implicit reads may follow stale translations referenced by the previous satp value.
RULE 49: Changing satp does **not** implicitly cause a TLB or address-translation-cache flush; explicit SFENCE.VMA instructions are required only when the memory-management data structures that affect translations have been modified.

RULE 52: When the satp register is configured for Sv32, both supervisor and user virtual addresses are translated to supervisor physical addresses by traversing a radix-tree page table.
RULE 53: The satp register contains a MODE field that selects the virtual-memory mode (e.g., Sv32 or Bare).
