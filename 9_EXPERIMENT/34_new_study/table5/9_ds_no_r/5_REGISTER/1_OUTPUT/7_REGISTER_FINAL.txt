REGISTER: mseccfg
NUMBER: 0x747
MODE: M-mode
WIDTH: 64
FIELDS: 33..32=PMM, 10..10=MLPE, 9..9=SSEED, 8..8=USEED, 2..2=RLB, 1..1=MMWP, 0..0=MML
EXTENSIONS: Smepmp, Smmpm, Zicfilp, Zkr
RULE 1: If mseccfg.SSEED is 0, then an S-mode or HS-mode access to the seed CSR raises an illegal-instruction exception; if mseccfg.USEED is 0, then a U-mode access to the seed CSR raises an illegal-instruction exception; when the applicable field is 1, that mode’s access to the seed CSR is permitted.
RULE 2: An implementation may implement mseccfg such that [s,u]seed is a read-only constant value 0.
RULE 3: Software may discover whether access to the seed CSR can be enabled in U and S mode by writing a 1 to [s,u]seed in mseccfg and reading back the result.
RULE 4: The mseccfg.[s,u]seed option is a direct option.
RULE 5: The mseccfg.[s,u]seed option allows one to draw a security boundary around a component in relation to Sensitive Security Parameter (SSP) flows.
RULE 6: The mseccfg.[s,u]seed option allows the security boundary to be drawn even if the component is not in M mode.
RULE 7: The mseccfg.[s,u]seed option is helpful when implementing trusted enclaves.
RULE 8: Using mseccfg.[s,u]seed, such modules can enforce the entire key lifecycle from birth in the entropy source to death by zeroization without the key being passed across the boundary to external code.
RULE 9: If a CSR instruction uses CSR address 0x747, then it accesses mseccfg, so reading CSR 0x747 returns the current mseccfg value and writing CSR 0x747 updates mseccfg.
RULE 10: mseccfg has privilege value MRW.
RULE 11: If any extension that adds a field to mseccfg is implemented, then CSR accesses to mseccfg are legal and complete without an illegal-instruction exception; if no such extension is implemented, then any CSR read or write access to mseccfg raises an illegal-instruction exception.
RULE 12: If mseccfg.SSEED=0, an S-mode read of the seed CSR raises an illegal-instruction exception, while if mseccfg.SSEED=1 that read completes and returns the seed CSR value; if mseccfg.USEED=0, a U-mode read of the seed CSR raises an illegal-instruction exception, while if mseccfg.USEED=1 that read completes and returns the seed CSR value; M-mode reads of the seed CSR are not gated by SSEED or USEED.
RULE 13: When mseccfg.USEED is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 14: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed; all other types of accesses raise an illegal-instruction exception.
RULE 15: When mseccfg.SSEED is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 16: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-/HS-mode is allowed; all other types of accesses raise an illegal-instruction exception.
RULE 17: Under mseccfg entropy access control, in U-mode with USEED=0, any seed CSR access raises an illegal-instruction exception.
RULE 18: Under mseccfg entropy access control, in U-mode with USEED=1, the seed CSR is accessible as normal and no exception is raised for read-write.
RULE 19: Under mseccfg entropy access control, in S/HS-mode with SSEED=0, any seed CSR access raises an illegal-instruction exception.
RULE 20: Under mseccfg entropy access control, in S/HS-mode with SSEED=1, the seed CSR is accessible as normal and no exception is raised for read-write.
RULE 21: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 22: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any rule or entry, including disabled entries, mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 23: mseccfg.MMWP is a sticky bit, meaning once set it cannot be unset until a PMP reset; when set, it changes the default M-mode PMP policy for regions without a matching PMP rule from ignored to denied.
RULE 24: mseccfg.MML is a sticky bit, meaning once set it cannot be unset until a PMP reset.
RULE 25: When mseccfg.MML is set, pmpcfg.L marks a rule as M-mode-only when set and S/U-mode-only when unset, instead of marking the rule as locked and enforced in all modes.
RULE 26: If mseccfg.MML is set, then a PMP entry with pmpcfg.RW=01 or pmpcfg.LRWX=1111 is decoded as a Shared-Region rather than as a reserved encoding, observable by the entry being accepted/read back as that encoding with MML still set; if mseccfg.MML is clear, those encodings are not decoded as a Shared-Region.
RULE 27: Under mseccfg.MML, an M-mode-only rule is enforced on Machine mode and denied in Supervisor or User mode, and it remains locked so further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 28: Under mseccfg.MML, an S/U-mode-only rule is enforced on Supervisor and User modes and denied on Machine mode.
RULE 29: If mseccfg.MML=1 and a PMP entry is configured as a Shared Region by its pmpcfg.L and pmpcfg.X bits, then that Shared-Region restriction is enforced in both M-mode and S/U-mode: an access that violates the entry’s Shared-Region permissions raises the corresponding instruction-access fault, load-access fault, or store/AMO-access fault (mcause 1, 5, or 7) and does not modify architectural state, while an access permitted by the Shared-Region rule completes normally.
RULE 30: Under mseccfg.MML, a Shared-Region rule where pmpcfg.L is not set can share data between M-mode and S/U-mode, is not executable, gives M-mode read/write access, and gives S/U-mode read access if pmpcfg.X is not set or read/write access if pmpcfg.X is set.
RULE 31: Under mseccfg.MML, a Shared-Region rule where pmpcfg.L is set can share code between M-mode and S/U-mode, is not writable, both M-mode and S/U-mode have execute access, M-mode also has read access if pmpcfg.X is set, and the rule remains locked so further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 32: Under mseccfg.MML, the encoding pmpcfg.LRWX=1111 can share data between M-mode and S/U-mode where both modes only have read-only access, and the rule remains locked so further modifications to its associated configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 33: Under mseccfg.MML, adding a rule with executable privileges that is either M-mode-only or a locked Shared-Region is not possible, and such pmpcfg writes are ignored leaving pmpcfg unchanged; this restriction can be temporarily lifted by setting mseccfg.RLB, e.g. during boot.
RULE 34: Under mseccfg.MML, executing code with Machine-mode privileges is only possible from memory regions with a matching M-mode-only rule or a locked Shared-Region rule with executable privileges; executing from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 35: If Smmpm is not implemented, then any write to mseccfg.PMM is ignored and mseccfg.PMM reads back as 0; if Smmpm is implemented, then mseccfg.PMM is writable, its readback value reflects the PMM setting, and that setting enables or disables M-mode pointer masking as specified by Table 21.
RULE 36: For mseccfg.PMM, legal WARL value 01 is reserved.
RULE 37: With Zicfilp implemented, mseccfg includes the MLPE field, and if mseccfg.MLPE reads as 1 then Zicfilp is enabled in M-mode, while if mseccfg.MLPE reads as 0 then Zicfilp is disabled in M-mode, observable from mseccfg.MLPE CSR readback and whether M-mode Zicfilp enforcement occurs.
RULE 38: When mseccfg.MLPE is 0, Zicfilp is not enabled in M-mode, the hart does not update the ELP state and it remains NO_LP_EXPECTED, and the LPAD instruction operates as a no-op.
RULE 39: If the Zicfilp extension is implemented, the mseccfg.MLPE field is reset to 0.
RULE 40: When mseccfg.MML is set to 1, a matching PMP entry’s L/R/W/X bits select M-mode and S/U-mode permissions from the MML truth table, and if an access is not permitted by that selected permission then it raises a load access-fault, store/AMO access-fault, or instruction access-fault according to the access type and does not update the load destination register or memory.
RULE 41: When mseccfg.MML is 1 and pmpcfg L=0, R=0, W=0, X=0, the region is inaccessible in both M-mode and S/U-mode, with an access exception.
RULE 42: When mseccfg.MML is 1 and pmpcfg L=0, R=0, W=0, X=1, M-mode gets an access exception and S/U-mode gets an execute-only region.
RULE 43: When mseccfg.MML is 1 and pmpcfg L=0, R=0, W=1, X=0, the result is a shared data region: read/write on M-mode and read-only on S/U-mode.
RULE 44: When mseccfg.MML is 1 and pmpcfg L=0, R=0, W=1, X=1, the result is a shared data region: read/write for both M-mode and S/U-mode.
RULE 45: When mseccfg.MML is 1 and pmpcfg L=0, R=1, W=0, X=0, M-mode gets an access exception and S/U-mode gets a read-only region.
RULE 46: When mseccfg.MML is 1 and pmpcfg L=0, R=1, W=0, X=1, M-mode gets an access exception and S/U-mode gets a read/execute region.
RULE 47: When mseccfg.MML is 1 and pmpcfg L=0, R=1, W=1, X=0, M-mode gets an access exception and S/U-mode gets a read/write region.
RULE 48: When mseccfg.MML is 1 and pmpcfg L=0, R=1, W=1, X=1, M-mode gets an access exception and S/U-mode gets a read/write/execute region.
RULE 49: When mseccfg.MML is 1 and pmpcfg L=1, R=0, W=0, X=0, the result is a locked inaccessible region* with an access exception in both M-mode and S/U-mode.
RULE 50: When mseccfg.MML is 1 and pmpcfg L=1, R=0, W=0, X=1, M-mode gets a locked execute-only region* and S/U-mode gets an access exception.
RULE 51: When mseccfg.MML is 1 and pmpcfg L=1, R=0, W=1, X=0, the result is a locked shared code region: execute-only on both M-mode and S/U-mode*.
RULE 52: When mseccfg.MML is 1 and pmpcfg L=1, R=0, W=1, X=1, the result is a locked shared code region: execute-only on S/U-mode and read/execute on M-mode*.
RULE 53: When mseccfg.MML is 1 and pmpcfg L=1, R=1, W=0, X=0, M-mode gets a locked read-only region* and S/U-mode gets an access exception.
RULE 54: When mseccfg.MML is 1 and pmpcfg L=1, R=1, W=0, X=1, M-mode gets a locked read/execute region* and S/U-mode gets an access exception.
RULE 55: When mseccfg.MML is 1 and pmpcfg L=1, R=1, W=1, X=0, M-mode gets a locked read/write region* and S/U-mode gets an access exception.
RULE 56: When mseccfg.MML is 1 and pmpcfg L=1, R=1, W=1, X=1, the result is a locked shared data region: read-only on both M-mode and S/U-mode*.
RULE 57: When S-mode is implemented, xLPE at privilege mode M is determined by mseccfg.MLPE.
RULE 58: If mseccfg.MLPE is 1, then xLPE for M-mode is 1; if mseccfg.MLPE is 0, then xLPE for M-mode is 0, observable through the mseccfg.MLPE readback value and the resulting M-mode PMP lock/permission enforcement.
RULE 59: For the current privilege mode, if its xLPE state is 0, then Zicfilp forward-edge CFI landing-pad checking is disabled in that mode and a control transfer whose target lacks a valid landing pad does not raise the Zicfilp software-check exception; if its xLPE state is 1, then landing-pad checking is enabled and such a control transfer raises the Zicfilp software-check exception; for M-mode, xLPE is mseccfg.MLPE, so mseccfg.MLPE=0 disables and mseccfg.MLPE=1 enables the M-mode landing-pad check.
RULE 60: If Zicfilp is not explicitly enabled for the current privilege mode, then Zicfilp is inactive in that mode and no Zicfilp enforcement occurs there; for M-mode, this is observed when mseccfg.MLPE reads 0, and M-mode Zicfilp remains inactive until mseccfg.MLPE is set to 1.
RULE 61: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 62: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 63: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 64: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 65: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 66: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 67: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 68: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 69: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 70: In M-mode, accessing mseccfg register while Zicfilp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zicfilp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 71: In M-mode, accessing mseccfg register while Zkr extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zkr; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
NUMBER: 0x300
MODE: M-mode
WIDTH: MXLEN
FIELDS: 63..63=SD, 42..42=MDT, 41..41=MPELP, 39..39=MPV, 38..38=GVA, 37..37=MBE, 36..36=SBE, 35..34=SXL, 33..32=UXL, 23..23=SPELP, 22..22=TSR, 21..21=TW, 20..20=TVM, 19..19=MXR, 18..18=SUM, 17..17=MPRV, 16..15=XS, 14..13=FS, 12..11=MPP, 10..9=VS, 8..8=SPP, 7..7=MPIE, 6..6=UBE, 5..5=SPIE, 3..3=MIE, 1..1=SIE
EXTENSIONS: F, H, Smdbltrp, Smrnmi, Ssdbltrp, V, Zfinx, Zicfilp
RULE 1: If M-mode software writes mstatus.TW (bit 21) to 1 and reads mstatus, the TW readback value is 1, and if TW=1 when WFI executes in a mode less privileged than M-mode and the WFI does not complete within the implementation-specific bounded time, the WFI raises an illegal-instruction exception.
RULE 2: If mstatus.TW is set, WRS.NTO is executed in any privilege mode other than M mode, and WRS.NTO does not complete within the implementation-specific bounded time limit, then WRS.NTO raises an illegal-instruction exception instead of completing normally.
RULE 3: mstatus has a vector context status field named mstatus.VS located at mstatus[10:9].
RULE 4: mstatus.VS is shadowed in sstatus[10:9].
RULE 5: When the vector extension is implemented, mstatus.VS is a 2-bit read/write field analogous to mstatus.FS: writing a value 0–3 to mstatus.VS makes a subsequent mstatus read return that value until a vector-state-modifying instruction changes it, and if mstatus.VS is Off (0) when a vector instruction is executed, that instruction raises an illegal-instruction exception, whereas if mstatus.VS is nonzero, vector instructions execute and any instruction that modifies vector state sets mstatus.VS to Dirty (3).
RULE 6: Attempts to execute any vector instruction, or to access the vector CSRs, raise an illegal-instruction exception when mstatus.VS is set to Off.
RULE 7: When mstatus.VS is set to Initial or Clean, executing any instruction that changes vector state, including the vector CSRs, will change mstatus.VS to Dirty.
RULE 8: If mstatus.VS is Dirty (3), then a read of mstatus returns mstatus.SD = 1; otherwise, a read of mstatus returns the mstatus.SD value defined by the existing specification and is not forced to 1 by this rule.
RULE 9: If the hypervisor extension is present and V=1, then a vector instruction executed with either vsstatus.VS=Off or mstatus.VS=Off raises an illegal-instruction exception; vector state is enabled only when both vsstatus.VS and mstatus.VS are non-Off.
RULE 10: When V=1, attempts to execute any vector instruction or to access the vector CSRs raise an illegal-instruction exception when either mstatus.VS or vsstatus.VS is set to Off.
RULE 11: When V=1 and neither mstatus.VS nor vsstatus.VS is set to Off, executing any instruction that changes vector state, including the vector CSRs, will change both mstatus.VS and vsstatus.VS to Dirty.
RULE 12: If mstatus.VS is Dirty, then mstatus.SD is 1.
RULE 13: If mstatus.VS is not Dirty, then a read of mstatus returns mstatus.SD as 1 exactly when mstatus.FS is Dirty or mstatus.XS is Dirty (with mstatus.VS contributing 0); if the returned SD has any other value, the mstatus dirty-summary behavior violates the specification.
RULE 14: If the floating-point unit status field mstatus.FS is Off, any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 15: Any vector floating-point instruction that modifies any floating-point extension state (i.e., floating-point CSRs or f registers) must set mstatus.FS to Dirty.
RULE 16: When the hypervisor extension is implemented and V=1, a vector floating-point instruction is subject to both mstatus.FS and vsstatus.FS: if either field is Off, the instruction raises an illegal-instruction exception with mcause=2; if neither field is Off, the instruction proceeds with its normal architectural effects and does not raise an illegal-instruction exception due to FS.
RULE 17: If the hypervisor extension is implemented and V=1, and either vsstatus.FS or mstatus.FS is Off, any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 18: If the hypervisor extension is implemented and V=1, any vector floating-point instruction that modifies any floating-point extension state (i.e., floating-point CSRs or f registers) must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 19: If an instruction uses CSR address 0x300, then in M-mode it accesses the machine-level CSR mstatus; if CSR address 0x300 is accessed from S-mode or U-mode, the access raises an illegal-instruction exception.
RULE 20: If an instruction reads or writes mstatus from S-mode or U-mode, it raises an illegal-instruction exception; from M-mode, CSR reads return the current mstatus value and CSR writes update the writable mstatus fields.
RULE 21: If a CSR instruction encodes address 0x300, then it accesses mstatus, so a read of CSR 0x300 returns the mstatus value and a write to CSR 0x300 updates mstatus.
RULE 22: A CSR read of mstatus returns the MXLEN-bit mstatus value, and a CSR write to mstatus updates that MXLEN-bit value; if an access to mstatus is not readable or writable as an MXLEN-bit register, it raises an illegal-instruction exception.
RULE 23: If software writes a supported value to a writable mstatus field that controls the hart's current operating state, then a subsequent read of mstatus returns that value in that field and the hart's operating state follows that field; if the written value is not supported by a WARL field, then mstatus readback contains the implementation-selected legal value instead.
RULE 24: If software in S-mode writes a field that is visible in sstatus, then the corresponding mstatus field is updated and a subsequent read of sstatus returns that updated value, while a write to sstatus does not change any mstatus field that is not visible through sstatus.
RULE 25: For RV64, a read of mstatus exposes the SD field in bit 63, so if the architectural SD value is 1 then mstatus[63] reads as 1 and if the architectural SD value is 0 then mstatus[63] reads as 0; a readback where mstatus[63] differs from the SD value violates the RV64 mstatus SD-field location.
RULE 26: For RV64, an mstatus CSR read returns the MPELP field value in bit 41; if bit 41 of the mstatus readback differs from the MPELP field value, the bit-41 MPELP field location is violated.
RULE 27: For RV64, the mstatus.MPV field is observable in mstatus bit 39: if mstatus.MPV is 1, then a read of mstatus returns bit 39 set to 1, and if mstatus.MPV is 0, then a read of mstatus returns bit 39 set to 0; a readback where bit 39 does not equal MPV violates the RV64 mstatus.MPV field mapping.
RULE 28: For RV64 mstatus, bits 35:34 are the SXL[1:0] field.
RULE 29: For RV64 mstatus, bits 33:32 are the UXL[1:0] field.
RULE 30: mstatus provides global interrupt-enable bits MIE for M-mode and SIE for S-mode.
RULE 31: In mstatus, the global xIE bits are located in the low-order bits, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 32: In mstatus, xPIE holds the value of the interrupt-enable bit active prior to the trap.
RULE 33: If a trap is taken into privilege mode x, then mstatus.xPP is set to the privilege mode active immediately before the trap, so reading mstatus after the trap returns that previous privilege mode in xPP.
RULE 34: If a write to mstatus attempts to set MPP or SPP to a privilege-mode value wider than the implemented field, then the field does not hold the excess value: a subsequent mstatus readback shows MPP only as the 2-bit field in mstatus[12:11] and SPP only as the 1-bit field in mstatus[8].
RULE 35: In mstatus, when a trap is taken from privilege mode y into privilege mode x, xPIE is set to the value of xIE, xIE is set to 0, and xPP is set to y.
RULE 36: In mstatus, when an MRET or SRET instruction executes, supposing xPP holds the value y, xIE is set to xPIE, the privilege mode is changed to y, xPIE is set to 1, and xPP is set to the least-privileged supported mode (U if U-mode is implemented, else M).
RULE 37: In mstatus, if y ≠ M during an xRET, xRET also sets MPRV=0.
RULE 38: If an xRET executes, then after the xRET the xPP field in the corresponding status CSR reads the least-privileged supported mode (U if U-mode is implemented, otherwise M); if the readback differs, the xRET has violated the architectural xPP update rule.
RULE 39: In mstatus, xPP fields are WARL fields that can hold only privilege mode x and any implemented privilege mode lower than x.
RULE 40: M-mode software can determine whether a privilege mode is implemented by writing that mode to MPP in mstatus and then reading it back.
RULE 41: When the mstatus CSR is read, the returned value contains the Machine Interrupt Enable (MIE) bit in the mstatus.MIE field, and that bit reflects the current machine interrupt enable state.
RULE 42: The MIE bit in mstatus can only be set to 1 by an explicit CSR write if MDT is already 0 or, for RV64, is being set to 0 by the same write.
RULE 43: For MRET or SRET executed in M-mode that clear the mstatus-associated MDT bit, if the new privilege mode is U, VS, or VU, sstatus.SDT is also set to 0; if the new privilege mode is VU, vsstatus.SDT is also set to 0.
RULE 44: If mstatus.SXL or mstatus.UXL reads back an encoding value, then that value has the same XLEN interpretation as the identical value in misa.MXL (1 = 32-bit, 2 = 64-bit, 3 = 128-bit); a readback encoding that does not match the misa.MXL encoding for that XLEN is a violation observable through the CSR value.
RULE 45: If MXLEN=64 and S-mode is supported, then mstatus.SXL is a WARL field that reads back the implementation-supported encoding of the current SXLEN: a write of a supported encoding updates SXLEN and reads back that same encoding, while a write of an unsupported encoding raises no exception, is legalized to a supported encoding, and a subsequent read of mstatus.SXL returns that legal encoding.
RULE 46: When MXLEN=64 and U-mode is supported, if software writes mstatus.UXL, then the write does not raise an illegal-instruction exception solely because the written UXL encoding is unsupported; mstatus.UXL reads back a supported encoding, and UXLEN is the value encoded by that readback, with a write of a supported encoding reading back unchanged.
RULE 47: If S-mode is implemented, the set of legal values that the UXL field in mstatus may assume excludes those that would cause UXLEN to be greater than SXLEN.
RULE 48: In mstatus, the MPRV bit modifies the effective privilege mode, i.e., the privilege level at which explicit memory accesses execute.
RULE 49: In mstatus, an MRET or SRET instruction that changes the privilege mode to a mode less privileged than M also sets MPRV=0.
RULE 50: In mstatus, the MXR and SUM mechanisms have no impact on whether access-fault exceptions are raised due to PMAs or PMP.
RULE 51: The MBE bit in mstatus controls whether non-instruction-fetch memory accesses made from M-mode, assuming mstatus.MPRV=0, are little-endian when MBE=0 or big-endian when MBE=1.
RULE 52: If S-mode is supported, the SBE bit in mstatus controls whether explicit load and store memory accesses made from S-mode are little-endian when SBE=0 or big-endian when SBE=1.
RULE 53: If U-mode is supported, the UBE bit in mstatus controls whether explicit load and store memory accesses made from U-mode are little-endian when UBE=0 or big-endian when UBE=1.
RULE 54: An implementation supports only little-endian memory accesses if the MBE, SBE, and UBE fields in mstatus are all read-only 0.
RULE 55: An implementation supports only big-endian memory accesses, aside from instruction fetches, if the MBE bit in mstatus is read-only 1 and the SBE and UBE bits in mstatus are each read-only 1 when S-mode and U-mode are supported.
RULE 56: If the mstatus endianness mode is changed, byte loads and stores still access the same byte at each address, while halfword and word loads and stores map the consecutive memory bytes to or from the multibyte value in the selected endian order, so the loaded destination register value or the bytes written by a store reflect that order without changing the address-to-byte correspondence.
RULE 57: If a write to mstatus.TVM leaves mstatus.TVM reading as 1, then an S-mode supervisor virtual-memory management operation, including a read or write of satp and execution of SFENCE.VMA, raises an illegal-instruction exception (mcause/scause=2 according to trap delegation) instead of performing the operation; if mstatus.TVM reads as 0, TVM does not intercept those operations.
RULE 58: When mstatus.TVM=1, attempts to read or write the satp CSR or execute an SFENCE.VMA or SINVAL.VMA instruction while executing in S-mode will raise an illegal-instruction exception.
RULE 59: When mstatus.TVM=0, reads or writes of satp and execution of SFENCE.VMA or SINVAL.VMA are permitted in S-mode.
