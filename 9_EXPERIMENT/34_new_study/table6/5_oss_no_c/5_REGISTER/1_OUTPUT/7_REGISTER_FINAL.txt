REGISTER: mseccfg
NUMBER: 0x747
MODE: M-mode
WIDTH: 64
FIELDS: 33..32=PMM, 10..10=MLPE, 9..9=SSEED, 8..8=USEED, 2..2=RLB, 1..1=MMWP, 0..0=MML
EXTENSIONS: Smepmp, Smmpm, Zicfilp, Zkr
RULE 1: Software may discover if access to the seed CSR can be enabled in U and S mode by writing a 1 to the SSEED or USEED field of the mseccfg CSR and reading back the result.
RULE 2: The mseccfg CSR is a Machine-mode read/write (MRW) register.
RULE 3: The upper 32 bits of the mseccfg register are accessed through the CSR named mseccfgh located at address 0x757.
RULE 4: mseccfg is a 64-bit read/write register.
RULE 5: If no implemented extension defines a field in the mseccfg CSR, then any CSR read or write of address 0x301 (mseccfg) raises an illegal‑instruction exception (mcause = 2).
RULE 6: When mseccfg.USEED is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 7: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed.
RULE 8: When mseccfg.USEED is 1, all other types of accesses to the seed CSR from U-mode raise an illegal-instruction exception.
RULE 9: When mseccfg.SSEED is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 10: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-/HS-mode is allowed.
RULE 11: When mseccfg.SSEED is 1, all other types of accesses to the seed CSR from S-/HS-mode raise an illegal-instruction exception.
RULE 12: When the H extension is also implemented, all other types of accesses to the seed CSR raise an illegal-instruction exception.
RULE 13: In machine mode, mseccfg does not restrict access to the seed CSR; the seed CSR is always available as a normal read-write CSR and a read without a write raises an illegal-instruction exception regardless of mseccfg field values.
RULE 14: In U-mode with mseccfg.USEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 15: In U-mode with mseccfg.USEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 16: In S-/HS-mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 17: In S-/HS-mode with mseccfg.SSEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 18: In VS/VU mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 19: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 20: When mseccfg.RLB is 0 and any pmpcfg.L is 1 in any rule or entry (including disabled entries), mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 21: mseccfg.MMWP changes the default PMP policy for Machine mode when accessing memory regions that do not have a matching PMP rule.
RULE 22: mseccfg.MMWP is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 23: When mseccfg.MMWP is set, the default PMP policy for M-mode for unmatched regions becomes denied instead of ignored.
RULE 24: mseccfg.MML is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 25: When mseccfg.MML is set, the meaning of pmpcfg.L changes so that it marks a rule as M-mode-only when set and as S/U-mode-only when unset.
RULE 26: When mseccfg.MML is set, the previously reserved encoding pmpcfg.RW = 01 and the encoding pmpcfg.LRWX = 1111 now encode a Shared-Region.
RULE 27: An M-mode-only rule (when mseccfg.MML is set) is enforced on Machine mode, denied on Supervisor and User modes, and remains locked so that any further modifications to its configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 28: If mseccfg.MML = 1 and the current privilege mode is Machine, then executing any Supervisor‑or‑User‑mode‑only instruction raises an illegal‑instruction exception; in Supervisor or User mode the same instruction executes normally without exception.
RULE 29: A Shared-Region rule with pmpcfg.L not set (when mseccfg.MML is set) permits data sharing between M-mode and S/U-mode, is not executable, gives M-mode read/write access, and gives S/U-mode read access unless pmpcfg.X is set, in which case S/U-mode has read/write access.
RULE 30: A Shared-Region rule with pmpcfg.L set (when mseccfg.MML is set) permits code sharing between M-mode and S/U-mode, is not writable, gives both modes execute access, gives M-mode read access if pmpcfg.X is set, and remains locked unless mseccfg.RLB is set.
RULE 31: A Shared-Region rule with pmpcfg.LRWX = 1111 (when mseccfg.MML is set) permits data sharing between M-mode and S/U-mode with both modes read-only access and remains locked unless mseccfg.RLB is set.
RULE 32: Adding a pmpcfg write that would create an executable M-mode-only or a locked Shared-Region rule is not possible; such writes are ignored and pmpcfg remains unchanged.
RULE 33: If an instruction fetch in Machine mode targets a memory region that is neither marked as M‑mode‑only nor a locked Shared‑Region with executable privilege, then an instruction‑access‑fault exception is raised and mcause is set to the instruction‑access‑fault code.
RULE 34: Executing code from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 35: If the Smmpm extension is not implemented, the PMM field in mseccfg is read-only zero.
RULE 36: PMM field value 00 in mseccfg indicates pointer masking is disabled (PMLEN = 0).
RULE 37: PMM field value 10 in mseccfg indicates pointer masking is enabled with PMLEN = XLEN - 57 (PMLEN = 7 on RV64).
RULE 38: PMM field value 11 in mseccfg indicates pointer masking is enabled with PMLEN = XLEN - 48 (PMLEN = 16 on RV64).
RULE 39: When the Zicfilp extension is present, the MLPE field in mseccfg being 1 enables the Zicfilp extension in M-mode.
RULE 40: If the Zicfilp extension is implemented, the MLPE field of the mseccfg register is reset to 0.
RULE 41: The MML field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 42: The MMWP field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 43: The RLB field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 44: When mseccfg.MML = 1 and the PMP configuration bits L, R, W, X are all zero, any access in either M-mode or S/U-mode is an inaccessible region that raises an access exception.
RULE 45: When mseccfg.MML = 1, L = 0, R = 0, W = 0, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted only as an execute-only region.
RULE 46: When mseccfg.MML = 1, L = 0, R = 0, W = 1, X = 0, M-mode accesses are allowed to read and write the shared data region, and S/U-mode accesses are allowed to read only.
RULE 47: When mseccfg.MML = 1, L = 0, R = 0, W = 1, X = 1, both M-mode and S/U-mode accesses are allowed to read and write the shared data region.
RULE 48: When mseccfg.MML = 1, L = 0, R = 1, W = 0, X = 0, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-only region.
RULE 49: When mseccfg.MML = 1, L = 0, R = 1, W = 0, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-execute region.
RULE 50: When mseccfg.MML = 1, L = 0, R = 1, W = 1, X = 0, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-write region.
RULE 51: When mseccfg.MML = 1, L = 0, R = 1, W = 1, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-write-execute region.
RULE 52: When mseccfg.MML = 1, L = 1, R = 0, W = 0, X = 0, any access in either M-mode or S/U-mode is a locked inaccessible region that raises an access exception.
RULE 53: When mseccfg.MML = 1, L = 1, R = 0, W = 0, X = 1, M-mode accesses are limited to a locked execute-only region, whereas S/U-mode accesses raise an access exception.
RULE 54: When mseccfg.MML = 1, L = 1, R = 0, W = 1, X = 0, both M-mode and S/U-mode accesses are limited to a locked shared code region that permits execution only.
RULE 55: When mseccfg.MML = 1, L = 1, R = 0, W = 1, X = 1, M-mode accesses are permitted as read/execute in a locked shared code region, while S/U-mode accesses are limited to execution only in the same locked region.
RULE 56: When mseccfg.MML = 1, L = 1, R = 1, W = 0, X = 0, M-mode accesses are permitted as a locked read-only region, while S/U-mode accesses raise an access exception.
RULE 57: When mseccfg.MML = 1, L = 1, R = 1, W = 0, X = 1, M-mode accesses are permitted as a locked read/execute region, while S/U-mode accesses raise an access exception.
RULE 58: When mseccfg.MML = 1, L = 1, R = 1, W = 1, X = 0, M-mode accesses are permitted as a locked read/write region, while S/U-mode accesses raise an access exception.
RULE 59: If mseccfg.MML = 1 and mseccfg.L = 1 and mseccfg.R = 1 and mseccfg.W = 1 and mseccfg.X = 1, then any load, store, AMO, or instruction‑fetch executed in M‑mode or S/U‑mode to an address outside the locked shared region raises a load‑access‑fault (mcause = 5) or store/AMO‑access‑fault (mcause = 7) exception as appropriate, and any store or AMO to an address inside the locked shared region raises a store‑access‑fault (mcause = 7) exception.
RULE 60: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 61: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 62: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 63: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 64: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 65: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 66: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 67: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 68: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 69: In M-mode, accessing mseccfg register while Zicfilp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zicfilp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 70: In M-mode, accessing mseccfg register while Zkr extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zkr; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
NUMBER: 0x300
MODE: M-mode
WIDTH: MXLEN
FIELDS: 63..63=SD, 42..42=MDT, 41..41=MPELP, 39..39=MPV, 38..38=GVA, 37..37=MBE, 36..36=SBE, 35..34=SXL, 33..32=UXL, 23..23=SPELP, 22..22=TSR, 21..21=TW, 20..20=TVM, 19..19=MXR, 18..18=SUM, 17..17=MPRV, 16..15=XS, 14..13=FS, 12..11=MPP, 10..9=VS, 8..8=SPP, 7..7=MPIE, 6..6=UBE, 5..5=SPIE, 3..3=MIE, 1..1=SIE
EXTENSIONS: H, Smdbltrp, V, Zdinx, Zfinx, Zhinx, Zicboz, Zicfilp
RULE 1: Bits 10-9 of sstatus contain a shadow copy of the VS field of mstatus.
RULE 2: When mstatus.VS is Off, executing any vector instruction raises an illegal-instruction exception.
RULE 3: When mstatus.VS is Off, accessing a vector CSR raises an illegal-instruction exception.
RULE 4: When mstatus.VS is Initial or Clean, executing any instruction that changes vector state, including accesses to vector CSRs, sets mstatus.VS to Dirty.
RULE 5: If mstatus.VS is Dirty, mstatus.SD is set to 1.
RULE 6: If mstatus.VS is not Dirty, then mstatus.SD is 1 iff either mstatus.FS or mstatus.XS is Dirty (otherwise mstatus.SD is 0).
RULE 7: When V=1 and either vsstatus.VS or mstatus.VS is Off, any attempt to execute a vector instruction or to access a vector CSR must raise an illegal-instruction exception.
RULE 8: When V=1 and both vsstatus.VS and mstatus.VS are not Off, executing any instruction that changes vector state, including accesses to vector CSRs, must set both mstatus.VS and vsstatus.VS to Dirty.
RULE 9: If mstatus.VS is Dirty, then mstatus.SD must be 1.
RULE 10: If mstatus.FS is Off then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 11: Any vector floating-point instruction that modifies any floating-point extension state must set mstatus.FS to Dirty.
RULE 12: If either vsstatus.FS or mstatus.FS is Off then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 13: Any vector floating-point instruction that modifies any floating-point extension state must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 14: The mstatus CSR is a machine-mode register that is readable and writable (MRW).
RULE 15: Bits 30:4 of mstatush generally contain the same fields found in bits 62:36 of mstatus for RV64.
RULE 16: The global interrupt-enable bits MIE and SIE reside in the low-order bits of mstatus, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 17: When a trap is taken from privilege mode y into privilege mode x, the xPIE field in mstatus is set to the current value of xIE, the xIE field in mstatus is cleared to zero, and the xPP field in mstatus is written with the value y.
RULE 18: An xRET instruction (MRET or SRET) sets the xIE field in mstatus to the value of xPIE when the xPP field holds the previous mode y.
RULE 19: An xRET instruction updates the architectural privilege mode stored in mstatus to the value held in the xPP field.
RULE 20: An xRET instruction sets the xPIE field in mstatus to 1.
RULE 21: An xRET instruction writes the xPP field in mstatus with the least-privileged supported mode, which is U if user mode is implemented otherwise M.
RULE 22: If the previous privilege mode y is not M, an xRET instruction also clears the MPRV field in mstatus to 0.
RULE 23: Each xPP field in mstatus is a WARL field that may contain only the privilege mode x or any implemented privilege mode lower than x.
RULE 24: Machine-mode software can test the implementation of a privilege mode by writing that mode into the MPP field of mstatus and then reading the field back.
RULE 25: Upon reset, the MDT field in mstatus is set to 1.
RULE 26: When the MDT bit in mstatus is set to 1 by an explicit CSR write, the MIE bit in mstatus is cleared to 0.
RULE 27: If a trap is taken into M-mode while the MDT bit in mstatus is 0, the MDT bit is set to 1 before the trap is delivered.
RULE 28: In mstatus for RV64 harts, the SXL and UXL fields are WARL fields that control the XLEN value used in S-mode and U-mode respectively.
RULE 29: The encoding of the SXL and UXL fields in mstatus matches the encoding of the MXL field in the misa register.
RULE 30: If S-mode is supported and MXLEN = 64, the SXL field in mstatus is a WARL field that encodes the current SXLEN value.
RULE 31: An implementation may make the SXL field in mstatus read-only such that its value always forces SXLEN to equal MXLEN.
RULE 32: If U-mode is supported and MXLEN = 64, the UXL field in mstatus is a WARL field that encodes the current UXLEN value.
RULE 33: If a program writes a value to the UXL field of mstatus that would make UXLEN differ from both MXLEN and SXLEN, then the write is ignored and reading mstatus.UXL (and the resulting UXLEN) returns a value that forces UXLEN to equal either MXLEN or SXLEN.
RULE 34: When S-mode is implemented, the set of legal values that the UXL field in mstatus may assume excludes any value that would cause UXLEN to be greater than SXLEN.
RULE 35: Whenever XLEN in any privilege mode is configured via mstatus to a value less than the widest supported XLEN, all operations must ignore source-operand register bits above the configured XLEN and must sign-extend results to fill the entire widest supported XLEN in the destination register.
RULE 36: When XLEN in any privilege mode is configured via mstatus to a value less than the widest supported XLEN, PC bits above the configured XLEN are ignored and when the PC is written it must be sign-extended to fill the widest supported XLEN.
RULE 37: The MPRV field in mstatus modifies the effective privilege mode at which explicit memory accesses execute.
RULE 38: When the MPRV field in mstatus is 0, explicit memory accesses behave normally using the translation and protection mechanisms of the current privilege mode.
RULE 39: When the MPRV field in mstatus is 1, load and store memory addresses are translated, protected, and have endianness applied as if the current privilege mode were set to the value in the MPP field of mstatus.
RULE 40: Instruction address-translation and protection are unaffected by the setting of the MPRV field in mstatus.
RULE 41: Executing an MRET or SRET instruction that changes the privilege mode to a mode less privileged than machine mode also sets the MPRV field in mstatus to zero.
RULE 42: The MXR field in mstatus modifies the privilege with which load instructions access virtual memory.
RULE 43: When the MXR field in mstatus is 1, loads from pages marked readable (R=1) or executable (X=1) will succeed.
RULE 44: The MXR field in mstatus has no effect when page-based virtual memory is not in effect.
RULE 45: The SUM field in mstatus modifies the privilege with which supervisor-mode loads and stores access virtual memory.
RULE 46: When the SUM field in mstatus is 0, supervisor-mode memory accesses to pages that are accessible by user mode (U=1) will fault.
RULE 47: When the SUM field in mstatus is 1, supervisor-mode memory accesses to pages that are accessible by user mode (U=1) are permitted.
RULE 48: The SUM field in mstatus has no effect when page-based virtual memory is not in effect.
RULE 49: The SUM field in mstatus is in effect when MPRV is 1 and the MPP field is set to supervisor mode, even if the current execution mode is not supervisor mode.
RULE 50: The MXR and SUM fields in mstatus have no impact on whether access-fault exceptions are raised due to physical memory attributes or the physical memory protection subsystem.
RULE 51: The MBE, SBE, and UBE bits in mstatus (and mstatush) are WARL fields that control the endianness of memory accesses other than instruction fetches.
RULE 52: Instruction fetches are always little-endian regardless of the values of the fields in mstatus.
RULE 53: When mstatus.MPRV=0, the MBE bit in mstatus determines whether non-instruction-fetch memory accesses from M-mode are little-endian (MBE=0) or big-endian (MBE=1).
RULE 54: When supervisor mode is supported, the SBE bit in mstatus determines whether explicit load and store accesses from S-mode are little-endian (SBE=0) or big-endian (SBE=1).
RULE 55: When user mode is supported, the UBE bit in mstatus determines whether explicit load and store accesses from U-mode are little-endian (UBE=0) or big-endian (UBE=1).
RULE 56: For implicit accesses to supervisor-level memory-management data structures, such as page tables, the endianness is always controlled by the SBE bit in mstatus.
RULE 57: An implementation supports only little-endian memory accesses (aside from instruction fetches) when the MBE, SBE, and UBE bits in mstatus are all read-only 0.
RULE 58: An implementation supports only big-endian memory accesses (aside from instruction fetches) when MBE is read-only 1 and, if supervisor mode and user mode are supported, SBE and UBE are each read-only 1 in mstatus.
RULE 59: If a value with an illegal encoding is written to the TVM field in mstatus, then a subsequent read of mstatus returns a legal TVM encoding (the hardware may mask or adjust the field to a permitted value) and no exception is raised.
RULE 60: When the TVM field in mstatus is 1, attempts to read or write the satp CSR or to execute an SFENCE.VMA or SINVAL.VMA instruction while executing in S-mode raise an illegal-instruction exception.
RULE 61: When the TVM field in mstatus is 0, reads or writes of the satp CSR and execution of SFENCE.VMA or SINVAL.VMA instructions are permitted in S-mode.
RULE 62: The TW field in mstatus is read-only 0 when there are no modes less privileged than M.
RULE 63: When the TSR field in mstatus is 1, attempts to execute SRET while executing in S-mode raise an illegal-instruction exception.
RULE 64: When the TSR field in mstatus is 0, execution of SRET is permitted in S-mode.
RULE 65: If a floating‑point register (f0‑f31) or a floating‑point CSR (fcsr, frm, or fflags) is written, then a read of the FS field in mstatus must return the Dirty encoding; if no floating‑point register or CSR has been modified since the last transition to Clean, then a read of mstatus.FS must return the Clean encoding; and if software writes a value to mstatus.FS that is not one of the defined encodings, the hardware masks the write to the nearest legal encoding, so the readback of mstatus.FS reflects that legal encoding and no exception is raised.
RULE 66: If software writes a value to the VS field in mstatus that is not a legal encoding of the vector extension state (registers v0‑v31 and CSRs vcsr, vxrm, vxsat, vstart, vl, vtype, vlenb), then reading back the VS field returns a legal WARL‑encoded value representing a possible vector‑extension state.
RULE 67: The XS field in mstatus is a read-only field that encodes the status of additional user-mode extensions and associated state.
RULE 68: The SD bit in mstatus is a read-only bit that summarizes whether the FS, VS, or XS fields signal dirty state, defined as SD = (FS == 0b11) OR (VS == 0b11) OR (XS == 0b11).
RULE 69: If the F extension is implemented, the FS field in mstatus shall not be read-only zero.
RULE 70: If the v registers are implemented, the VS field in mstatus shall not be read-only zero.
RULE 71: In harts without additional user extensions requiring new state, the XS field in mstatus is read-only zero.
RULE 72: If the FS, VS, and XS fields in mstatus are all read-only zero, then the SD bit in mstatus is also always zero.
RULE 73: When an extension's status in mstatus is set to Off, any instruction that attempts to read or write the corresponding state shall cause an illegal-instruction exception.
RULE 74: If the mstatus register holds the reset‑initial pattern, then reading mstatus returns the defined constant value and the architectural state derived from it (current privilege mode, MIE, MPIE, MPP, etc.) equals the specified initial constants.
RULE 75: If the status field in mstatus is Dirty during a context restore, then the context is not loaded from memory (no memory load of the saved context occurs).
RULE 76: The XS field in mstatus is set indirectly by writing to the status register of the individual extensions.
RULE 77: If an instruction executes, then every mstatus field that the specification defines to be modified by that instruction is updated, and reading the mstatus CSR after the instruction shows the new values regardless of the current privilege mode.
RULE 78: Changing the FS setting in mstatus has no effect on the contents of the floating-point register state.

RULE 80: Setting FS=Initial in mstatus does not clear the floating-point register contents.
RULE 81: Changing the VS setting in mstatus has no effect on the contents of the vector register state.
