REGISTER: mseccfg
RULE 1: Implementations may implement the mseccfg CSR such that the SSEED and USEED fields are read-only constant zero.
RULE 2: Software may discover if access to the seed CSR can be enabled in U and S mode by writing a 1 to the SSEED or USEED field of the mseccfg CSR and reading back the result.
RULE 3: The mseccfg CSR is a Machine-mode read/write (MRW) register.
RULE 4: The upper 32 bits of the mseccfg register are accessed through the CSR named mseccfgh located at address 0x757.
RULE 5: mseccfg is a 64-bit read/write register.
RULE 6: mseccfg exists if any extension that adds a field to mseccfg is implemented; otherwise it is reserved.
RULE 7: When mseccfg.USEED is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 8: When mseccfg.USEED is 1, read-write access to the seed CSR from U-mode is allowed.
RULE 9: When mseccfg.USEED is 1, all other types of accesses to the seed CSR from U-mode raise an illegal-instruction exception.
RULE 10: If Zkr or U-mode is not implemented, mseccfg.USEED is read-only zero.
RULE 11: When mseccfg.SSEED is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 12: When mseccfg.SSEED is 1, read-write access to the seed CSR from S-/HS-mode is allowed.
RULE 13: When mseccfg.SSEED is 1, all other types of accesses to the seed CSR from S-/HS-mode raise an illegal-instruction exception.
RULE 14: If Zkr or S-mode is not implemented, mseccfg.SSEED is read-only zero.
RULE 15: When the H extension is also implemented, access to the seed CSR from an HS-qualified instruction leads to a virtual-instruction exception in VS and VU modes.
RULE 16: When the H extension is also implemented, all other types of accesses to the seed CSR raise an illegal-instruction exception.
RULE 17: In machine mode, mseccfg does not restrict access to the seed CSR; the seed CSR is always available as a normal read-write CSR and a read without a write raises an illegal-instruction exception regardless of mseccfg field values.
RULE 18: In U-mode with mseccfg.USEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 19: In U-mode with mseccfg.USEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 20: In S-/HS-mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 21: In S-/HS-mode with mseccfg.SSEED = 1, the seed CSR is accessible as normal and no exception is raised for read-write accesses.
RULE 22: In VS/VU mode with mseccfg.SSEED = 0, any seed CSR access raises an illegal-instruction exception.
RULE 23: In VS/VU mode with mseccfg.SSEED = 1, a read-write seed access raises a virtual-instruction exception while other access types raise an illegal-instruction exception.
RULE 24: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 25: When mseccfg.RLB is 0 and any pmpcfg.L is 1 in any rule or entry (including disabled entries), mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 26: mseccfg.MMWP changes the default PMP policy for Machine mode when accessing memory regions that do not have a matching PMP rule.
RULE 27: mseccfg.MMWP is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 28: When mseccfg.MMWP is set, the default PMP policy for M-mode for unmatched regions becomes denied instead of ignored.
RULE 29: mseccfg.MML is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 30: When mseccfg.MML is set, the meaning of pmpcfg.L changes so that it marks a rule as M-mode-only when set and as S/U-mode-only when unset.
RULE 31: When mseccfg.MML is set, the previously reserved encoding pmpcfg.RW = 01 and the encoding pmpcfg.LRWX = 1111 now encode a Shared-Region.
RULE 32: An M-mode-only rule (when mseccfg.MML is set) is enforced on Machine mode, denied on Supervisor and User modes, and remains locked so that any further modifications to its configuration or address registers are ignored until a PMP reset unless mseccfg.RLB is set.
RULE 33: An S/U-mode-only rule (when mseccfg.MML is set) is enforced on Supervisor and User modes and denied on Machine mode.
RULE 34: A Shared-Region rule with pmpcfg.L not set (when mseccfg.MML is set) permits data sharing between M-mode and S/U-mode, is not executable, gives M-mode read/write access, and gives S/U-mode read access unless pmpcfg.X is set, in which case S/U-mode has read/write access.
RULE 35: A Shared-Region rule with pmpcfg.L set (when mseccfg.MML is set) permits code sharing between M-mode and S/U-mode, is not writable, gives both modes execute access, gives M-mode read access if pmpcfg.X is set, and remains locked unless mseccfg.RLB is set.
RULE 36: A Shared-Region rule with pmpcfg.LRWX = 1111 (when mseccfg.MML is set) permits data sharing between M-mode and S/U-mode with both modes read-only access and remains locked unless mseccfg.RLB is set.
RULE 37: Adding a pmpcfg write that would create an executable M-mode-only or a locked Shared-Region rule is not possible; such writes are ignored and pmpcfg remains unchanged.
RULE 38: The restriction on adding executable M-mode-only or locked Shared-Region rules can be temporarily lifted by setting mseccfg.RLB.
RULE 39: Executing code with Machine mode privileges is only possible from memory regions with a matching M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 40: Executing code from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 41: If mseccfg.MML is not set, the encoding pmpcfg.RW = 01 remains reserved for future standard use.
RULE 42: If the Smmpm extension is implemented, the PMM field in mseccfg enables or disables pointer masking for M-mode according to Table 21 values.
RULE 43: If the Smmpm extension is not implemented, the PMM field in mseccfg is read-only zero.
RULE 44: PMM field value 00 in mseccfg indicates pointer masking is disabled (PMLEN = 0).
RULE 45: PMM field value 10 in mseccfg indicates pointer masking is enabled with PMLEN = XLEN - 57 (PMLEN = 7 on RV64).
RULE 46: PMM field value 11 in mseccfg indicates pointer masking is enabled with PMLEN = XLEN - 48 (PMLEN = 16 on RV64).
RULE 47: When the Zicfilp extension is present, the MLPE field in mseccfg being 1 enables the Zicfilp extension in M-mode.
RULE 48: When the MLPE field in mseccfg is 0, the Zicfilp extension is not enabled in M-mode and the hart does not update the ELP state, which remains NO_LP_EXPECTED.
RULE 49: When the MLPE field in mseccfg is 0, the LPAD instruction operates as a no-op.
RULE 50: If the Zicfilp extension is implemented, the MLPE field of the mseccfg register is reset to 0.
RULE 51: The MML field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 52: The MMWP field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 53: The RLB field of the mseccfg register is set to 0 unless the platform mandates a different reset value.
RULE 54: When mseccfg.MML = 1 and the PMP configuration bits L, R, W, X are all zero, any access in either M-mode or S/U-mode is an inaccessible region that raises an access exception.
RULE 55: When mseccfg.MML = 1, L = 0, R = 0, W = 0, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted only as an execute-only region.
RULE 56: When mseccfg.MML = 1, L = 0, R = 0, W = 1, X = 0, M-mode accesses are allowed to read and write the shared data region, and S/U-mode accesses are allowed to read only.
RULE 57: When mseccfg.MML = 1, L = 0, R = 0, W = 1, X = 1, both M-mode and S/U-mode accesses are allowed to read and write the shared data region.
RULE 58: When mseccfg.MML = 1, L = 0, R = 1, W = 0, X = 0, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-only region.
RULE 59: When mseccfg.MML = 1, L = 0, R = 1, W = 0, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-execute region.
RULE 60: When mseccfg.MML = 1, L = 0, R = 1, W = 1, X = 0, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-write region.
RULE 61: When mseccfg.MML = 1, L = 0, R = 1, W = 1, X = 1, an access in M-mode raises an access exception while an access in S/U-mode is permitted as a read-write-execute region.
RULE 62: When mseccfg.MML = 1, L = 1, R = 0, W = 0, X = 0, any access in either M-mode or S/U-mode is a locked inaccessible region that raises an access exception.
RULE 63: When mseccfg.MML = 1, L = 1, R = 0, W = 0, X = 1, M-mode accesses are limited to a locked execute-only region, whereas S/U-mode accesses raise an access exception.
RULE 64: When mseccfg.MML = 1, L = 1, R = 0, W = 1, X = 0, both M-mode and S/U-mode accesses are limited to a locked shared code region that permits execution only.
RULE 65: When mseccfg.MML = 1, L = 1, R = 0, W = 1, X = 1, M-mode accesses are permitted as read/execute in a locked shared code region, while S/U-mode accesses are limited to execution only in the same locked region.
RULE 66: When mseccfg.MML = 1, L = 1, R = 1, W = 0, X = 0, M-mode accesses are permitted as a locked read-only region, while S/U-mode accesses raise an access exception.
RULE 67: When mseccfg.MML = 1, L = 1, R = 1, W = 0, X = 1, M-mode accesses are permitted as a locked read/execute region, while S/U-mode accesses raise an access exception.
RULE 68: When mseccfg.MML = 1, L = 1, R = 1, W = 1, X = 0, M-mode accesses are permitted as a locked read/write region, while S/U-mode accesses raise an access exception.
RULE 69: When mseccfg.MML = 1, L = 1, R = 1, W = 1, X = 1, both M-mode and S/U-mode accesses are limited to a locked shared data region that is read-only for both privilege modes.
RULE 70: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 71: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 72: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 73: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 74: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 75: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 76: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 77: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 78: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 79: In M-mode, accessing mseccfg register while Zicfilp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zicfilp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 80: In M-mode, accessing mseccfg register while Zkr extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zkr; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
RULE 1: If the TW bit in mstatus is set, a WRS.NTO instruction is executed in a privilege mode other than M mode, and the instruction does not complete within an implementation-specific bounded time limit, then the instruction causes an illegal-instruction exception.
RULE 2: If execution is in VS mode or VU mode, the VTW bit in hstatus is set, the TW bit in mstatus is clear, and a WRS.NTO instruction does not complete within an implementation-specific bounded time limit, then the instruction causes a virtual-instruction exception.
RULE 3: A CMO instruction may be permitted or denied access to a cache block depending on the values of the MPRV, MPV, and MPP fields in mstatus.
RULE 4: A CMO instruction may be permitted or denied access to a cache block depending on the value of the SUM field in mstatus, sstatus, and vsstatus.
RULE 5: A CMO instruction may be permitted or denied access to a cache block depending on the value of the MXR field in mstatus, sstatus, and vsstatus.
RULE 6: When the Zfinx extension is implemented, the FS field in mstatus is hardwired to 0.
RULE 7: When the Zfinx extension is implemented, the FS field in mstatus does not affect the trapping behavior of floating-point instructions or fcsr accesses.
RULE 8: Bits 10-9 of sstatus contain a shadow copy of the VS field of mstatus.
RULE 9: When mstatus.VS is Off, executing any vector instruction raises an illegal-instruction exception.
RULE 10: When mstatus.VS is Off, accessing a vector CSR raises an illegal-instruction exception.
RULE 11: When mstatus.VS is Initial or Clean, executing any instruction that changes vector state, including accesses to vector CSRs, sets mstatus.VS to Dirty.
RULE 12: If mstatus.VS is Dirty, mstatus.SD is set to 1.
RULE 13: If mstatus.VS is not Dirty, mstatus.SD follows the rules defined elsewhere for the SD bit.
RULE 14: When V=1 and either vsstatus.VS or mstatus.VS is Off, any attempt to execute a vector instruction or to access a vector CSR must raise an illegal-instruction exception.
RULE 15: When V=1 and both vsstatus.VS and mstatus.VS are not Off, executing any instruction that changes vector state, including accesses to vector CSRs, must set both mstatus.VS and vsstatus.VS to Dirty.
RULE 16: If mstatus.VS is Dirty, then mstatus.SD must be 1.
RULE 17: If mstatus.FS is Off then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 18: Any vector floating-point instruction that modifies any floating-point extension state must set mstatus.FS to Dirty.
RULE 19: If either vsstatus.FS or mstatus.FS is Off then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 20: Any vector floating-point instruction that modifies any floating-point extension state must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 21: The mstatus CSR is a machine-mode register that is readable and writable (MRW).
RULE 22: Bits 30:4 of mstatush generally contain the same fields found in bits 62:36 of mstatus for RV64.
RULE 23: The global interrupt-enable bits MIE and SIE reside in the low-order bits of mstatus, allowing them to be atomically set or cleared with a single CSR instruction.
RULE 24: If supervisor mode is not implemented, the SIE and SPIE fields in mstatus are read-only zero.
RULE 25: When a trap is taken from privilege mode y into privilege mode x, the xPIE field in mstatus is set to the current value of xIE, the xIE field in mstatus is cleared to zero, and the xPP field in mstatus is written with the value y.
RULE 26: An xRET instruction (MRET or SRET) sets the xIE field in mstatus to the value of xPIE when the xPP field holds the previous mode y.
RULE 27: An xRET instruction updates the architectural privilege mode stored in mstatus to the value held in the xPP field.
RULE 28: An xRET instruction sets the xPIE field in mstatus to 1.
RULE 29: An xRET instruction writes the xPP field in mstatus with the least-privileged supported mode, which is U if user mode is implemented otherwise M.
RULE 30: If the previous privilege mode y is not M, an xRET instruction also clears the MPRV field in mstatus to 0.
RULE 31: Each xPP field in mstatus is a WARL field that may contain only the privilege mode x or any implemented privilege mode lower than x.
RULE 32: If privilege mode x is not implemented, the corresponding xPP field in mstatus must be read-only zero.
RULE 33: Machine-mode software can test the implementation of a privilege mode by writing that mode into the MPP field of mstatus and then reading the field back.
RULE 34: Upon reset, the MDT field in mstatus is set to 1.
RULE 35: When the MDT bit in mstatus is set to 1 by an explicit CSR write, the MIE bit in mstatus is cleared to 0.
RULE 36: On RV64, writing the MDT bit to 1 in mstatus clears the MIE bit to 0 regardless of any value supplied for the MIE bit in the same CSR write.
RULE 37: The MIE bit in mstatus may be set to 1 by an explicit CSR write only if the MDT bit in mstatus is already 0, or on RV64 only if the same CSR write also sets the MDT bit to 0.
RULE 38: If a trap is taken into M-mode while the MDT bit in mstatus is 0, the MDT bit is set to 1 before the trap is delivered.
RULE 39: A trap caused by an RNMI does not set the MDT bit in mstatus.
RULE 40: When executed in M-mode, the MRET instruction sets the MDT bit in mstatus to 0.
RULE 41: When executed in M-mode, the SRET instruction sets the MDT bit in mstatus to 0.
RULE 42: When the MNRET instruction (provided by the Smrnmi extension) is executed, it sets the MDT bit in mstatus to 0 if the resulting privilege mode is not M.
RULE 43: In mstatus for RV64 harts, the SXL and UXL fields are WARL fields that control the XLEN value used in S-mode and U-mode respectively.
RULE 44: The encoding of the SXL and UXL fields in mstatus matches the encoding of the MXL field in the misa register.
RULE 45: If S-mode is not supported and MXLEN = 64, the SXL field in mstatus is a read-only zero.
RULE 46: If S-mode is supported and MXLEN = 64, the SXL field in mstatus is a WARL field that encodes the current SXLEN value.
RULE 47: An implementation may make the SXL field in mstatus read-only such that its value always forces SXLEN to equal MXLEN.
RULE 48: If U-mode is not supported and MXLEN = 64, the UXL field in mstatus is a read-only zero.
RULE 49: If U-mode is supported and MXLEN = 64, the UXL field in mstatus is a WARL field that encodes the current UXLEN value.
RULE 50: An implementation may make the UXL field in mstatus read-only such that its value always forces UXLEN to equal MXLEN or to equal SXLEN.
RULE 51: When S-mode is implemented, the set of legal values that the UXL field in mstatus may assume excludes any value that would cause UXLEN to be greater than SXLEN.
RULE 52: Whenever XLEN in any privilege mode is configured via mstatus to a value less than the widest supported XLEN, all operations must ignore source-operand register bits above the configured XLEN and must sign-extend results to fill the entire widest supported XLEN in the destination register.
RULE 53: When XLEN in any privilege mode is configured via mstatus to a value less than the widest supported XLEN, PC bits above the configured XLEN are ignored and when the PC is written it must be sign-extended to fill the widest supported XLEN.
RULE 54: When a HINT instruction that overwrites its destination register with its current value is executed with XLEN < MXLEN and the bits from MXLEN down to XLEN of the destination register are not all equal to bit XLEN-1, it is implementation-defined whether those bits are unchanged or are overwritten with copies of bit XLEN-1, as observed through the XLEN settings in mstatus.
RULE 55: Implementations may elide the register write-back for some HINT instructions while performing normal write-back for other integer computational instructions, and this choice is observable only by privilege modes whose XLEN setting, as defined by mstatus, is greater than the current XLEN.
RULE 56: The MPRV field in mstatus modifies the effective privilege mode at which explicit memory accesses execute.
RULE 57: When the MPRV field in mstatus is 0, explicit memory accesses behave normally using the translation and protection mechanisms of the current privilege mode.
RULE 58: When the MPRV field in mstatus is 1, load and store memory addresses are translated, protected, and have endianness applied as if the current privilege mode were set to the value in the MPP field of mstatus.
RULE 59: Instruction address-translation and protection are unaffected by the setting of the MPRV field in mstatus.
RULE 60: The MPRV field in mstatus is read-only zero if user mode is not supported.
RULE 61: Executing an MRET or SRET instruction that changes the privilege mode to a mode less privileged than machine mode also sets the MPRV field in mstatus to zero.
RULE 62: When the MPRV field in mstatus is 1, load and store memory addresses are treated as though the current XLEN were the XLEN associated with the MPP field of mstatus.
RULE 63: The MXR field in mstatus modifies the privilege with which load instructions access virtual memory.
RULE 64: When the MXR field in mstatus is 0, only loads from pages marked readable (R=1) will succeed.
RULE 65: When the MXR field in mstatus is 1, loads from pages marked readable (R=1) or executable (X=1) will succeed.
RULE 66: The MXR field in mstatus has no effect when page-based virtual memory is not in effect.
RULE 67: The MXR field in mstatus is read-only zero if supervisor mode is not supported.
RULE 68: The SUM field in mstatus modifies the privilege with which supervisor-mode loads and stores access virtual memory.
RULE 69: When the SUM field in mstatus is 0, supervisor-mode memory accesses to pages that are accessible by user mode (U=1) will fault.
RULE 70: When the SUM field in mstatus is 1, supervisor-mode memory accesses to pages that are accessible by user mode (U=1) are permitted.
RULE 71: The SUM field in mstatus has no effect when page-based virtual memory is not in effect.
RULE 72: The SUM field in mstatus is in effect when MPRV is 1 and the MPP field is set to supervisor mode, even if the current execution mode is not supervisor mode.
RULE 73: The SUM field in mstatus is read-only zero if supervisor mode is not supported or if the satp.MODE field is read-only zero.
RULE 74: The MXR and SUM fields in mstatus have no impact on whether access-fault exceptions are raised due to physical memory attributes or the physical memory protection subsystem.
RULE 75: The MBE, SBE, and UBE bits in mstatus (and mstatush) are WARL fields that control the endianness of memory accesses other than instruction fetches.
RULE 76: Instruction fetches are always little-endian regardless of the values of the fields in mstatus.
RULE 77: When mstatus.MPRV=0, the MBE bit in mstatus determines whether non-instruction-fetch memory accesses from M-mode are little-endian (MBE=0) or big-endian (MBE=1).
RULE 78: If supervisor mode is not supported, the SBE bit in mstatus is read-only 0.
RULE 79: When supervisor mode is supported, the SBE bit in mstatus determines whether explicit load and store accesses from S-mode are little-endian (SBE=0) or big-endian (SBE=1).
RULE 80: If user mode is not supported, the UBE bit in mstatus is read-only 0.
RULE 81: When user mode is supported, the UBE bit in mstatus determines whether explicit load and store accesses from U-mode are little-endian (UBE=0) or big-endian (UBE=1).
RULE 82: For implicit accesses to supervisor-level memory-management data structures, such as page tables, the endianness is always controlled by the SBE bit in mstatus.
RULE 83: An implementation supports only little-endian memory accesses (aside from instruction fetches) when the MBE, SBE, and UBE bits in mstatus are all read-only 0.
RULE 84: An implementation supports only big-endian memory accesses (aside from instruction fetches) when MBE is read-only 1 and, if supervisor mode and user mode are supported, SBE and UBE are each read-only 1 in mstatus.
RULE 85: The TVM field in mstatus is a WARL field.
RULE 86: When the TVM field in mstatus is 1, attempts to read or write the satp CSR or to execute an SFENCE.VMA or SINVAL.VMA instruction while executing in S-mode raise an illegal-instruction exception.
RULE 87: When the TVM field in mstatus is 0, reads or writes of the satp CSR and execution of SFENCE.VMA or SINVAL.VMA instructions are permitted in S-mode.
RULE 88: The TVM field in mstatus is read-only 0 when S-mode is not supported.
RULE 89: The TW field in mstatus is a WARL field.
RULE 90: The TW field in mstatus is read-only 0 when there are no modes less privileged than M.
RULE 91: The TSR field in mstatus is a WARL field.
RULE 92: When the TSR field in mstatus is 1, attempts to execute SRET while executing in S-mode raise an illegal-instruction exception.
RULE 93: When the TSR field in mstatus is 0, execution of SRET is permitted in S-mode.
RULE 94: The TSR field in mstatus is read-only 0 when S-mode is not supported.
RULE 95: The FS field in mstatus is a WARL field that encodes the status of the floating-point unit state, including registers f0-f31 and the CSRs fcsr, frm, and fflags.
RULE 96: The VS field in mstatus is a WARL field that encodes the status of the vector extension state, including registers v0-v31 and the CSRs vcsr, vxrm, vxsat, vstart, vl, vtype, and vlenb.
RULE 97: The XS field in mstatus is a read-only field that encodes the status of additional user-mode extensions and associated state.
RULE 98: The SD bit in mstatus is a read-only bit that summarizes whether the FS, VS, or XS fields signal dirty state, defined as SD = (FS == 0b11) OR (VS == 0b11) OR (XS == 0b11).
RULE 99: If the F extension is implemented, the FS field in mstatus shall not be read-only zero.
RULE 100: If neither the F extension nor S-mode is implemented, then the FS field in mstatus is read-only zero.
RULE 101: If S-mode is implemented but the F extension is not, the FS field in mstatus may optionally be read-only zero.
RULE 102: Implementations with S-mode but without the F extension are permitted, but not required, to make the FS field in mstatus be read-only zero.
RULE 103: If the v registers are implemented, the VS field in mstatus shall not be read-only zero.
RULE 104: If neither the v registers nor S-mode is implemented, then the VS field in mstatus is read-only zero.
RULE 105: If S-mode is implemented but the v registers are not, the VS field in mstatus may optionally be read-only zero.
RULE 106: In harts without additional user extensions requiring new state, the XS field in mstatus is read-only zero.
RULE 107: If the FS, VS, and XS fields in mstatus are all read-only zero, then the SD bit in mstatus is also always zero.
RULE 108: When an extension's status in mstatus is set to Off, any instruction that attempts to read or write the corresponding state shall cause an illegal-instruction exception.

RULE 1: The satp CSR is readable and writable at supervisor privilege level.
RULE 2: Unless otherwise specified, an implicit read of satp MUST return the same value that would be returned by an explicit read of satp using a CSR-access instruction in a sufficient privilege mode.
RULE 3: The SUM (permit Supervisor User Memory access) bit is read-only 0 if S-mode is not supported or if satp.MODE is read-only 0.
RULE 4: When the TVM field in mstatus equals 1, any attempt to read or write the satp CSR while executing in S-mode MUST raise an illegal-instruction exception.
RULE 5: When TVM equals 1, the same condition that traps satp CSR accesses also requires that execution of an SFENCE.VMA or SINVAL.VMA instruction in S-mode MUST raise an illegal-instruction exception.
RULE 6: When TVM equals 0, reads or writes of the satp CSR in S-mode do not raise an illegal-instruction exception.
RULE 7: If S-mode is not supported, or if the satp MODE field is read-only zero (always Bare), the implementation may make the FIOM register read-only zero.
RULE 8: If the Svpbmt extension is not implemented, the PBMTE bit is read-only zero.
RULE 9: For implementations that include the hypervisor extension, if menvcfg.PBMTE is zero then henvcfg.PBMTE is read-only zero, affecting address translation of page tables referenced by satp.
RULE 10: When ADUE=1, hardware updating of PTE A/D bits is enabled during S-mode address translation of page tables referenced by satp, and the implementation behaves as though the Svade extension is not implemented for S-mode address translation.
RULE 11: When the hypervisor extension is implemented and ADUE=1, hardware updating of PTE A/D bits is enabled during G-stage address translation of page tables referenced by satp, and the implementation behaves as though the Svade extension is not implemented for G-stage address translation.
RULE 12: When ADUE=0, the implementation behaves as though the Svade extension is implemented for S-mode and G-stage address translation of page tables referenced by satp.
RULE 13: If the Svadu extension is not implemented, the ADUE bit is read-only zero.
RULE 14: For implementations with the hypervisor extension, if menvcfg.ADUE is zero then henvcfg.ADUE is read-only zero, influencing address translation of page tables referenced by satp.
RULE 15: The Svade extension requires page-fault exceptions to be raised when PTE A/D bits need to be set, and therefore the Svade extension is considered implemented when ADUE=0 for address translation of page tables referenced by satp.
RULE 16: The MODE field of the satp register is read-only 0.
RULE 17: If the MODE field of satp is read-only 0, then the SUM bit in the sstatus register is read-only 0.
RULE 18: For SXLEN=64, bits 63-60 of satp constitute the MODE field, which is a WARL field.
RULE 19: For SXLEN=64, bits 59-44 of satp constitute the ASID field, which is a WARL field.
RULE 20: For SXLEN=64, bits 43-0 of satp constitute the PPN field, which is a WARL field.
RULE 21: When the MODE field of satp is Bare, supervisor virtual addresses are equal to supervisor physical addresses and no additional memory protection beyond the physical memory protection scheme is provided.
RULE 22: When SXLEN=64, all satp encodings with MODE = Bare are reserved for future standard use.
RULE 23: For SXLEN=64, the defined paged virtual-memory MODE values for satp are Sv39, Sv48, and Sv57.
RULE 24: All other MODE settings of satp are reserved for future use and may assign different interpretations to the remaining satp fields.
RULE 25: Implementations are not required to support every MODE value, and if satp is written with an unsupported MODE, the entire write has no effect and no satp fields are modified.
RULE 26: The implemented number of ASID bits in satp, called ASIDLEN, can be discovered by writing ones to every bit position of the ASID field and reading back which bits retain a one.
RULE 27: If ASIDLEN > 0, the least-significant ASIDLEN bits of the satp ASID field are writable.
RULE 28: The maximum possible ASIDLEN value, ASIDMAX, is 9 for Sv32 and 16 for Sv39, Sv48, and Sv57 as encoded in satp.
RULE 29: The satp CSR is considered active when the effective privilege mode is S-mode or U-mode.
RULE 30: Address-translation algorithm executions may only begin using a given satp value when satp is active.
RULE 31: Translations that started while satp was active are not required to complete or terminate when satp becomes inactive, unless a matching SFENCE.VMA instruction is executed.
RULE 32: An SFENCE.VMA instruction must be used to ensure that updates to address-translation data structures become visible to subsequent implicit reads by a hart.
RULE 33: Writing satp does not impose any ordering constraints between page-table updates and later address translations, nor does it cause any invalidation of address-translation caches.
RULE 34: Implementations must only perform implicit reads of translation data structures pointed to by the current contents of satp or a subsequent valid (V=1) translation-data-structure entry.
RULE 35: Changes to satp.MODE from Bare to another mode or from another mode to Bare take effect immediately and do not require execution of an SFENCE.VMA instruction.
RULE 36: Changes to satp.ASID take effect immediately.
RULE 37: For implementations where satp.MODE is read-only zero (always Bare), attempts to execute an SFENCE.VMA instruction might raise an illegal-instruction exception.
RULE 38: When satp is configured for Sv32 mode, supervisor and user virtual addresses are translated into supervisor physical addresses by traversing a radix-tree page table.
RULE 39: If the MODE field of satp is set to Sv32, supervisor virtual addresses are translated to supervisor physical addresses using a two-level page table.
RULE 40: When satp.MODE is Sv32, the 20-bit virtual-page number is translated into a 22-bit physical-page number while the 12-bit page offset remains unchanged.
RULE 41: When satp.MODE is Sv32, the supervisor-level physical addresses produced are examined by any physical-memory-protection structures before being directly converted to machine-level physical addresses.
RULE 42: When satp.MODE is Sv32, if required, the supervisor-level physical addresses are zero-extended to match the number of physical-address bits implemented in the hardware.
RULE 43: The physical page number of the root page table is stored in satp.
RULE 44: The address space for which implicit reads of NAPOT page-table entries may create address-translation cache entries is the address space identified in satp as loaded by step 1.
RULE 45: When VTVM = 1, an attempt in VS-mode to access CSR satp raises a virtual-instruction exception.
RULE 46: When VTVM = 1, an attempt in VS-mode to access CSR satp causes a virtual-instruction exception instead of an illegal-instruction exception.
RULE 47: If a write to the satp CSR specifies a MODE value that is not supported, the write is ignored and the previous value of satp remains unchanged.
RULE 48: When V=1, any instruction that reads or modifies the satp register accesses the vsatp register instead.
RULE 49: When V=0, a write to vsatp with an unsupported MODE value is either ignored as it is for satp, or the fields of vsatp are treated as WARL in the normal way.
RULE 50: When V=1, a write to satp with an unsupported MODE value is ignored and no write to vsatp is effected.
RULE 51: SFENCE.VMA applies only to the memory-management data structures controlled by the current satp, where the current satp is the HS-level satp when the V field of satp is 0 and the vsatp when the V field of satp is 1.
RULE 52: When the V field of satp is 1, any attempt to execute HFENCE.VVMA or HFENCE.GVMA MUST cause a virtual-instruction exception.
RULE 53: When the TVM field in mstatus is set to 1, the instruction traps that become enabled permit machine-level software to co-opt the satp register (and hgatp).
RULE 54: When the TVM field in mstatus is set to 1, the instruction traps that become enabled permit machine-level software to substitute shadow page tables via the satp register that merge the OS's chosen page translations with machine-level lower-stage translations.
RULE 55: When the satp-controlled algorithm is used for G-stage address translation, the effective privilege mode must be VS-mode or VU-mode for the translation to begin.
RULE 56: When the satp-controlled algorithm checks the U bit during G-stage address translation, the current privilege mode is always taken to be U-mode.
RULE 57: When the satp-controlled algorithm encounters a page-fault during G-stage address translation, a guest-page-fault exception is raised instead of a regular page-fault exception.
RULE 58: When V=1 in VS-mode and an attempt is made to access the satp register while hstatus.VTVM=1, a virtual-instruction exception with exception code 22 is raised.
RULE 59: If satp.MODE (or vsatp.MODE when V=1) is set to Bare and the effective privilege mode is any mode lower than M, then any shadow-stack instruction MUST raise a store/AMO access-fault exception.
RULE 60: If the effective privilege mode is M and satp.MODE (or vsatp.MODE when V=1) is set to Bare, then a memory access performed by an SSAMOSWAP.W or SSAMOSWAP.D instruction MUST cause a store/AMO access-fault exception.
RULE 61: When the active satp register's MODE field equals Bare, the ignore transformation applied to a physical address (including guest-physical addresses) replaces the upper PMLEN bits with 0.
RULE 62: When the active satp register's MODE field does not equal Bare, the ignore transformation is not applied to a physical address (including guest-physical addresses), so the upper PMLEN bits are not replaced with 0.

REGISTER: scounteren
RULE 1: The scounteren CSR has supervisor-read/write privilege (SRW).
RULE 2: Any bit in scounteren may be read-only zero.
RULE 3: A read-only-zero bit in scounteren indicates that reads to the corresponding counter will cause an exception when executing in U-mode.
RULE 4: When a CY, TM, IR, or HPM n bit in scounteren is clear, attempts to read the corresponding counter register while executing in U-mode will cause an illegal-instruction exception.
RULE 5: When a CY, TM, IR, or HPM n bit in scounteren is set, access to the corresponding counter register is permitted.
RULE 6: The setting of a bit in mcounteren does not affect whether the corresponding bit in scounteren is writable.
RULE 7: U-mode may only access a counter if the corresponding bits in both scounteren and mcounteren are set.
RULE 8: When V = 1, scounteren continues to have its usual function and accessibility.
RULE 9: When V = 1, accesses to scounteren that would be in HS-mode are instead performed in VS-mode, and accesses that would be in U-mode are performed in VU-mode.
RULE 10: In VU-mode, a counter MUST NOT be readable unless the applicable bits are set in both hcounteren and scounteren.
RULE 11: When V=1 and an HS-qualified instruction is prevented from executing because scounteren disables the instruction, a virtual-instruction exception with exception code 22 is raised instead of an illegal-instruction exception.
RULE 12: In VU-mode, if an attempt to access a non-high-half counter CSR finds the corresponding bit in scounteren equal to 0 while the same bit in mcounteren is 1, a virtual-instruction exception is raised.
