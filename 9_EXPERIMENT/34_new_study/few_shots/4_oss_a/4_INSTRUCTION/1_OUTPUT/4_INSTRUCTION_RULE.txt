INSTRUCTION: CSRRWI
RULE 1: CSRRWI updates the targeted CSR with an XLEN-bit value obtained by zero-extending the 5-bit unsigned immediate field encoded in the rs1 position.
RULE 2: CSRRWI performs an atomic read-modify-write of the addressed CSR.
RULE 3: If the destination register rd of a CSRRWI instruction is x0, the instruction shall not read the CSR and shall not cause any side effects that might occur on a CSR read.
RULE 4: If the destination register rd of a CSRRWI instruction is not x0, the instruction reads the old value of the CSR, zero-extends it to XLEN bits, and writes it to integer register rd.
RULE 5: CSRRWI always writes the addressed CSR with the XLEN-bit value obtained by zero-extending the 5-bit immediate, regardless of the immediate's value.
RULE 6: CSRRWI triggers the defined side-effects for all writable fields of the CSR that are written by the instruction.
RULE 7: When rd is x0, CSRRWI does not read the CSR but does write the CSR.
RULE 8: When rd is not x0, CSRRWI both reads the CSR and writes the CSR.

INSTRUCTION: FCVT.W.D


INSTRUCTION: SFENCE.VMA
RULE 1: SFENCE.VMA must not order invalidate, clean, or flush operations.
RULE 2: When the TVM bit in the mstatus register is 1, any attempt to execute SFENCE.VMA while executing in S-mode must raise an illegal-instruction exception.
RULE 3: When the TVM bit in the mstatus register is 0, executing SFENCE.VMA in S-mode is permitted.
RULE 4: Executing an SFENCE.VMA instruction with rs1=x0 and rs2=x0 after changing menvcfg.PBMTE MUST synchronize the address-translation caches with respect to the altered interpretation of page-table entries' PBMT fields.
RULE 5: When the hypervisor extension is implemented, executing an SFENCE.VMA instruction with rs1=x0 and rs2=x0 after changing menvcfg.PBMTE does NOT by itself guarantee complete synchronization; additional synchronization requirements described in Section 22.5.3 MUST also be satisfied.
RULE 6: Executing an SFENCE.VMA instruction with rs1=x0 and rs2=x0 after changing menvcfg.ADUE MUST synchronize the address-translation caches with respect to the altered interpretation of page-table entries' A/D bits.
RULE 7: When the hypervisor extension is implemented, executing an SFENCE.VMA instruction with rs1=x0 and rs2=x0 after changing menvcfg.ADUE does NOT by itself guarantee complete synchronization; additional synchronization requirements described in Section 22.5.3 MUST also be satisfied.
RULE 8: An SFENCE.VMA instruction with rs1 = x0 and rs2 = x0 executed after any PMP CSR is written must synchronize the PMP settings with the virtual-memory system and with any PMP or address-translation caches.
RULE 9: When paging is enabled and PMP settings have been modified, M-mode software must synchronize the PMP settings with the virtual-memory system and any PMP or address-translation caches by executing an SFENCE.VMA instruction with rs1 = x0 and rs2 = x0.
RULE 10: If page-based virtual memory is not implemented, memory accesses check PMP settings synchronously, and SFENCE.VMA execution is not required for PMP-virtual-memory synchronization.
RULE 11: Translations that began while satp was active are not required to complete or terminate when satp is no longer active unless an SFENCE.VMA instruction matching the same virtual address and ASID is executed.
RULE 12: A hart must execute an SFENCE.VMA instruction to ensure that updates to address-translation data structures are observed by subsequent implicit reads performed by that hart.
RULE 13: Executing an SFENCE.VMA instruction guarantees that any previous stores already visible to the current hart are ordered before certain implicit references by subsequent instructions in that hart to the memory-management data structures.
RULE 14: The set of operations ordered by an SFENCE.VMA instruction is determined by the values in rs1 and rs2.
RULE 15: An SFENCE.VMA instruction also invalidates entries in the address-translation cache associated with the hart.
RULE 16: An SFENCE.VMA instruction orders only the local hart's implicit references to the memory-management data structures.
RULE 17: If rs1 = x0 and rs2 = x0, an SFENCE.VMA instruction orders all reads and writes made to any level of the page tables for all address spaces.
RULE 18: If rs1 = x0 and rs2 = x0, an SFENCE.VMA instruction invalidates all address-translation cache entries for all address spaces.
RULE 19: If rs1 = x0 and rs2 ≠ x0, an SFENCE.VMA instruction orders all reads and writes made to any level of the page tables only for the address space identified by rs2.
RULE 20: If rs1 = x0 and rs2 ≠ x0, an SFENCE.VMA instruction does not order accesses to global mappings.
RULE 21: If rs1 = x0 and rs2 ≠ x0, an SFENCE.VMA instruction invalidates all address-translation cache entries matching the address space identified by rs2, except for entries containing global mappings.
RULE 22: If rs1 ≠ x0 and rs2 = x0, an SFENCE.VMA instruction orders only reads and writes made to leaf page-table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 23: If rs1 ≠ x0 and rs2 = x0, an SFENCE.VMA instruction invalidates all address-translation cache entries that contain leaf page-table entries corresponding to the virtual address in rs1 for all address spaces.
RULE 24: If rs1 ≠ x0 and rs2 ≠ x0, an SFENCE.VMA instruction orders only reads and writes made to leaf page-table entries corresponding to the virtual address in rs1 for the address space identified by rs2.
RULE 25: If rs1 ≠ x0 and rs2 ≠ x0, an SFENCE.VMA instruction does not order accesses to global mappings.
RULE 26: If rs1 ≠ x0 and rs2 ≠ x0, an SFENCE.VMA instruction invalidates all address-translation cache entries that contain leaf page-table entries corresponding to the virtual address in rs1 and that match the address space identified by rs2, except for entries containing global mappings.
RULE 27: If the value held in rs1 is not a valid virtual address, an SFENCE.VMA instruction has no effect and does not raise an exception.
RULE 28: When rs2 ≠ x0, bits SXLEN-1:ASIDMAX of the value held in rs2 are reserved for future standard use and current implementations must ignore them.
RULE 29: If ASIDLEN < ASIDMAX, an implementation shall ignore bits ASIDMAX-1:ASIDLEN of the value held in rs2.
RULE 30: An implicit read of the memory-management data structures after an SFENCE.VMA may return any translation that was valid at any time since the most recent SFENCE.VMA that subsumes the accessed address.
RULE 31: The ordering implied by an SFENCE.VMA does not place implicit reads and writes to the memory-management data structures into the global memory order in a way that interacts cleanly with the standard RVWMO ordering rules.
RULE 32: Prior explicit accesses are not necessarily ordered before subsequent explicit accesses in the global memory order as a result of an SFENCE.VMA.
RULE 33: Implicit loads generated by address translation need not obey normal program-order semantics with respect to prior loads or stores to the same address.
RULE 34: If a leaf PTE is modified and the corresponding virtual address is accessed without an intervening subsuming SFENCE.VMA, the implementation may use either the new translation or any older translation that was valid since the last subsuming SFENCE.VMA, and it is unpredictable which translation will be chosen.
RULE 35: Subsequent accesses to the same virtual address may use different translations from the set of translations valid since the last subsuming SFENCE.VMA, while the overall behavior remains well defined.
RULE 36: Implementations must only perform implicit reads of translation data structures pointed to by the current satp register or a subsequent valid (V=1) translation-data-structure entry.
RULE 37: Implementations must only raise exceptions for implicit accesses that are generated as a result of instruction execution, not for those performed speculatively.
RULE 38: For implementations where satp.MODE is read-only zero (always Bare), execution of an SFENCE.VMA instruction may raise an illegal-instruction exception.
RULE 39: An SFENCE.VMA instruction invalidates address-translation cache entries associated with the hart according to the values in rs1 and rs2.
RULE 40: Executing an SFENCE.VMA instruction with rs1 = x0 synchronizes address-translation caches for all 4 KiB virtual pages in the entire address space.
RULE 41: Executing an SFENCE.VMA instruction with rs1 ≠ x0 synchronizes address-translation caches for the single 4 KiB virtual page whose virtual address is specified in rs1.
RULE 42: SFENCE.VMA must invalidate address-translation cache entries as defined by the values in its rs1 and rs2 registers.
RULE 43: The set of address-translation cache entries invalidated by SINVAL.VMA with given rs1 and rs2 values is identical to the set that would be invalidated by SFENCE.VMA with the same rs1 and rs2 values.
RULE 44: SFENCE.VMA must order all memory reads and writes that occur before its execution to be observed as occurring before the invalidation of the address-translation caches.
RULE 45: SFENCE.VMA must order all memory reads and writes that occur after its execution to be observed as occurring after the invalidation of the address-translation caches.
RULE 46: The sequence SFENCE.W.INVAL, SINVAL.VMA, SFENCE.INVAL.IR has the same architectural effect as a SFENCE.VMA with the same rs1 and rs2 values, with reads/writes prior to SFENCE.W.INVAL treated as prior to SFENCE.VMA and reads/writes after SFENCE.INVAL.IR treated as subsequent to SFENCE.VMA.
RULE 47: Executing SFENCE.VMA in U-mode always raises an illegal-instruction exception.
RULE 48: SFENCE.VMA must have the same permission checks and raise the same exceptions as SINVAL.VMA.
RULE 49: SFENCE.VMA must not raise any exceptions other than the illegal-instruction exception when executed in U-mode.
RULE 50: SFENCE.VMA synchronizes the hart's address-translation caches when a memory-resident page-table entry is changed from Invalid to Valid.
RULE 51: SFENCE.VMA may be used as a suitable memory-management instruction to synchronize the hart's address-translation caches when a memory-resident page-table entry is changed from Valid to Invalid.
RULE 52: In VS-mode, when the VTVM field of the hstatus register is 1, executing SFENCE.VMA MUST raise a virtual-instruction exception.
RULE 53: SFENCE.VMA MUST affect only the memory-management data structures that are controlled by the current satp, where the current satp is the HS-level satp when its V field is 0 or the vsatp when its V field is 1.
RULE 54: SFENCE.VMA guarantees that any stores whose results are already visible to the executing hart are ordered before all implicit address-translation reads performed by that hart for instructions that execute after the SFENCE.VMA.
RULE 55: The ordering effect of SFENCE.VMA is equivalent to the effect obtained by temporarily entering VS-mode and executing SFENCE.VMA, which is the effect described for the hypervisor fence HFENCE.VVMA.
RULE 56: When V=0, the virtual-address operand of SFENCE.VMA is interpreted as an HS-level virtual address.
RULE 57: When V=0, the ASID operand of SFENCE.VMA is interpreted as an HS-level ASID.
RULE 58: When V=0, SFENCE.VMA orders stores only to HS-level address-translation structures and orders subsequent HS-level address translations.
RULE 59: When V=1, the virtual-address operand of SFENCE.VMA is interpreted as a guest virtual address within the current virtual machine.
RULE 60: When V=1, the ASID operand of SFENCE.VMA is interpreted as a VS-level ASID within the current virtual machine.
RULE 61: When V=1, the effective ASID used by SFENCE.VMA is the combination of the VMID field of CSR hgatp and the VS-level ASID operand.
RULE 62: When V=1, SFENCE.VMA orders stores only to VS-level address-translation structures and orders subsequent VS-stage address translations for the same virtual machine, i.e., only when the VMID in hgatp at execution matches the VMID used for the translation.
RULE 63: M-mode software MUST execute SFENCE.VMA with rs1=x0 and rs2=x0 after writing PMP CSRs to synchronize PMP settings with the virtual-memory system for HS-level address translation.
RULE 64: If the V bit is 1 and execution of SFENCE.VMA is prevented because the current privilege level is insufficient or because the instruction is disabled by a supervisor or hypervisor CSR such as scounteren or hcounteren, then a virtual-instruction exception with exception code 22 must be raised instead of an illegal-instruction exception.
RULE 65: In VU-mode, an attempt to execute the supervisor instruction SFENCE.VMA must cause a virtual-instruction exception.
RULE 66: In VS-mode, if hstatus.VTVM=1, an attempt to execute SFENCE.VMA must cause a virtual-instruction exception.
RULE 67: When a virtual-instruction trap is taken for SFENCE.VMA, the mtval or stval CSR must be written with the same value that would be written for an illegal-instruction trap.
RULE 68: The exception code associated with a virtual-instruction trap raised by SFENCE.VMA must be 22.
RULE 69: SFENCE.VMA (as well as HFENCE.GVMA and HFENCE.VVMA) is not required to synchronize address-translation caches after a change to xSSE because such changes take effect immediately.
RULE 70: The instruction encoding for SFENCE.VMA MUST have the funct7 field equal to 0b0001001.
RULE 71: The instruction encoding for SFENCE.VMA uses the rs2 field to specify its second source register.
RULE 72: The instruction encoding for SFENCE.VMA uses the rs1 field to specify its first source register.
RULE 73: The instruction encoding for SFENCE.VMA MUST have the funct3 field equal to 0b000.
RULE 74: The instruction encoding for SFENCE.VMA MUST have the rd field equal to zero (x0).
RULE 75: The instruction encoding for SFENCE.VMA MUST have the opcode field equal to 0b1110011.

INSTRUCTION: VLE32FF.V
RULE 1: VLE32FF.V executes as a regular load but only takes a trap caused by a synchronous exception on element 0.
RULE 2: If element 0 raises an exception during VLE32FF.V execution, the trap is taken and the architectural vector length register vl is not modified.
RULE 3: If an element with index greater than 0 raises an exception during VLE32FF.V execution, the trap is not taken and vl is reduced to the index of that element.
RULE 4: When vstart equals 0 and vl is greater than 0 for VLE32FF.V, at least one element must be processed.
RULE 5: When VLE32FF.V takes a trap due to an interrupt, the implementation should not reduce vl and should set an appropriate vstart value instead.
RULE 6: When VLE32FF.V would cause a debug data-watchpoint trap on an element beyond the first, the implementation should not reduce vl but should deliver the debug trap so that the event is not lost.
