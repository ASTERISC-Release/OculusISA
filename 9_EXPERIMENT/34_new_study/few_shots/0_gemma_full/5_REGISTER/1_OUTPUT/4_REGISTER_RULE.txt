REGISTER: mseccfg
RULE 1: Software may discover if access to the seed CSR can be enabled in S mode by writing a 1 to the SSEED field of the mseccfg CSR and reading back the result.
RULE 2: Software may discover if access to the seed CSR can be enabled in U mode by writing a 1 to the USEED field of the mseccfg CSR and reading back the result.
RULE 3: The mseccfg register has MRW privilege.
RULE 4: mseccfg is a 64-bit read/write register that controls security features.
RULE 5: When the USEED field in mseccfg is 0, access to the seed CSR in U-mode raises an illegal-instruction exception.
RULE 6: When the USEED field in mseccfg is 1, read-write access to the seed CSR from U-mode is allowed, while all other types of accesses raise an illegal-instruction exception.
RULE 7: The USEED field in mseccfg is read-only zero if Zkr or U-mode is not implemented.
RULE 8: When the SSEED field in mseccfg is 0, access to the seed CSR from S-/HS-mode raises an illegal-instruction exception.
RULE 9: When the SSEED field in mseccfg is 1, read-write access to the seed CSR from S-/HS-mode is allowed, while all other types of accesses raise an illegal-instruction exception.
RULE 10: The SSEED field in mseccfg is read-only zero if Zkr or S-mode is not implemented.
RULE 11: When the H extension is also implemented and the SSEED field in mseccfg is 1, access to the seed CSR from an HS-qualified instruction leads to a virtual-instruction exception in VS and VU modes, while all other types of accesses raise an illegal-instruction exception.
RULE 12: When the SSEED field in mseccfg is 0, any seed CSR access from VS/VU mode raises an illegal-instruction exception.
RULE 13: When the SSEED field in mseccfg is 1, a read-write seed access from VS/VU mode raises a virtual-instruction exception, while other access conditions raise an illegal-instruction exception.
RULE 14: When mseccfg.RLB is 1, locked PMP rules may be removed or modified and locked PMP rules may be edited.
RULE 15: When mseccfg.RLB is 0 and pmpcfg.L is 1 in any rule or entry (including disabled entries), then mseccfg.RLB remains 0 and any further modifications to mseccfg.RLB are ignored until a PMP reset.
RULE 16: mseccfg.MMWP (Machine-Mode Allowlist Policy) is a WARL field.
RULE 17: The mseccfg.MMWP field is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 18: When mseccfg.MMWP is set, the default PMP policy for M-mode when accessing memory regions that don't have a matching PMP rule changes to denied instead of ignored.
RULE 19: mseccfg.MML (Machine Mode Lockdown) is a WARL field.
RULE 20: The mseccfg.MML field is a sticky bit, meaning that once set it cannot be unset until a PMP reset.
RULE 21: When mseccfg.MML is set, pmpcfg.L marks a rule as M-mode-only when set and S/U-mode-only when unset, instead of marking a rule as locked and enforced in all modes.
RULE 22: When mseccfg.MML is set, the encoding pmpcfg.RW=01 and the encoding pmpcfg.LRWX=1111 encode a Shared-Region.
RULE 23: When mseccfg.MML is set, an M-mode-only rule is enforced on Machine mode and denied in Supervisor or User mode.
RULE 24: When mseccfg.MML is set, an M-mode-only rule remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 25: When mseccfg.MML is set, an S/U-mode-only rule is enforced on Supervisor and User modes and denied on Machine mode.
RULE 26: When mseccfg.MML is set, a Shared-Region rule where pmpcfg.L is not set is not executable, M-mode has read/write access to that region, and S/U-mode has read access if pmpcfg.X is not set or read/write access if pmpcfg.X is set.
RULE 27: When mseccfg.MML is set, a Shared-Region rule where pmpcfg.L is set is not writable, both M-mode and S/U-mode have execute access on the region, and M-mode also has read access if pmpcfg.X is set.
RULE 28: When mseccfg.MML is set, a Shared-Region rule where pmpcfg.L is set remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 29: When mseccfg.MML is set, a Shared-Region rule encoded by pmpcfg.LRWX=1111 provides read-only access to the region for both M-mode and S/U mode.
RULE 30: When mseccfg.MML is set, a Shared-Region rule encoded by pmpcfg.LRWX=1111 remains locked so that any further modifications to its associated configuration or address registers are ignored until a PMP reset, unless mseccfg.RLB is set.
RULE 31: When mseccfg.MML is set, adding a rule with executable privileges that is either M-mode-only or a locked Shared-Region is not possible and such pmpcfg writes are ignored, leaving pmpcfg unchanged, unless mseccfg.RLB is set.
RULE 32: When mseccfg.MML is set, executing code with Machine mode privileges is only possible from memory regions with a matching M-mode-only rule or a locked Shared-Region rule with executable privileges.
RULE 33: When mseccfg.MML is set, executing code from a region without a matching rule or with a matching S/U-mode-only rule is denied.
RULE 34: If mseccfg.MML is not set, the combination of pmpcfg.RW=01 remains reserved for future standard use.
RULE 35: When the PMM field in mseccfg is 00, pointer masking is disabled (PMLEN = 0).
RULE 36: When the PMM field in mseccfg is 10, pointer masking is enabled with PMLEN = XLEN - 57.
RULE 37: When the PMM field in mseccfg is 11, pointer masking is enabled with PMLEN = XLEN - 48.
RULE 38: The PMM field in mseccfg is read-only zero if Smmpm is not implemented.
RULE 39: When the MLPE field in mseccfg is 1, Zicfilp extension is enabled in M-mode.
RULE 40: When the MLPE field in mseccfg is 0, the Zicfilp extension is not enabled in M-mode, the hart does not update the ELP state (it remains as NO_LP_EXPECTED), and the LPAD instruction operates as a no-op.
RULE 41: If the Zicfilp extension is implemented, the mseccfg.MLPE field is reset to 0.
RULE 42: Upon reset, the MML field of the mseccfg register is set to 0, unless the platform mandates a different reset value.
RULE 43: Upon reset, the MMWP field of the mseccfg register is set to 0, unless the platform mandates a different reset value.
RULE 44: Upon reset, the RLB field of the mseccfg register is set to 0, unless the platform mandates a different reset value.
RULE 45: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=0, pmpcfg W=0, and pmpcfg X=0 results in an inaccessible region causing an access exception for both M mode and S/U mode.
RULE 46: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=0, pmpcfg W=0, and pmpcfg X=1 results in an access exception for M mode and an execute-only region for S/U mode.
RULE 47: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=0, pmpcfg W=1, and pmpcfg X=0 results in a shared data region that is read/write on M mode and read-only on S/U mode for both M mode and S/U mode.
RULE 48: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=0, pmpcfg W=1, and pmpcfg X=1 results in a shared data region that is read/write for both M mode and S/U mode.
RULE 49: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=1, pmpcfg W=0, and pmpcfg X=0 results in an access exception for M mode and a read-only region for S/U mode.
RULE 50: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=1, pmpcfg W=0, and pmpcfg X=1 results in an access exception for M mode and a read/execute region for S/U mode.
RULE 51: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=1, pmpcfg W=1, and pmpcfg X=0 results in an access exception for M mode and a read/write region for S/U mode.
RULE 52: When mseccfg.MML is set to 1, pmpcfg L=0, pmpcfg R=1, pmpcfg W=1, and pmpcfg X=1 results in an access exception for M mode and a read/write/execute region for S/U mode.
RULE 53: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=0, pmpcfg W=0, and pmpcfg X=0 results in a locked inaccessible region causing an access exception for both M mode and S/U mode.
RULE 54: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=0, pmpcfg W=0, and pmpcfg X=1 results in a locked execute-only region for M mode and an access exception for S/U mode.
RULE 55: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=0, pmpcfg W=1, and pmpcfg X=0 results in a locked shared code region that is execute only on both M mode and S/U mode.
RULE 56: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=0, pmpcfg W=1, and pmpcfg X=1 results in a locked shared code region that is execute only on S/U mode and read/execute on M mode.
RULE 57: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=1, pmpcfg W=0, and pmpcfg X=0 results in a locked read-only region for M mode and an access exception for S/U mode.
RULE 58: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=1, pmpcfg W=0, and pmpcfg X=1 results in a locked read/execute region for M mode and an access exception for S/U mode.
RULE 59: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=1, pmpcfg W=1, and pmpcfg X=0 results in a locked read/write region for M mode and an access exception for S/U mode.
RULE 60: When mseccfg.MML is set to 1, pmpcfg L=1, pmpcfg R=1, pmpcfg W=1, and pmpcfg X=1 results in a locked shared data region that is read only on both M mode and S/U mode.
RULE 61: When S-mode is implemented, the xLPE for privilege mode M is determined by mseccfg.MLPE.
RULE 62: When S-mode is not implemented, the xLPE for privilege mode M is determined by mseccfg.MLPE.
RULE 63: In M-mode, accessing mseccfg register should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: NONE; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 64: In S-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_supervisor; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 65: In U-mode, accessing mseccfg register should result in illegal-instruction exception (# Result: mcause = 0x2) [# Extension Must Be Active: NONE; call machine_to_user; csrr a0, 0x747; # Result: mcause = 0x2].
RULE 66: In M-mode, setting mseccfg.SSEED (bit 9) should be reflected on the readback (# Result: a2 = 0x200) [# Extension Must Be Active: NONE; li a0, 0x200; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x200].
RULE 67: In M-mode, setting mseccfg.USEED (bit 8) should be reflected on the readback (# Result: a2 = 0x100) [# Extension Must Be Active: NONE; li a0, 0x100; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x100].
RULE 68: In M-mode, setting mseccfg.RLB (bit 2) should be reflected on the readback (# Result: a2 = 0x4) [# Extension Must Be Active: NONE; li a0, 0x4; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x4].
RULE 69: In M-mode, setting mseccfg.MMWP (bit 1) should be reflected on the readback (# Result: a2 = 0x2) [# Extension Must Be Active: NONE; li a0, 0x2; csrs 0x747, a0; csrr a1, 0x747; and a2, a0, a1; # Result: a2 = 0x2].
RULE 70: In M-mode, accessing mseccfg register while Smepmp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smepmp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 71: In M-mode, accessing mseccfg register while Smmpm extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Smmpm; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 72: In M-mode, accessing mseccfg register while Zicfilp extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zicfilp; csrr a0, 0x747; # Result: mcause = 0x0].
RULE 73: In M-mode, accessing mseccfg register while Zkr extension is active should result in no exception (# Result: mcause = 0x0) [# Extension Must Be Active: Zkr; csrr a0, 0x747; # Result: mcause = 0x0].

REGISTER: mstatus
RULE 1: When the TW (Timeout Wait) bit in mstatus is set and WRS.NTO is executed in any privilege mode other than M mode, and it does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause an illegal-instruction exception.
RULE 2: When executing in VS or VU mode, if the VTW bit is set in hstatus, the TW bit in mstatus is clear, and the WRS.NTO does not complete within an implementation-specific bounded time limit, the WRS.NTO instruction will cause a virtual-instruction exception.
RULE 3: If the Zfinx extension is implemented, the mstatus field FS is hardwired to 0.
RULE 4: If the Zfinx extension is implemented, the mstatus field FS no longer affects the trapping behavior of floating-point instructions or fcsr accesses.
RULE 5: The mstatus register contains a vector context status field, VS, in bits [10:9].
RULE 6: The mstatus.VS field is shadowed in sstatus[10:9].
RULE 7: Attempts to execute any vector instruction or access the vector CSRs raise an illegal-instruction exception when mstatus.VS is set to Off.
RULE 8: Executing any instruction that changes vector state, including the vector CSRs, will change mstatus.VS to Dirty when mstatus.VS is set to Initial or Clean.
RULE 9: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 10: If mstatus.VS is not Dirty, mstatus.SD is set in accordance with existing specifications.
RULE 11: When V=1, attempts to execute any vector instruction or access vector CSRs raise an illegal-instruction exception if mstatus.VS is set to Off, regardless of the value of vsstatus.VS.
RULE 12: When V=1, attempts to execute any vector instruction or access vector CSRs raise an illegal-instruction exception if vsstatus.VS is set to Off, regardless of the value of mstatus.VS.
RULE 13: When V=1 and neither vsstatus.VS nor mstatus.VS is set to Off, executing any instruction that changes vector state, including the vector CSRs, will change mstatus.VS to Dirty.
RULE 14: When V=1 and neither vsstatus.VS nor mstatus.VS is set to Off, executing any instruction that changes vector state, including the vector CSRs, will change vsstatus.VS to Dirty.
RULE 15: If mstatus.VS is Dirty, mstatus.SD is 1.
RULE 16: If mstatus.VS is not Dirty, mstatus.SD is set in accordance with existing specifications.
RULE 17: If the floating-point unit status field mstatus.FS is Off, then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 18: Any vector floating-point instruction that modifies any floating-point extension state, such as floating-point CSRs or f registers, must set mstatus.FS to Dirty.
RULE 19: If the hypervisor extension is implemented and V=1, and either vsstatus.FS or mstatus.FS is Off, then any attempt to execute a vector floating-point instruction will raise an illegal-instruction exception.
RULE 20: If the hypervisor extension is implemented and V=1, any vector floating-point instruction that modifies any floating-point extension state, such as floating-point CSRs or f registers, must set both mstatus.FS and vsstatus.FS to Dirty.
RULE 21: The mstatus register has MRW privilege.
RULE 22: The mstatus register provides global interrupt-enable bits MIE and SIE for M-mode and S-mode respectively.
RULE 23: If supervisor mode is not implemented, then SIE and SPIE in mstatus are read-only 0.
RULE 24: The xPIE field in mstatus holds the value of the interrupt-enable bit active prior to the trap.
RULE 25: The xPP field in mstatus holds the previous privilege mode.
RULE 26: When a trap is taken from privilege mode y into privilege mode x, the xPIE field in mstatus is set to the value of xIE.
RULE 27: When a trap is taken from privilege mode y into privilege mode x, the xIE field in mstatus is set to 0.
RULE 28: When a trap is taken from privilege mode y into privilege mode x, the xPP field in mstatus is set to y.
RULE 29: When executing an xRET instruction (MRET or SRET), if xPP in mstatus holds the value y, xIE in mstatus is set to xPIE.
RULE 30: When executing an xRET instruction (MRET or SRET), if xPP in mstatus holds the value y, the privilege mode is changed to y.
RULE 31: When executing an xRET instruction (MRET or SRET), if xPP in mstatus holds the value y, xPIE in mstatus is set to 1.
RULE 32: When executing an xRET instruction (MRET or SRET), if xPP in mstatus holds the value y, xPP in mstatus is set to the least-privileged supported mode (U if U-mode is implemented, else M).
RULE 33: When executing an xRET instruction, if the value y held in xPP of mstatus is not equal to M, xRET also sets MPRV in mstatus to 0.
RULE 34: The xPP fields in mstatus are WARL fields that can hold only privilege mode x and any implemented privilege mode lower than x.
RULE 35: If privilege mode x is not implemented, then xPP in mstatus must be read-only 0.
RULE 36: M-mode software can determine whether a privilege mode is implemented by writing that mode to MPP in mstatus then reading it back.
RULE 37: The MDT field in the mstatus register is set to 1 upon reset.
RULE 38: When the MDT bit in the mstatus register is set to 1 by an explicit CSR write, the MIE (Machine Interrupt Enable) bit in the mstatus register is cleared to 0.
RULE 39: For RV64, the clearing of the MIE bit in the mstatus register occurs regardless of the value written, if any, to the MIE bit by the same write that sets the MDT bit to 1.
RULE 40: The MIE bit in the mstatus register can only be set to 1 by an explicit CSR write if the MDT bit in the mstatus register is already 0 or, for RV64, if the MDT bit in the mstatus register is being set to 0 by the same write.
RULE 41: When a trap is to be taken into M-mode, if the MDT bit in the mstatus register is currently 0, the MDT bit in the mstatus register is set to 1 and the trap is delivered as expected.
RULE 42: When a trap is to be taken into M-mode, if the MDT bit in the mstatus register is already set to 1, then this is an unexpected trap.
RULE 43: When the Smrnmi extension is implemented, a trap caused by an RNMI is not considered an unexpected trap irrespective of the state of the MDT bit in the mstatus register.
RULE 44: When the Smrnmi extension is implemented, a trap caused by an RNMI does not set the MDT bit in the mstatus register.
RULE 45: A trap that occurs when executing in M-mode with mnstatus.NMIE set to 0 is an unexpected trap.
RULE 46: In the event of an unexpected trap, if the Smrnmi extension is implemented and mnstatus.NMIE is 1, the hart traps to the RNMI handler, and the privilege mode information fields in the mnstatus register are written to indicate M-mode and its NMIE field is set to 0.
RULE 47: In the event of an unexpected trap, if the Smrnmi extension is not implemented, or if the Smrnmi extension is implemented and mnstatus.NMIE is 0, the hart enters a critical-error state without updating any architectural state, including the pc or the mstatus register.
RULE 48: The MRET and SRET instructions, when executed in M-mode, set the MDT bit in the mstatus register to 0.
RULE 49: The MNRET instruction, provided by the Smrnmi extension, sets the MDT bit in the mstatus register to 0 if the new privilege mode is not M.
RULE 50: For RV64 harts, the SXL field of mstatus is a WARL field that controls the value of XLEN for S-mode.
RULE 51: For RV64 harts, the UXL field of mstatus is a WARL field that controls the value of XLEN for U-mode.
RULE 52: When MXLEN=64 and S-mode is not supported, the SXL field of mstatus is read-only zero.
RULE 53: When MXLEN=64 and S-mode is supported, the SXL field of mstatus is a WARL field that encodes the current value of SXLEN.
RULE 54: When MXLEN=64 and U-mode is not supported, the UXL field of mstatus is read-only zero.
RULE 55: When MXLEN=64 and U-mode is supported, the UXL field of mstatus is a WARL field that encodes the current value of UXLEN.
RULE 56: If S-mode is implemented, the set of legal values that the UXL field of mstatus may assume excludes those that would cause UXLEN to be greater than SXLEN.
RULE 57: The MPRV bit in mstatus modifies the effective privilege mode, which is the privilege level at which explicit memory accesses execute.
RULE 58: When the MPRV bit in mstatus is 0, explicit memory accesses behave as normal, using the translation and protection mechanisms of the current privilege mode.
RULE 59: When the MPRV bit in mstatus is 1, load and store memory addresses are translated and protected, and endianness is applied, as though the current privilege mode were set to MPP.
RULE 60: Instruction address-translation and protection are unaffected by the setting of the MPRV bit in mstatus.
RULE 61: The MPRV bit in mstatus is read-only 0 if U-mode is not supported.
RULE 62: An MRET or SRET instruction that changes the privilege mode to a mode less privileged than M also sets the MPRV bit in mstatus to 0.
RULE 63: When the MPRV bit in mstatus is 1, load and store memory addresses are treated as though the current XLEN were set to MPP's XLEN.
RULE 64: The SUM bit in mstatus is in effect when the MPRV bit in mstatus is 1 and MPP is S.
RULE 65: When the MXR bit in mstatus is 0, only loads from pages marked readable (R=1) will succeed.
RULE 66: When the MXR bit in mstatus is 1, loads from pages marked either readable or executable (R=1 or X=1) will succeed.
RULE 67: The MXR bit in mstatus has no effect when page-based virtual memory is not in effect.
RULE 68: The MXR bit in mstatus is read-only 0 if S-mode is not supported.
RULE 69: When the SUM bit in mstatus is 0, S-mode memory accesses to pages that are accessible by U-mode (U=1) will fault.
RULE 70: When the SUM bit in mstatus is 1, S-mode memory accesses to pages that are accessible by U-mode (U=1) are permitted.
RULE 71: The SUM bit in mstatus has no effect when page-based virtual memory is not in effect.
RULE 72: The SUM bit in mstatus is read-only 0 if S-mode is not supported or if satp.MODE is read-only 0.
RULE 73: The MBE, SBE, and UBE bits in mstatus and mstatush are WARL fields that control the endianness of memory accesses other than instruction fetches.
RULE 74: The MBE field in mstatus controls whether non-instruction-fetch memory accesses made from M-mode (assuming mstatus.MPRV=0) are little-endian (MBE=0) or big-endian (MBE=1).
RULE 75: The SBE field in mstatus is read-only 0 if S-mode is not supported.
RULE 76: The SBE field in mstatus controls whether explicit load and store memory accesses made from S-mode are little-endian (SBE=0) or big-endian (SBE=1) if S-mode is supported.
RULE 77: The UBE field in mstatus is read-only 0 if U-mode is not supported.
RULE 78: The UBE field in mstatus controls whether explicit load and store memory accesses made from U-mode are little-endian (UBE=0) or big-endian (UBE=1) if U-mode is supported.
RULE 79: Endianness for implicit accesses to supervisor-level memory management data structures, such as page tables, is always controlled by the SBE field in mstatus.
RULE 80: An implementation supports only little-endian memory accesses if the MBE, SBE, and UBE fields in mstatus are all read-only 0.
RULE 81: An implementation supports only big-endian memory accesses (aside from instruction fetches) if the MBE field in mstatus is read-only 1 and the SBE and UBE fields in mstatus are each read-only 1 when S-mode and U-mode are supported.
RULE 82: The TVM (Trap Virtual Memory) bit in mstatus is a WARL field.
RULE 83: When the TVM bit in mstatus is 1, attempts to read or write the satp CSR or execute an SFENCE.VMA or SINVAL.VMA instruction while executing in S-mode will raise an illegal-instruction exception.
RULE 84: When the TVM bit in mstatus is 0, attempts to read or write the satp CSR or execute an SFENCE.VMA or SINVAL.VMA instruction are permitted in S-mode.
RULE 85: The TVM bit in mstatus is read-only 0 when S-mode is not supported.
RULE 86: The TW (Timeout Wait) bit in mstatus is a WARL field.
RULE 87: The TW bit in mstatus is read-only 0 when there are no modes less privileged than M.
RULE 88: The TSR (Trap SRET) bit in mstatus is a WARL field.
RULE 89: When the TSR bit in mstatus is 1, attempts to execute SRET while executing in S-mode will raise an illegal-instruction exception.
RULE 90: When the TSR bit in mstatus is 0, executing SRET while executing in S-mode is permitted in S-mode.
RULE 91: The TSR bit in mstatus is read-only 0 when S-mode is not supported.
RULE 92: The mstatus register contains a WARL field FS[1:0] that encodes the status of the floating-point unit state, including the floating-point registers f0-f31 and the CSRs fcsr, frm, and fflags.
RULE 93: The mstatus register contains a WARL field VS[1:0] that encodes the status of the vector extension state, including the vector registers v0-v31 and the CSRs vcsr, vxrm, vxsat, vstart, vl, vtype, and vlenb.
RULE 94: The mstatus register contains a read-only field XS[1:0] that encodes the status of additional user-mode extensions and associated state.
RULE 95: The mstatus register contains a read-only bit SD that summarizes whether either the FS, VS, or XS fields signal the presence of some dirty state that will require saving extended user context to memory.
RULE 96: The SD bit in mstatus is set when either the FS, VS, or XS bits encode a Dirty state, such that SD=(FS==0b11 OR XS==0b11 OR VS==0b11).
RULE 97: If the FS, XS, and VS fields in mstatus are all readonly zero, then the SD bit in mstatus is also always zero.
RULE 98: In the mstatus FS and VS fields, a status value of 0 means Off.
RULE 99: In the mstatus FS and VS fields, a status value of 1 means Initial.
RULE 100: In the mstatus FS and VS fields, a status value of 2 means Clean.
RULE 101: In the mstatus FS and VS fields, a status value of 3 means Dirty.
RULE 102: In the mstatus XS field, a status value of 0 means All off.
RULE 103: In the mstatus XS field, a status value of 1 means None dirty or clean, some on.
RULE 104: In the mstatus XS field, a status value of 2 means None dirty, some clean.
RULE 105: In the mstatus XS field, a status value of 3 means Some dirty.
RULE 106: If the F extension is implemented, the FS field in mstatus shall not be read-only zero.
RULE 107: If neither the F extension nor S-mode is implemented, then the FS field in mstatus is read-only zero.
RULE 108: Changing the setting of the FS field in mstatus has no effect on the contents of the floating-point register state.
RULE 109: Setting the FS field in mstatus to Off does not destroy the floating-point register state.
