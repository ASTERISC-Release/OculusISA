RULE 1: If SFENCE.VMA is executed in S-mode or M-mode when mstatus.TVM is 0, the instruction does not trap for lack of privilege.
RULE 2: If SFENCE.VMA is executed in U-mode, the instruction raises an illegal-instruction exception.
RULE 3: If SFENCE.VMA is executed in S-mode when mstatus.TVM is 1, the instruction raises an illegal-instruction exception.
RULE 4: If SFENCE.VMA is executed, the instruction does not write any integer register.
RULE 5: If SFENCE.VMA is executed, the instruction does not change any CSR state.
RULE 6: If SFENCE.VMA is executed with rs1 = x0 and rs2 = x0, all previous stores already visible to the executing hart are ordered before all subsequent implicit address-translation memory references by that hart.
RULE 7: If SFENCE.VMA is executed with rs1 != x0 and rs2 = x0, all previous stores already visible to the executing hart are ordered before subsequent implicit address-translation memory references by that hart for the virtual address contained in rs1.
RULE 8: If SFENCE.VMA is executed with rs1 = x0 and rs2 != x0, all previous stores already visible to the executing hart are ordered before subsequent implicit address-translation memory references by that hart for address translations associated with the ASID contained in rs2.
RULE 9: If SFENCE.VMA is executed with rs1 != x0 and rs2 != x0, all previous stores already visible to the executing hart are ordered before subsequent implicit address-translation memory references by that hart for the virtual address contained in rs1 and the ASID contained in rs2.
RULE 10: If SFENCE.VMA is executed with rs2 != x0, the instruction also orders previous stores already visible to the executing hart before subsequent implicit address-translation memory references by that hart for global mappings, regardless of the ASID value in rs2.
RULE 11: If SFENCE.VMA is executed with rs1 != x0, the instruction does not order subsequent implicit address-translation memory references for virtual addresses other than the virtual address contained in rs1, except as otherwise required by the architecture.
RULE 12: If SFENCE.VMA is executed with rs2 != x0, the instruction does not order subsequent implicit address-translation memory references for non-global mappings associated with ASIDs other than the ASID contained in rs2, except as otherwise required by the architecture.
RULE 13: If SFENCE.VMA is executed, its ordering effect applies only to subsequent implicit address-translation memory references made by the executing hart.
RULE 14: If SFENCE.VMA is executed, its ordering effect does not apply to implicit address-translation memory references made by other harts.
RULE 15: If SFENCE.VMA is executed, the instruction does not by itself make stores visible to other harts.
RULE 16: If SFENCE.VMA is executed, the instruction does not by itself order previous stores before subsequent explicit memory accesses.
RULE 17: If SFENCE.VMA is executed when address translation is disabled, the instruction still executes subject to its privilege checks.
RULE 18: If SFENCE.VMA is executed with a value in rs1 that is not a valid virtual address, the instruction does not raise an exception solely because of that invalid virtual-address value.
RULE 19: If SFENCE.VMA is executed with a value in rs2 whose bits exceed the implemented ASID width, those unimplemented ASID bits are ignored for the ASID-selective effect of the instruction.
RULE 20: If SFENCE.VMA is executed with rs2 != x0, the ASID used for the ASID-selective effect is the implemented ASID field value contained in rs2.
RULE 21: If a hart modifies a page table and then executes an appropriately scoped SFENCE.VMA, subsequent address translations by that same hart within the scope of the SFENCE.VMA must observe the page-table modification or a later modification in the memory order.
RULE 22: If a hart modifies a page table but does not execute an appropriately scoped SFENCE.VMA, subsequent address translations by that hart may use either the old translation or the new translation when both are otherwise architecturally valid.
RULE 23: If software changes satp to select a different address space and the change is not ordered by an appropriate SFENCE.VMA, subsequent address translations may use translations associated with the previous address space when those translations are not otherwise disambiguated by ASID.
RULE 24: If software changes satp and executes an appropriately scoped SFENCE.VMA, subsequent address translations by that hart within the scope of the SFENCE.VMA are ordered after the address-space change.
RULE 25: If a page-table entry is modified from invalid to valid and an appropriately scoped SFENCE.VMA is executed after the store, subsequent address translations by that hart within the scope of the SFENCE.VMA must not fault solely because they used the previous invalid entry.
RULE 26: If a page-table entry is modified from valid to invalid and an appropriately scoped SFENCE.VMA is executed after the store, subsequent address translations by that hart within the scope of the SFENCE.VMA must not use the previous valid translation.
RULE 27: If a page-table entry is modified from one valid translation to another valid translation and no appropriately scoped SFENCE.VMA is executed, subsequent address translations by that hart may use either valid translation.
RULE 28: If a page-table entry is modified from one valid translation to another valid translation and an appropriately scoped SFENCE.VMA is executed after the store, subsequent address translations by that hart within the scope of the SFENCE.VMA must use the new translation or a later translation.
RULE 29: If a page-table entry’s permission bits are made more restrictive and no appropriately scoped SFENCE.VMA is executed, subsequent address translations by that hart may continue to use the previous less-restrictive permissions.
RULE 30: If a page-table entry’s permission bits are made more restrictive and an appropriately scoped SFENCE.VMA is executed after the store, subsequent address translations by that hart within the scope of the SFENCE.VMA must enforce the new permissions or later permissions.
RULE 31: If a page-table entry’s permission bits are made more permissive and no appropriately scoped SFENCE.VMA is executed, subsequent address translations by that hart may either use the previous less-permissive permissions or the new more-permissive permissions.
RULE 32: If a page-table entry’s permission bits are made more permissive and an appropriately scoped SFENCE.VMA is executed after the store, subsequent address translations by that hart within the scope of the SFENCE.VMA must enforce the new permissions or later permissions.
RULE 33: If SFENCE.VMA is executed while virtualization is active in VS-mode, the instruction raises a virtual-instruction exception unless permitted by the hypervisor virtualization controls.
RULE 34: If SFENCE.VMA is executed in VS-mode and is permitted by the hypervisor virtualization controls, its ordering effect applies to VS-stage address translations for the executing virtual hart.
RULE 35: If SFENCE.VMA is executed in VS-mode and is permitted by the hypervisor virtualization controls, its ordering effect does not by itself apply to G-stage address translations.
RULE 36: If SFENCE.VMA is executed in HS-mode, its ordering effect applies to address translations controlled by satp, not to VS-stage translations controlled by vsatp.
RULE 37: If SFENCE.VMA is executed in HS-mode, the instruction does not by itself order prior stores before subsequent implicit memory references for G-stage address translation controlled by hgatp.
RULE 38: If a trapped or intercepted SFENCE.VMA instruction raises an exception, the instruction has no architectural ordering effect.
