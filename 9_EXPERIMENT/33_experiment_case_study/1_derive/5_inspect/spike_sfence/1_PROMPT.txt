Convert each given path into exactly one atomic architectural rule.

Input format:

* Source behavior or semantic behavior
* Architectural outcome
* Observable oracle
* Feasibility
* Natural language path summary

Important:
Use ONLY the given paths and path summaries.
Do NOT use external knowledge.
Do NOT use the RISC-V specification unless it is explicitly included in the given path.
Do NOT use known bugs.
Do NOT infer unrelated behavior.
Do NOT merge paths.
Do NOT skip paths.
Do NOT deduplicate paths.
Do NOT collapse multiple similar paths into one rule.
If the input contains N paths, the output must contain exactly N rules.
Each path must produce exactly one rule.
Preserve the path number from the input.
Base each rule only on the explicit condition and outcome stated in the corresponding path.

Rule requirements:
Each rule must be a single testable statement.
Each rule must be atomic.
Each rule must express exactly one architectural behavior or one event -> outcome relationship.
Each rule must describe behavioral semantics, not naming, encoding, syntax, formatting, source-code structure, or implementation commentary.
Each rule must describe architectural cause -> effect semantics, meaning condition/event -> architectural outcome.
Each rule must include the architectural condition and the architectural outcome.
Each rule must be testable using architectural observations such as trap cause, CSR state, register state, memory state, address-translation behavior, or trap versus no trap behavior.
Each rule must begin with the word `RULE`.
Each rule must preserve the path number from the input.
Each rule must be clear and detailed.
Do not mention source file names, function names, helper names, or model-internal names unless they are necessary to express the architectural condition or outcome.
Do not include implementation details unless they directly determine an architecturally visible outcome.
If a path contains both source/model behavior and architectural outcome, write the rule using the architectural outcome.
If a path contains feasibility information, do not output the feasibility field; use it only to avoid inventing unsupported behavior.
If a path is marked source-incomplete, produce a rule only from the explicit behavior that is present in the path and do not invent the missing behavior.
If a path is marked infeasible, still output one rule for that path, but phrase it only as the explicit condition -> outcome relationship stated by the path.

Output format:
Output only the rules.
Do not give any introduction.
Do not give headings.
Do not give bullet points.
Do not include explanations.
Do not include citations.
Do not include blank lines between rules.

Required rule format:
RULE <path number>: <one atomic testable architectural rule>
